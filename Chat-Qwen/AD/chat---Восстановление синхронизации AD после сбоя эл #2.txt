### Шаг 1 — Поиск точного пути (DN) подписки SYSVOL в AD

**[Объяснение / действие]**
Предыдущая ошибка `PathNotFound` возникла из-за того, что в современных версиях Windows Server (при использовании DFSR) параметры репликации SYSVOL больше не хранятся в локальном реестре. Локальный реестр (и параметр `BurFlags`) использовался только для устаревшей службы FRS. В случае с DFSR параметры подписки хранятся как атрибуты в базе самого Active Directory (в разделе Configuration) .

Чтобы выполнить неавторитетное восстановление (аналог D2), нам нужно будет временно отключить репликацию, изменив атрибут `msDFSR-Enabled` на `FALSE` в AD.
Чтобы исключить ошибку в имени сервера (так как NetBIOS имя хоста ОС и имя объекта компьютера в AD иногда могут отличаться), сначала выполним безопасную read-only команду для поиска точного Distinguished Name (DN) нужного объекта.

Выполните следующую команду в PowerShell (от имени администратора домена) на сервере 192.168.200.225:

```powershell
Get-ADObject -LDAPFilter "(objectClass=msDFSR-Subscription)" -SearchBase "CN=DFSR-LocalSettings,CN=$env:COMPUTERNAME,OU=Domain Controllers,DC=krnn,DC=ru" -Properties msDFSR-Enabled, distinguishedName, msDFSR-RootPath | Format-List
```

**Сверка с environment_facts:** Домен `krnn.ru` учтен в `SearchBase`. Имя сервера подставляется автоматически через `$env:COMPUTERNAME`, что исключает опечатки.
**Как проверить результат:** Команда должна вернуть объект, в котором будут поля `distinguishedName` (начинается с `CN=SYSVOL Subscription,CN=Domain System Volume...`) и `msDFSR-Enabled` (скорее всего, `True`).
**Риск:** Нет (команда только читает данные из AD).
**Идемпотентность:** Идемпотентно, можно повторять при сбое.
**Откат:** Не требуется.
**Ожидаемое время:** < 1 мин.
**Уверенность:** Высокий — методика основана на официальной документации Microsoft по принудительной синхронизации DFSR-replicated SYSVOL .
**Протокол (обновлённый, коротко):** Установлено, что локальный реестр не содержит параметров DFSR (это было справедливо только для FRS). Параметры хранятся в AD. Выполняется поиск DN объекта подписки SYSVOL для последующего изменения атрибута `msDFSR-Enabled`.

# Протокол переноса (версия промта: v6)
**Задача:** Восстановление репликации SYSVOL (DFSR) на контроллере домена AD после сбоя питания методом неавторитетного восстановления (D2).
**Тип / режим:** Изменение / Подробный.
**Окружение:** Proxmox VE (узел pve01, 192.168.202.121), ВМ 2002 (AD, Windows Server 2025, 192.168.200.225). Домен: krnn.ru. Партнеры репликации: DC (192.168.200.2), ANDQ (192.168.200.10).
**Environment_facts:** Ключевые параметры указаны выше. Снапшот ВМ 2002 создан: `before-d2-sysvol-restor...` (2026-10-27 18:07:23).

**Зафиксировано:**
1. Репликация базы данных AD полностью восстановлена (ошибка 8453 устранена путем установки `127.0.0.1` первым DNS-сервером на адаптере Ethernet сервера AD). `repadmin /showrepl` показывает 0 сбоев.
2. Репликация SYSVOL застряла в `State: 2` (Initial Sync). Коренная причина: событие DFSR 4012 (ошибка 9061, MaxOfflineTimeInDays) из-за повреждения журнала USN при внезапном отключении питания. Служба DFSR намеренно закрыла порт 5722.
3. GUID реплицируемой папки SYSVOL (из лога события 4012): `731DD3EA-8C59-42FD-90C4-5E9DFFE0A741`.
4. Предыдущая попытка initiate D2-восстановления приостановлена: предложенный ассистентом путь реестра для параметра `Enabled` не существовал (ошибка ассистента, правило v6 п.18, признана). 
5. Текущий статус службы `dfsr` на сервере AD: `Running`.

**Текущий шаг:** 
1. Найти *реальный, существующий* путь в реестре для параметра `Enabled` данной группы репликации (избегая предыдущей галлюцинации с путем).
2. Остановить службу `dfsr` (`Stop-Service dfsr -Force`).
3. Изменить значение `Enabled` на `2` (Non-Authoritative Restore).
4. Запустить службу `dfsr` и проконтролировать переход SYSVOL в `State: 4` (Normal).

**Открытые вопросы:** Нет.
**Последний вывод:** Команда `Get-ItemProperty` вернула `PathNotFound` для неверного пути. Команда `Get-Service dfsr` вернула статус `Running`.

### Шаг 1.1 — Уточнение механизма D2 для DFSR и проверка текущего состояния в AD

**[Объяснение / действие]**
Критически важное уточнение: в современных версиях Windows Server (где SYSVOL реплицируется через DFSR, а не через устаревшую FRS) процедура неавторитетного восстановления (D2) **выполняется не через локальный реестр Windows**, а через **изменение атрибутов в самом Active Directory**. 

Локальный реестр (ключи вроде `BurFlags`) использовался только для FRS. Для DFSR аналогом является атрибут `msDFSR-Enabled` у объекта подписки SYSVOL в AD. Службу DFSR останавливать для выполнения D2 также **не требуется**.

Чтобы исключить любые ошибки и галлюцинации с путями, мы будем работать с AD напрямую через PowerShell. Сначала выполним безопасную read-only команду, которая найдет точный Distinguished Name (DN) объекта подписки SYSVOL на текущем сервере и покажет текущее значение атрибута `msDFSR-Enabled`.

Выполните следующую команду в PowerShell (от имени администратора):

```powershell
$dn = "CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=$env:COMPUTERNAME,OU=Domain Controllers,DC=krnn,DC=ru"
Get-ADObject -Identity $dn -Properties msDFSR-Enabled, distinguishedName | Select-Object distinguishedName, msDFSR-Enabled
```

**Сверка с environment_facts:** Домен `krnn.ru` учтен в DN. Имя сервера подставляется автоматически через `$env:COMPUTERNAME`, что исключает опечатки в NetBIOS-имени объекта в AD.
**Как проверить результат:** Команда должна вернуть объект, в котором поле `msDFSR-Enabled` имеет значение `True` (или `TRUE`).
**Риск:** Нет (команда только читает данные из AD, ничего не меняет).
**Идемпотентность:** Идемпотентно, можно повторять при сбое.
**Откат:** Не требуется.
**Ожидаемое время:** < 1 мин.
**Уверенность:** Высокий — методика основана на официальной документации Microsoft по принудительной синхронизации DFSR-replicated SYSVOL (раздел *How to perform a non-authoritative synchronization of DFSR-replicated sysvol replication*).
**Протокол (обновлённый, коротко):** Установлено, что для DFSR D2-восстановление выполняется через атрибут `msDFSR-Enabled` в AD, а не через локальный реестр (как было в FRS). Выполняется read-only проверка текущего состояния объекта в AD.
**Вопросы:** Пришлите вывод команды целиком.

### Шаг 1.2 — Проверка состояния SYSVOL на всех контроллерах домена перед отключением репликации

**[Объяснение / действие]**
Отлично, мы нашли точный Distinguished Name объекта подписки SYSVOL на текущем сервере:
`CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru`
Текущее значение атрибута `msDFSR-Enabled` = `True`. Имя сервера в AD (CN) — `AD`.

**Критически важный момент безопасности:** Перед тем как мы переведем текущий DC (AD, 192.168.200.225) в режим неавторитетного восстановления (D2), мы должны убедиться, что на другом рабочем DC (партнере по репликации, 192.168.200.2 или 192.168.200.10) SYSVOL находится в нормальном состоянии и репликация включена (`msDFSR-Enabled = True`). Если мы случайно отключим репликацию SYSVOL на всех DC одновременно, она встанет полностью, и восстановить её будет сложнее.

Поэтому сначала выполним безопасную read-only команду, которая покажет состояние SYSVOL на всех контроллерах домена.

Выполните следующую команду в PowerShell:

```powershell
Get-ADObject -LDAPFilter "(objectClass=msDFSR-Subscription)" -SearchBase "OU=Domain Controllers,DC=krnn,DC=ru" -Properties msDFSR-Enabled, distinguishedName | Format-Table distinguishedName, msDFSR-Enabled -AutoSize
```

**Сверка с environment_facts:** Домен `krnn.ru` учтен в `SearchBase`. Команда не меняет состояние системы, только читает атрибуты из AD.
**Как проверить результат:** В выводе должны быть перечислены все DC домена (включая `CN=AD`, `CN=DC` и, возможно, другие). Убедитесь, что на другом DC (не `CN=AD`) значение `msDFSR-Enabled` равно `True`.
**Риск:** Нет (команда только читает данные из AD).
**Идемпотентность:** Идемпотентно.
**Откат:** Не требуется.
**Ожидаемое время:** < 1 мин.
**Уверенность:** Высокий — команда использует стандартный LDAP-фильтр для поиска объектов подписки DFSR в AD.
**Протокол (обновлённый, коротко):** Найден точный DN объекта подписки SYSVOL на сервере AD: `CN=SYSVOL Subscription,...,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru`. ### Шаг 2.1 — Отключение репликации SYSVOL на проблемном контроллере домена (AD)

**[Объяснение / действие]**
Отлично. Вывод подтверждает, что в домене `krnn.ru` есть два контроллера домена: `DC` и `AD`. На обоих атрибут `msDFSR-Enabled` имеет значение `True`. Это идеальная ситуация для начала неавторитетного восстановления (D2) на сервере `AD`, так как у нас есть здоровый партнер (`DC`), который выступит в качестве источника для синхронизации.

Согласно официальной методике Microsoft, первый шаг процедуры D2 для DFSR — это установка атрибута `msDFSR-Enabled` в значение `$false` для объекта подписки SYSVOL на проблемном сервере. Это заставит службу DFSR остановить репликацию SYSVOL и подготовить её к повторной инициализации. Службу `dfsr` при этом останавливать **не нужно**.

Выполните следующую команду в PowerShell (от имени администратора) на сервере `AD` (192.168.200.225):

```powershell
Set-ADObject -Identity "CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru" -Replace @{msDFSR-Enabled=$false}
```

**Сверка с environment_facts:** Используется точный `distinguishedName`, полученный на предыдущем шаге для сервера `AD` в домене `krnn.ru`.
**Как проверить результат:** Команда не должна вывести никаких сообщений об ошибке (успешное выполнение проходит молча). Для уверенности можно сразу выполнить проверочную команду:
```powershell
Get-ADObject -Identity "CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru" -Properties msDFSR-Enabled | Select-Object msDFSR-Enabled
```
**Риск:** Низкий. Это штатная, обратимая процедура Microsoft. Снапшот ВМ `before-d2-sysvol-restor...` уже создан.
**Чек-лист:**

**Идемпотентность:** Идемпотентно (повторная установка в `$false` не вызовет ошибки).
**Откат:** Выполнить ту же команду, заменив `$false` на `$true`.
**Ожидаемое время:** < 1 мин.
**Уверенность:** Высокий — команда точно соответствует официальной документации Microsoft по неавторитетной синхронизации DFSR.
**Протокол (обновлённый, коротко):** Подтверждено, что на обоих DC (`AD` и `DC`) атрибут `msDFSR-Enabled = True`. Выполняется первый шаг D2: отключение репликации SYSVOL на сервере `AD` через установку атрибута в `$false`.
