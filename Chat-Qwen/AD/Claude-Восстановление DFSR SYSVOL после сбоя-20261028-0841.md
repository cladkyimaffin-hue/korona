# Шаг 1.18: перед выбором A/B/V нужно перепроверить диагноз

**Я не рекомендую выбирать ни A, ни Б. Вывод «конфигурация фундаментально повреждена» скорее всего ошибочный.** Уверенность: средняя-высокая. Ниже причины и безопасные проверки.

## Почему диагноз сомнителен

1. **Атрибуты искали не там.** В здоровом домене у объекта `CN=Domain System Volume,CN=DFSR-GlobalSettings` обычно нет `msDFSR-ReplicationGroupGuid`, `msDFSR-Flags` и `msDFSR-Enabled`. По моим данным, эти атрибуты живут в локальных объектах подписки каждого DC:
   `CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru`
   Именно их и надо проверять.
2. **`whenChanged` = 26.03.2025 ничего не доказывает.** Объекты топологии не меняются годами и обновляются только при промоуте, демоуте или изменении топологии. Это, скорее всего, дата добавления DC.
3. **События 2212/2218 типичны для сбоя питания.** Они указывают на локальную БД DFSR, а не на AD. Штатное лечение: auto-recovery или D2/D4, без правки AD.
4. **Эталон есть.** Партнёр DC (192.168.200.2) здоров с точки зрения AD, поэтому достаточно сравнить его объекты с объектами AD.

Если я ошибаюсь и атрибуты подписки на AD действительно отсутствуют, а у DC на месте, тогда A становится осмысленным. Но сначала нужны факты.

## Шаг 1.18: только чтение, ничего не меняем

На **AD** (PowerShell от администратора):

```powershell
# 1. Состояние миграции SYSVOL (должно быть Eliminated / 3)
dfsrmig /getglobalstate

# 2. Реальное состояние папки SYSVOL в DFSR на этом сервере
Get-CimInstance -Namespace root\microsoftdfs -ClassName DfsrReplicatedFolderInfo |
  Select ReplicationGroupName, ReplicatedFolderName, State

# 3. Режим автовосстановления
reg query HKLM\SYSTEM\CurrentControlSet\Services\DFSR\Parameters /v StopReplicationOnAutoRecovery

# 4. Последние события DFSR
Get-WinEvent -LogName "DFS Replication" -MaxEvents 30 |
  Select TimeCreated, Id, Message | Format-List

# 5. Локальная подписка SYSVOL (проверяем в правильном месте)
Get-ADObject -Identity "CN=SYSVOL Subscription,CN=Domain System Volume,CN=DFSR-LocalSettings,CN=AD,OU=Domain Controllers,DC=krnn,DC=ru" -Properties *
```

Тот же пункт 5 выполните для `CN=DC,...` и сравните два вывода (`msDFSR-Enabled`, `msDFSR-ReplicationGroupGuid`, `msDFSR-Flags`, `msDFSR-RootPath`).

**Пришлите вывод всех пяти пунктов.** Особенно важны состояние в п.2 (State: 1 Initialized, 2 Auto-recovery, 4 Normal и т.д.), п.3 и события 2213/2212 в п.4.

## Ответы на ваш чек-лист

- **Бэкап SYSVOL:** сделайте его сейчас, это безопасно:
  `robocopy C:\Windows\SYSVOL\domain D:\Backup\SYSVOL_domain /E /COPYALL /R:1 /W:1`
  Также сравните содержимое `\\DC\SYSVOL\krnn.ru` и `\\AD\SYSVOL\krnn.ru`: GPO у DC, скорее всего, целее.
- **Снапшоты в Proxmox:** откат снапшота контроллера домена даёт риск USN rollback. Если всё же понадобится откат, убедитесь, что у ВМ включён vmgenid. Для варианта В откатывать нужно только через авторитетное восстановление System State, а не снапшотом.
- **Пока ничего не меняем:** ни атрибутов AD, ни D2/D4, ни пересоздания топологии.

## Что вероятнее всего окажется

- Если DFSR на AD в состоянии auto-recovery или ждёт ручного возобновления (событие 2213), лечится одной командой возобновления.
- Если подписка на AD цела, а DC отдаёт нормальную копию SYSVOL, достаточно **неавторитетного D2** на AD, а не D4. Авторитетный D4 нужен только если эталонные данные есть лишь на AD.

## Шаг 1.23: вывести DC из состояния 4012 (изменение)

Это первое изменение за всё время. Меняется одно значение в конфигурации DFSR на DC, AD и DFSR на AD не трогаем. Тип DC здесь единственный источник данных, а AD пуст, поэтому устаревшие данные никуда не уйдут.

Все команды на **DC**:

```powershell
hostname

# 1. Текущее значение (ожидаем 60)
Get-CimInstance -Namespace root\microsoftdfs -ClassName DfsrMachineConfig | Select MaxOfflineTimeInDays

# 2. Поднять лимит выше 215 дней

# 3. Проверить, что значение записалось (ожидаем 365)
Get-CimInstance -Namespace root\microsoftdfs -ClassName DfsrMachineConfig | Select MaxOfflineTimeInDays

# 4. Перезапустить DFSR и подождать минуту
Restart-Service DFSR
Start-Sleep 60

# 5. Проверка результата
Get-CimInstance -Namespace root\microsoftdfs -ClassName DfsrReplicatedFolderInfo | Select ReplicatedFolderName, State

```

Если шаг 2 выдаст ошибку, запасной вариант на том же месте:

```powershell
$c = Get-WmiObject -Namespace root\microsoftdfs -Class DfsrMachineConfig
$c.MaxOfflineTimeInDays = 365
$c.Put()
```

Классическая команда `wmic` в Windows Server 2025 может отсутствовать, поэтому используем CIM и WMI.

if ($null -eq $m) { $o.repl_partners = -1; $o.repl_failed = -1; $o.repl_max_age_min = -1 }
