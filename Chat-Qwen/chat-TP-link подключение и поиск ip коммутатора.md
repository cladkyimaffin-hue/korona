Учитывая, что мы уже установили: линк физически работает на **1 Гбит/с** (из-за модулей 1000BASE-SX), а Ceph при репликации генерирует интенсивный burst-трафик, наиболее вероятная причина — **насыщение 1-гигабитного канала, переполнение буферов коммутатора и сброс пакетов (tail drop)**.

Ниже приведен пошаговый план диагностики этого участка. Выполняйте команды на обоих узлах (`pve01` и `pve02`).

---

### Шаг 1. Проверка физического уровня и счетчиков ошибок (без обнуления)
Убедимся, что нет физических ошибок (CRC, рассинхронизация), которые вызывают потери пакетов.

1. **Проверка текущих параметров линка:**
   ```bash
   ethtool nic4
   ethtool nic5
   ```
   *Что ищем:* `Speed: 1000Mb/s` (или `10000Mb/s`, если модули заменили), `Duplex: Full`, `Link detected: yes`. Если где-то `Half` или `Unknown` — это причина всех проблем.

2. **Детальная статистика адаптера (ищем ошибки):**
   ```bash
   ethtool -S nic4 | grep -iE 'error|drop|crc|miss|over|fifo'
   ethtool -S nic5 | grep -iE 'error|drop|crc|miss|over|fifo'
   ```
   *Что ищем:* Растущие счетчики `rx_crc_errors`, `rx_missed_errors`, `tx_dropped`. Их рост во время всплесков Ceph прямо указывает на проблемы на уровне L1/L2.

3. **Статистика ядра Linux:**
   ```bash
   ip -s link show bond0
   ```
   *Что ищем:* Значения `RX dropped` и `TX dropped`. Если они растут, пакеты отбрасываются либо сетевым стеком, либо драйвером из-за нехватки буферов.

---

### Шаг 2. Анализ TCP-соединений и задержек
Подтвердим, что задержки вызваны именно сетью, а не дисковой подсистемой.

1. **Проверка ретрансмиссий в реальном времени:**
   ```bash
   ss -ti | grep -A 5 -B 5 "10.10.10."
   ```
   *Что ищем:* Параметры `retrans` (должны быть 0 в стабильном состоянии), `rcv_rtt` и `rtt`. Если `rtt` скачет до 100-200 мс, проблема в сети.

2. **Тестирование ICMP-задержек с большой нагрузкой:**
   Запустите непрерывный пинг с размером пакета, близким к MTU, во время активной записи в Ceph:
   ```bash
   # На pve01:
   ping -i 0.1 -s 8000 10.10.10.2
   ```
   *Что ищем:* Если пинг также показывает всплески до 150-200 мс или потери (packet loss), это **железное доказательство** проблемы в сетевом пути (коммутатор или канал), а не в самом Ceph.

3. **Проверка MTU:**
   ```bash
   ip link show bond0
   ```
   *Что ищем:* Убедитесь, что MTU одинаков на обоих узлах (например, 1500 или 9000). **Несовпадение MTU** (например, 9000 на одном конце и 1500 на другом) приводит к фрагментации или молчаливому отбрасыванию пакетов, что вызывает именно такие задержки.

### Шаг 3. Мониторинг утилизации канала (поиск насыщения)
1 Гбит/с = теоретически ~115 МБ/с, на практике стабильно около 90-95 МБ/с. Ceph легко пробивает этот потолок.

1. Установите `iftop` или `nload` (если нет: `apt install iftop`):
   ```bash
   iftop -i bond0 -n
   ```
   *Что ищем:* Если шкала загрузки во время записи постоянно упирается в 1 Гбит/с (1000Mb), канал насыщен. При насыщении буферы коммутатора TP-Link TL-SX3008F переполняются, и он начинает отбрасывать пакеты, что вызывает TCP Retransmission и задержку ~200 мс.

### Шаг 4. Диагностика на стороне коммутатора (TP-Link TL-SX3008F)
Вам потребуется доступ к веб-интерфейсу или CLI коммутатора. Проверьте следующие разделы:

1. **Статистика портов (Port Statistics / RMON):**
   - Найдите порты, к которым подключены `pve01` и `pve02`.
   - Проверьте счетчики: `CRC Errors`, `Undersize`, `Oversize`, `Dropped Packets`. Рост этих счетчиков коррелирует со всплесками Ceph.
2. **DDM / DOM (Digital Diagnostic Monitoring) для SFP:**
   - В разделе мониторинга SFP посмотрите **Tx Power** (мощность передачи) и **Rx Power** (мощность приема) для обоих портов.
   - *Критично:* Если `Rx Power` находится на нижней границе или ниже порога (например, < -12 dBm для многомодовых модулей), это означает деградацию сигнала (грязный коннектор, плохой патч-корд или несовместимость модуля), что ведет к ошибкам на физическом уровне и ретрансмиссиям TCP.
3. **Управление потоком (Flow Control):**
   - Убедитесь, что на портах коммутатора включен **IEEE 802.3x Flow Control** (Pause Frames). Это позволит коммутатору временно приостанавливать передачу данных с сервера при переполнении буфера, вместо молчаливого сброса пакетов.

---

### Шаг 5. Проверка задержек непосредственно в Ceph
Чтобы окончательно отделить сетевую проблему от дисковой, выполните на любом узле:
```bash
ceph osd perf
```
*Что ищем:*
- `commit latency`: время записи в журнал/WAL (сеть + быстрый диск). Если оно высокое (десятки миллисекунд и выше) и скачет, проблема в сети или NVMe.
- `apply latency`: время применения данных в основной пул (SSD/HDD). 
Если `commit latency` значительно выше `apply latency`, это подтверждает, что узкое место — **сеть или WAL-диск**.

## Способ 1. Консольный кабель (самый надежный)

У TL-SX3008F на передней панели есть **консольный порт RJ45** (подписан как `Console`).

### Что нужно:
- Консольный кабель **RJ45 → DB9 (RS232)** + USB-to-Serial адаптер (или готовый **USB-to-RJ45 console cable**, как у Cisco).
- Программа **PuTTY** (Windows) или `screen`/`minicom` (Linux).

### Подключение:
1. Воткните кабель в консольный порт коммутатора и в ноутбук.
2. Определите COM-порт (в Диспетчере устройств Windows → Порты COM и LPT).
3. В PuTTY:
   - Connection type: **Serial**
   - Serial line: `COM3` (ваш номер)
   - Speed: **115200**
   - Data bits: **8**, Stop bits: **1**, Parity: **None**, Flow control: **None**
4. Нажмите Open, нажмите Enter — увидите приглашение `>`.

### Назначение IP через консоль:
```
enable
configure terminal
interface vlan 1
ip address 192.168.200.10 255.255.252.0
exit
ip default-gateway 192.168.200.1
exit
write
```

После этого коммутатор станет доступен по SSH/Web с ноутбука, если воткнуть его в ту же подсеть.

## Способ 2. Временное подключение к управляющей сети

Если консольного кабеля нет, но есть **SFP→RJ45 медиаконвертер** или **медный SFP+ модуль 10GBASE-T** (осторожно: X722 их не любит, см. `dont_repeat` в вашем репо):

1. Воткните медиаконвертер в **любой свободный SFP+ порт** коммутатора.
2. Патч-кордом соедините конвертер с ноутбуком или свободным портом управляющего коммутатора в сети `192.168.200.0/22`.
3. Если коммутатор получал IP по DHCP — найдите его в арендах DHCP-сервера по OUI TP-Link (`14:CC:20`, `24:4B:81`, `34:4D:F7`).
4. Если IP не получил — сбросьте коммутатор кнопкой Reset (см. Способ 3), после чего он запросит DHCP.

> ⚠️ **Важно:** не используйте медные 10GBASE-T SFP+ модули в портах Intel X722 на серверах — они несовместимы. Но для **одного порта коммутатора**, к которому вы подключаете ноутбук через медиаконвертер, это безопасно.

## Способ 3. Сброс к заводским настройкам

Если IP неизвестен, консоли нет, и DHCP не выдал адрес:

1. Найдите на передней панели кнопку **Reset** (отверстие, нужна скрепка).
2. При включенном коммутаторе зажмите на **10+ секунд**, пока индикаторы SYS не мигнут.
3. Коммутатор перезагрузится с заводскими настройками:
   - IP: **DHCP** (если есть DHCP-сервер в сети)
   - Логин/пароль: `admin` / `admin`
   - Web: `http://192.168.0.1` (fallback, если DHCP недоступен — но только при прямом подключении)

После сброса повторите Способ 2.

## Что делать после получения доступа

1. **Назначьте статический IP** в вашей management-сети:
   ```
   interface vlan 1
   ip address 192.168.200.10 255.255.252.0
   ip default-gateway 192.168.200.1
   ```
2. **Смените пароль** `admin` сразу.
3. **Включите SSH**, отключите Telnet и HTTP (оставьте HTTPS).
4. **Проверьте DDM/SFP** на портах, куда воткнуты `pve01` и `pve02`:
   ```
   show interfaces transceiver detail
   ```
   Смотрите `Rx Power` — если ниже -12 dBm, проблема в оптике.
5. **Посмотрите счетчики ошибок:**
   ```
   show interfaces counters errors
   ```
   Рост CRC/undersize/oversize = физическая проблема.
6. **Включите Flow Control** (802.3x) на портах серверов — это снизит потери при burst-нагрузке Ceph.

### Как найти реальный IP-адрес коммутатора?

#### Способ 1: Проверка ARP-таблицы (самый быстрый)


#### Способ 2: Сканирование Management-сети
Запустите сканирование вашей управляющей подсети с любой ноды Proxmox (или с ноутбука в той же сети):

```bash
# Установите nmap, если его нет
apt update && apt install nmap -y

# Сканируем всю подсеть управления (замените на ваш реальный диапазон, например, 192.168.200.0/22)
nmap -sn 192.168.200.0/22 | grep -B 2 -i "tp-link"
```

#### Способ 3: Если коммутатор действительно настроен на DHCP, но вы не знаете адрес

- `http://192.168.1.1`
