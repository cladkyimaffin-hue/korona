**Действие 2: Скрипт «Кнопка паники» (SQL Server)**
Сохрани этот запрос в SSMS. **Не запускай его сейчас.** Запусти его **только тогда**, когда пользователь прямо скажет: «Всё висит прямо сейчас!».

```sql
-- Замер в момент реальной жалобы
SELECT TOP 10 
    r.session_id,
    r.status,
    r.wait_type,
    r.wait_time / 1000.0 AS wait_sec,
    r.blocking_session_id,
    r.cpu_time / 1000.0 AS cpu_sec,
    r.total_elapsed_time / 1000.0 AS total_sec,
    DB_NAME(r.database_id) AS db_name,
    SUBSTRING(t.text, 1, 150) AS query_snippet
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t
WHERE r.session_id > 50 
  AND r.status = 'running' -- Нас интересуют только те, кто активно работает, а не спит
ORDER BY r.total_elapsed_time DESC;
```

**Как читать результат «Кнопки паники»:**
- Если `wait_type` пустой (NULL) или `SOS_SCHEDULER_YIELD`, а `cpu_sec` близок к `total_sec` → **это 100% проблема CPU/планов запросов** (подтверждает гипотезу про MAXDOP и временные таблицы). Диск тут ни при чем.
- Если `wait_type` = `WRITELOG` или `PAGEIOLATCH_*` → **это проблема диска/Ceph**.

**Идемпотентность:** Идемпотентно. Можно запускать сколько угодно раз в момент лага.

Шаг 7 — проверить гипотезу авторроста журнала (только чтение)

7.1. Модель восстановления и причина, по которой журнал не очищается:

sql
SELECT name, recovery_model_desc, log_reuse_wait_desc,
       CAST(log_reuse_wait_desc AS NVARCHAR(60)) AS wait_reason
FROM sys.databases WHERE name = 'MS_ERP';

Если recovery_model_desc = FULL и log_reuse_wait_desc = LOG_BACKUP — это подтверждает, что бэкапы журнала не делаются или делаются редко, журнал не может усечься и продолжает расти.

7.2. Настройки авторроста и текущий размер/лимит:

sql
USE MS_ERP;
SELECT name, size*8/1024 AS size_mb, growth,
       CASE WHEN is_percent_growth = 1 THEN 'percent' ELSE 'MB' END AS growth_type,
       max_size
FROM sys.database_files;

Если рост задан маленьким шагом (например, 10% или фиксированные 10-64 МБ) на файле в 94 ГБ — каждый шаг роста на десятки гигабайт данных отнимает заметное время именно на Ceph (зануление нового пространства журнала — это последовательная запись, но большого объёма).

7.3. Самое ценное — история реальных событий авторроста с точным временем и длительностью, из default trace SQL Server:

sql
DECLARE @path NVARCHAR(260);
SELECT @path = REVERSE(SUBSTRING(REVERSE([path]), CHARINDEX('\', REVERSE([path])), 260)) + N'log.trc'
FROM sys.traces WHERE is_default = 1;

SELECT DatabaseName, FileName, StartTime,
       Duration/1000.0 AS Duration_ms, EventClass
FROM ::fn_trace_gettable(@path, DEFAULT)
WHERE EventClass IN (92,93) -- 92=рост файла данных, 93=рост файла журнала
ORDER BY StartTime DESC;

Это самое важное из всего шага: если тут найдутся события EventClass=93 (рост .ldf) с Duration в секундах, и их время совпадёт с тем, когда пользователи жаловались — гипотеза подтверждается напрямую, по факту, а не по косвенным признакам. Default trace хранит историю за последние несколько файлов (обычно покрывает от нескольких часов до нескольких дней в зависимости от нагрузки), так что шанс поймать прошлые эпизоды есть уже сейчас, без ожидания следующей жалобы.

Значения **500–2000+** означают, что операционная система выстраивает тысячи запросов на ввод-вывод в линию, и они ждут своей очереди секунды или даже десятки секунд. Именно в эти моменты пользователи кричат «всё тормозит». 
При этом `CPU` в моменты пиков (например, 21:16:47) составляет всего 5%. Это **окончательно снимает гипотезу о том, что проблема в процессоре или MAXDOP**. Проблема на 100% в подсистеме ввода-вывода диска D: в конкретные моменты времени.

Учитывая предыдущие данные (журнал транзакций `MS_ERP_log.ldf` размером 94.6 ГБ, средняя задержка записи `.mdf` ~59 мс), эти пики с вероятностью 95% вызваны одним из двух событий:
1. **Авторост файла журнала транзакций (.ldf) или данных (.mdf).** При росте файла на Ceph SQL Server должен запросить и обнулить новый блок пространства, что при больших шагах роста (или фрагментации на уровне Ceph) вызывает огромный IO-stall.
2. **Массовый Checkpoint или Lazy Writer.** Если 6 процессов `rphost` активно «грязнят» буферный пул SQL (64 ГБ), SQL Server вынужден экстренно сбрасывать гигабайты грязных страниц на диск D: одновременно.

### Шаг 11.2 — Добавление диска для бэкапов на хранилище `ceph-bulk`

**Объяснение / действие:**
Согласно `AI-environment_facts-korona-proxmox.md`, в кластере `krnn` предусмотрено отдельное хранилище `ceph-bulk` (на базе SSD 7/7.68 ТБ), чьё прямое архитектурное назначение: *"Бэкапы, архивы, менее критичные ВМ. Не использовать для активных БД."*

Это идеальное и архитектурно верное решение: мы перенесём нагрузку записи бэкапов (3–9 ГБ каждые 30 минут) с быстрого NVMe-пула (`ceph-fast`), где живут файлы БД, на ёмкий SSD-пул (`ceph-bulk`). Это полностью устранит I/O-конфликт, который мы зафиксировали в логах (пики `QueueD` до 2000+).

**Действие 1.1: Добавление виртуального диска в ВМ 2001 (через Proxmox)**
Выполните на том узле Proxmox, где сейчас работает ВМ 2001 (проверьте через `qm status 2001` или в GUI Proxmox):
```bash
# Добавляем диск объемом 100 ГБ на хранилище ceph-bulk к ВМ 2001 как scsi1
qm set 2001 -scsi1 ceph-bulk:100
```
*Ожидаемый результат:* Команда завершится успешно, в конфигурации ВМ появится строка `scsi1: ceph-bulk:vm-2001-disk-...,size=100G`.

**Действие 1.2: Инициализация и форматирование диска в Windows (ВМ 2001)**
После добавления диска в Proxmox, он появится в Windows как новый неинициализированный диск (hot-add поддерживается, так как у ВМ 2001 контроллер VirtIO SCSI). Выполните в PowerShell от имени администратора на ВМ 2001:
```powershell
# 1. Находим новый диск (обычно он будет номером 1 или 2, проверьте по размеру ~100GB и стилю 'Raw')
Get-Disk | Where-Object PartitionStyle -eq 'Raw'

# 2. Инициализируем его (замените Number на реальный номер диска из предыдущей команды, например, 1)
Initialize-Disk -Number 1 -PartitionStyle GPT

# 3. Создаем раздел и назначаем букву E:
New-Partition -DiskNumber 1 -UseMaximumSize -DriveLetter E
Format-Volume -DriveLetter E -FileSystem NTFS -NewFileSystemLabel "SQL_BACKUP" -Confirm:$false
```
*Ожидаемый результат:* В системе появится диск `E:\` с меткой `SQL_BACKUP` и файловой системой NTFS.

**Действие 1.3: Изменение пути бэкапа в SQL Server**
После появления диска `E:\`, необходимо изменить путь в задании резервного копирования (Maintenance Plan, скрипт Ola Hallengren или задание агента SQL Server) с `D:\SQL\BACKUP\` на `E:\SQL_BACKUP\`. *(Этот шаг выполняется после подтверждения успешного создания диска).*

---

**Сверка с environment_facts:**
- Используется хранилище `ceph-bulk`, что полностью соответствует его назначению в `AI-environment_facts-korona-proxmox.md`.
- ВМ 2001 (`Srv1c`) уже использует `ceph-fast` для системного диска (`scsi0`), добавление `scsi1` на `ceph-bulk` безопасно и не требует остановки ВМ.

**Риск:** Низкий. Добавление диска к работающей ВМ с контроллером VirtIO SCSI является штатной безопасной операцией (hot-add).

**Идемпотентность:** Не идемпотентно (повторный запуск `qm set` с тем же именем диска `scsi1` выдаст ошибку, но не повредит систему). 

**Откат:** Если диск добавлен ошибочно, его можно отключить: `qm set 2001 -delete scsi1`, а затем удалить через GUI Proxmox (Remove) или `qm rescan`.

**Ожидаемое время:** 1–2 минуты.

### Шаг 12.1 — Определение источника резервного копирования

**Объяснение / действие:**
Это абсолютно нормальная ситуация. Чтобы безопасно перенести бэкапы на другой диск (и тем самым устранить пики очереди диска), нам нужно понять, *какой именно процесс* их запускает. Это может быть:
1. Задание агента SQL Server (SQL Server Agent Job).
2. План обслуживания (Maintenance Plan).
3. Стороннее ПО (например, Veeam Backup, который подключается к SQL через VDI, но в нашем случае путь `D:\SQL\BACKUP\` с расширениями `.trn` больше похож на нативный бэкап SQL).

Мы выполним несколько безопасных запросов только на чтение к системным таблицам `msdb`, чтобы найти виновника.

**Запрос 1: Поиск заданий агента SQL Server, содержащих команду BACKUP**
```sql
SELECT 
    j.name AS job_name,
    js.step_name,
    js.command
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.sysjobsteps js ON j.job_id = js.job_id
WHERE js.command LIKE '%BACKUP%' 
   OR js.command LIKE '%sqlmaint%'
ORDER BY j.name;
```
*Как читать:* Если в колонке `command` вы увидите что-то вроде `BACKUP LOG [MS_ERP] TO DISK = N'D:\SQL\BACKUP\...'`, значит, бэкапы делает встроенный агент SQL Server. Имя задания (`job_name`) подскажет, где его редактировать.

**Запрос 2: Проверка планов обслуживания (Maintenance Plans)**
```sql
SELECT 
    name AS plan_name, 
    description, 
    date_created
FROM msdb.dbo.sysmaintplan_plans;
```
*Как читать:* Если здесь есть записи (например, "План резервного копирования"), значит, бэкапы настроены через графический мастер планов обслуживания SSMS.

**Запрос 3: Кто именно инициировал последние бэкапы (пользователь и сервер)**
```sql
SELECT TOP 10 
    bs.database_name,
    bs.backup_start_date,
    bs.user_name,
    bs.server_name,
    bmf.physical_device_name,
    CASE bs.type 
        WHEN 'D' THEN 'Full' 
        WHEN 'I' THEN 'Differential' 
        WHEN 'L' THEN 'Log' 
    END AS backup_type
FROM msdb.dbo.backupset bs
JOIN msdb.dbo.backupmediafamily bmf ON bs.media_set_id = bmf.media_set_id
WHERE bs.database_name = 'MS_ERP'
ORDER BY bs.backup_start_date DESC;
```
*Как читать:* Колонка `user_name` покажет, под какой учетной записью запускался бэкап (часто это `NT AUTHORITY\SYSTEM`, `sa` или имя службы SQL Agent). Если `server_name` отличается от имени вашей ВМ 2001, значит, бэкап инициирован удаленно (например, скриптом с другой машины или сторонним ПО).
