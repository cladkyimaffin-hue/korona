Шаг 3.1 — Уточнение архитектуры для USB-принтеров на клиентских ПК

**Объяснение / действие**  
Это критически важное архитектурное уточнение. Роль «Сервер печати» (Print Server) на ВМ `PRINT.krnn.ru` может централизованно управлять очередями только тех принтеров, которые физически подключены к *ней самой* (по USB или сети), либо сетевых принтеров. 

Если принтер TSC TE200 подключен по USB к *клиентскому ПК в домене*, то сервер `PRINT` не может стать его диспетчером печати (Spooler) напрямую. В стандартной архитектуре Windows в такой схеме сам клиентский ПК с подключенным принтером фактически выполняет роль принт-сервера для этого устройства (он расшаривает принтер, и другие пользователи подключаются к нему).

Чтобы выстроить правильный процесс, нам нужно выбрать один из следующих вариантов:

1. **Оставить принтер на ПК, использовать PRINT только для драйверов (Частый сценарий для этикеточных принтеров)**. 
   Принтер физически остается на клиентском ПК. Этот ПК расшаривает принтер. ВМ `PRINT` настраивается *только* как хранилище драйвера TSC TE200, чтобы пользователи могли скачивать его автоматически при подключении (Point and Print), но сама очередь печати и задания обрабатываются на клиентском ПК.
2. **Подключить принтер напрямую к серверу PRINT (Полная централизация)**. 
   Физически перенести TSC TE200 к серверу. *Важный нюанс*: так как `PRINT` — это виртуальная машина (QEMU/KVM), для проброса USB-порта с физического хоста Proxmox в ВМ потребуется настроить USB passthrough. Это привяжет ВМ `PRINT` к конкретному физическому хосту (pve01 или pve02), на котором будет воткнут принтер.
3. **USB-over-IP (Не рекомендуется)**. 
   Использовать сторонний софт для проброса USB-порта по сети с клиентского ПК на ВМ `PRINT`. Обычно это работает нестабильно.
