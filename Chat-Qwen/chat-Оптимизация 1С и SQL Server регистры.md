### Шаг 1.2 — Изменение MAXDOP на 1

**Обоснование:** Текущее значение MAXDOP = 8 вызывает высокие ожидания `CXPACKET` (69249 сек зафиксировано в мониторинге). **Действие:** Выполнить T-SQL скрипт в SSMS для изменения MAXDOP.

1. Откройте **SSMS** на ВМ 2001.
2. Нажмите кнопку **New Query** (Новый запрос) в toolbar или `Ctrl+N`.
3. Убедитесь, что в выпадающем списке баз данных в toolbar выбрана **master** (или любая системная БД — не важно, но не пользовательская).
4. Скопируйте и вставьте следующий скрипт:

```sql
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;
EXEC sp_configure 'max degree of parallelism', 1;
RECONFIGURE;
```

5. Нажмите **Execute** (F5) или кнопку **!** в toolbar.
6. В окне результатов должно появиться сообщение: `Configuration option 'max degree of parallelism' changed from 8 to 1. Run the RECONFIGURE statement to install.`

- ВМ 2001, SQL Server 2019 Developer — учтено.
- Текущее значение MAXDOP = 8, целевое = 1 — корректно для 1С.

- `run_value` = 1

### Шаг 2.5 — Диагностика причин высокой I/O нагрузки от 1С:ERP

**Обоснование:**
Типичные причины высокой нагрузки на диск при работе 1С:ERP:
1. **Фрагментация индексов** — запросы читают больше данных, чем нужно.
2. **Устаревшая статистика** — SQL Server выбирает неоптимальные планы запросов.
3. **Настройки autogrow** — если файлы БД растут небольшими порциями, это создаёт фрагментацию на уровне файловой системы.
4. **Отсутствие критичных индексов** — некоторые запросы делают full table scan.

**Действие (выполните запрос в SSMS для проверки фрагментации индексов):**

```sql

GO

    OBJECT_NAME(s.object_id) AS table_name,

    s.index_id,

    s.fragment_count,
    s.avg_fragment_size_in_pages,
    s.page_count,
    i.type_desc AS index_type
```

-- Пороги: >30% фрагментации и page_count > 1000 → REBUILD ONLINE
--         5-30% фрагментации и page_count > 1000 → REORGANIZE
--         <5% или page_count < 1000 → пропуск

SET NOCOUNT ON;

SELECT 
    CASE 
        WHEN ips.avg_fragmentation_in_percent > 30 AND ips.page_count > 1000 
            THEN 'ALTER INDEX [' + i.name + '] ON [' + s.name + '].[' + t.name + '] REBUILD WITH (ONLINE = ON, SORT_IN_TEMPDB = ON);'
        WHEN ips.avg_fragmentation_in_percent BETWEEN 5 AND 30 AND ips.page_count > 1000 
            THEN 'ALTER INDEX [' + i.name + '] ON [' + s.name + '].[' + t.name + '] REORGANIZE;'
        ELSE NULL
    END AS command,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    s.name AS schema_name,
    t.name AS table_name,
    i.name AS index_name
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
INNER JOIN sys.tables t ON ips.object_id = t.object_id
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 5
  AND ips.page_count > 1000
  AND i.name IS NOT NULL
ORDER BY ips.page_count DESC;

### Связь с пиками QueueD

Это **вторая корневая причина** тормозов 1С, наряду с бэкапами на тот же диск. При фрагментации 99% SQL Server вместо последовательного чтения вынужден делать **случайные чтения** по всему диску. Для индекса размером 4 ГБ с фрагментацией 99% это означает ~500 000 случайных обращений к диску вместо ~500 последовательных. На NVMe (ceph-fast) это создаёт огромную очередь I/O — ровно то, что мы видим в логах (`QueueD` до 2000+).

Ресурс-монитор показывал запись 12 МБ/с в `MS_ERP.mdf` — это не только рабочая нагрузка, но и **autogrow** (файл почти заполнен, 6 МБ свободно), который при каждом расширении создаёт дополнительный пик.

### Шаг 3.1 — Подготовка скрипта обслуживания индексов

**Обоснование:** Microsoft рекомендует (источник: [docs.microsoft.com/sql/relational-databases/indexes/reorganize-and-rebuild-indexes](https://docs.microsoft.com/sql/relational-databases/indexes/reorganize-and-rebuild-indexes)):
- Фрагментация **> 30%** → `ALTER INDEX ... REBUILD`
- Фрагментация **5–30%** → `ALTER INDEX ... REORGANIZE`
- Фрагментация **< 5%** → не трогать

Для 1С:ERP с её типичной нагрузкой пороги те же. Учитывая, что у тебя подавляющее большинство индексов > 30%, нужен массовый `REBUILD`.

**Сверка с environment_facts:**
- SQL 2019 Developer → `ONLINE = ON` поддерживается (таблицы не блокируются для пользователей).
- Модель `SIMPLE` → лог не разрастётся после `REBUILD`.
- Диск D: 732 ГБ → достаточно для временных файлов `REBUILD` (~1.2× размер индекса).
- Файл `MS_ERP.mdf` почти заполнен (6 МБ свободно) → **до** обслуживания индексов нужно расширить файл вручную, иначе `REBUILD` крупных индексов упадёт с ошибкой "disk full".

- Текущий размер `MS_ERP.mdf` = 64 894 МБ, расширяем до 75 000 МБ (+10 ГБ). Это даст запас для `REBUILD` крупнейших индексов.
- Диск D: 732 ГБ → после расширения останется ~657 ГБ свободно, этого достаточно.

**Как проверить результат:**
- Второй запрос должен показать `size_mb ≈ 75000` и `free_mb > 10000` (с учётом того, что часть места уже использована данными).
