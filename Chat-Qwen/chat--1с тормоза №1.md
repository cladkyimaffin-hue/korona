### USER
Двойная запись: возможный подвох

Да, это один из двух главных кандидатов (вместе со скоростью ядра), уверенность средняя. Что происходит: у пулов size 2, то есть каждая запись идёт на два OSD на двух разных узлах и подтверждается только после обеих. Две копии пишутся параллельно, поэтому задержка получается не в два раза больше, а как у более медленной из двух плюс сеть. Раньше на локальном NVMe такого шага не было.

Проведение документа в 1С состоит из многих коротких транзакций, и каждая ждёт подтверждения записи журнала. Кэш writeback помогает обычным записям, но коммит SQL должен дождаться реального подтверждения. Поэтому лишняя миллисекунда на каждый коммит умножается на число коммитов. Это объясняет, почему жалобы именно на проведение.

Но числа у нас нет. Накопленные 6,1 мс на журнал выше, чем я ждал бы от одного Ceph на NVMe (обычно порядка 1–2 мс, это моя оценка, не замер). Значит, часть задержки может быть и в другом месте: например, в пути от ВМ до OSD по сети. Поэтому надо измерить сам Ceph отдельно от ВМ.

Накопительная статистика ожиданий указывает на три классические для 1С проблемы, которые **не связаны** с нехваткой ресурсов гипервизора или скоростью дисков:

1. **`CXPACKET` (110 319 сек) и `CXCONSUMER` (35 974 сек) + `SOS_SCHEDULER_YIELD` (3 421 сек):**  
   Это ожидания параллелизма. SQL Server пытается выполнить запросы 1С в несколько потоков (параллельно). Для OLTP-систем (каковой является 1С, особенно при проведении документов с множеством коротких транзакций) параллелизм часто **вреден**. Потоки тратят больше времени на ожидание друг друга (`CXPACKET`) и уступку процессорного времени (`SOS_SCHEDULER_YIELD`), чем на полезную работу. Это идеально объясняет, почему хост "простаивает" (потоки ждут, а не вычисляют), а операция тормозит.
2. **`ASYNC_NETWORK_IO` (4 963 сек, 50 млн задач):**  
   SQL Server уже обработал запрос и ждёт, пока клиент (процесс 1С) заберёт данные из сетевого буфера. Это прямой индикатор того, что "тормозит" не база данных, а сама обработка на стороне приложения 1С (или блокировки на уровне приложения), либо неэффективный план запроса, генерирующий огромный объём данных для передачи.
3. **`WRITELOG` (6 097 сек) и `PAGELATCH_EX` (771 043 сек):**  
   При проведении документов 1С генерирует множество мелких транзакций. Ожидание записи в журнал (`WRITELOG`) присутствует. Также высокое `PAGELATCH_EX` часто указывает на конкуренцию за страницы выделения в базе **TempDB** (классическая проблема 1С, если в TempDB только один файл данных).

**Запрос В: Мониторинг активных запросов в реальном времени**
```sql
SELECT 
    r.session_id,
    r.status,
    r.start_time,
    r.command,
    r.cpu_time,
    r.total_elapsed_time,
    r.reads,
    r.writes,
    r.logical_reads,
    r.wait_type,
    r.wait_time,
    r.last_wait_type,
    r.blocking_session_id,
    SUBSTRING(
        st.text, 
        (r.statement_start_offset / 2) + 1,
        ((CASE r.statement_end_offset 
            WHEN -1 THEN DATALENGTH(st.text) 
            ELSE r.statement_end_offset 
        END - r.statement_start_offset) / 2) + 1
    ) AS statement_text,
    st.text AS full_query_text,
    r.percent_complete
FROM sys.dm_exec_requests r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
WHERE r.session_id > 50  -- Исключаем системные сессии
  AND r.status IN ('running', 'suspended', 'runnable')  -- Только активные запросы
  AND r.session_id <> @@SPID  -- Исключаем сам запрос мониторинга
ORDER BY r.total_elapsed_time DESC;
```

**Запрос: Поиск исторических блокировок в логе**
```sql
USE [test];
GO

SELECT TOP 50
    a.capture_time,
    a.session_id AS blocked_session,
    a.blocking_session_id AS blocker_session,
    a.wait_type,
    a.wait_time_ms,
    a.database_name,
    LEFT(a.statement_text, 100) AS blocked_query_snippet,
    LEFT(b.statement_text, 100) AS blocker_query_snippet
FROM dbo.ActiveQueriesLog a
LEFT JOIN dbo.ActiveQueriesLog b 
    ON a.capture_time = b.capture_time 
    AND a.blocking_session_id = b.session_id
WHERE a.blocking_session_id <> 0
  AND a.database_name = 'MS_ERP'
ORDER BY a.wait_time_ms DESC;
GO
```
