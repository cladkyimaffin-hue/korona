### ASSISTANT
Да, **Zabbix — это идеальный инструмент**, чтобы окончательно и документально снять все подозрения с инфраструктуры (Proxmox, Ceph, сеть) и перевести фокус на уровень СУБД и приложения. 

Однако, прежде чем идти в Zabbix, нужно сделать **важное концептуальное замечание**:
Ожидания типа `LCK_M_S`, `LCK_M_U`, `LCK_M_X` и долгие `COMMIT TRANSACTION` **никогда не бывают вызваны медленным диском или "шумным соседом" на уровне гипервизора**. Это чисто логические/транзакционные блокировки на уровне SQL Server. Процессор и память могут простаивать, потому что сессии "ждут" друг друга, а не диск. 

Тем не менее, чтобы закрыть вопрос с инфраструктурой, вот что нужно проверить в Zabbix.

### 1. Что проверить в Zabbix для снятия подозрений с Proxmox/Ceph

Чтобы доказать, что гипервизор и хранилище не виноваты, посмотрите следующие метрики за период "тормозов" (08:00–16:00):

**На уровне хоста Proxmox (pve01):**
*   **CPU Steal Time (`cpu_steal`):** Должен быть строго 0%. Если он > 0%, значит, хост перегружен другими ВМ (тогда это "шумный сосед", но вы уже видели, что CPU idle высокий, так что скорее всего всё ок).
*   **Host Memory Usage:** Нет ли свопинга на самом хосте Proxmox (если хосту не хватает RAM, он может начинать свопить страницы ВМ, но при 160 GiB у ВМ и 50 GiB свободных это исключено).
*   **Network Latency/Drops:** Нет ли ошибок или потерь пакетов на интерфейсе, через который ВМ общается с Ceph (MONs/OSDs).

**На уровне Ceph (если Zabbix собирает метрики кластера):**
*   **OSD Apply/Commit Latency:** `rados bench` меряет "тепличный" одиночный ввод. В Zabbix нужно посмотреть график `osd_apply_latency` и `osd_commit_latency` в часы пиковой нагрузки. Если они не превышают 1-2 мс для пула `ceph-fast` — хранилище идеально.
*   **Ceph Recovery/Backfill:** Не шел ли в это время фоновый процесс восстановления (recovery) или ребалансировки (backfill) после каких-либо сбоев? Это может "подъедать" ресурсы OSD.
*   **PG State:** Все ли пулы в состоянии `active+clean`?

*Резюме по Zabbix:* Скорее всего, вы увидите "зеленую" картину. Это окончательно подтвердит, что проблема на 100% внутри ВМ 2001 (SQL Server / 1С).

### 2. Как поймать "блокировщика" (Вместо уменьшения интервала опроса)

Уменьшать интервал вашего скрипта до 1-2 секунд — плохая идея (нагрузка + "иголка в стоге сена"). Используйте штатные, легковесные механизмы SQL Server.

#### Вариант А: Extended Events (Самый правильный)
Настройте расширенное событие `blocked_process_report`. Оно срабатывает *только* когда возникает блокировка, и показывает и "жертву", и "блокировщика" с их SQL-запросами.

1. Сначала включите порог срабатывания (по умолчанию 0, нужно поставить, например, 5 секунд, чтобы не спамить):
   ```sql
   EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
   EXEC sp_configure 'blocked process threshold', 5; -- секунд
   RECONFIGURE;
   ```
2. Создайте Extended Event session (через SSMS GUI или скрипт), который ловит `blocked_process_report` и сохраняет в файл или кольцо (ring_buffer).
3. Когда блокировка случится, вы получите XML, в котором будет точный текст запроса блокировщика (например, `UPDATE Reg_Nakopl...`) и жертвы.

#### Вариант Б: sp_whoisactive (Быстрый и грязный)
Если тормоза происходят прямо сейчас, используйте знаменитую процедуру Адама Мачаника. Она показывает цепочки блокировок в реальном времени.
```sql
EXEC sp_whoisactive @get_locks = 1, @get_plans = 1;
```
*Смотрите на колонку `locks` и `blocking_session_id`.*

### 3. Анализ "Курящего пистолета" (COMMIT 157 секунд)

Факт того, что `COMMIT TRANSACTION` висел 157 секунд (сессия 60) — это **корень зла**. В 1С это классический симптом следующих проблем:

1.  **Монолитное проведение:** Документ проводится в одной гигантской транзакции, которая блокирует регистры/справочники. Пока она не завершится, другие документы ждут `LCK_M_X`.
2.  **Обмен данными / Фоновые задания:** Возможно, в 14:32 шел обмен данными с другим узлом или фоновая обработка, которая заблокировала таблицу (например, ` _Reference123` или регистр накопления).
3.  **Отсутствие индексов:** Если запрос внутри транзакции делает Table Scan (сканирование всей таблицы) при обновлении, он может держать блокировку очень долго.

**Что делать:**
Вам нужно найти, что именно выполняла сессия 60 в 14:32. 
Если у вас включен **Query Store** (рекомендую включить, если еще не), вы можете найти этот запрос:
```sql
SELECT qsqt.query_sql_text, qrs.avg_duration, qrs.last_duration
FROM sys.query_store_query_text qsqt
JOIN sys.query_store_query qsq ON qsqt.query_text_id = qsq.query_text_id
JOIN sys.query_store_plan qsp ON qsq.query_id = qsp.query_id
JOIN sys.query_store_runtime_stats qrs ON qsp.plan_id = qrs.plan_id
WHERE qrs.last_execution_time BETWEEN '2023-10-25 14:30:00' AND '2023-10-25 14:35:00'; -- подставьте вашу дату
```
*(Если Query Store не включен, смотрите планы в кэше через `sys.dm_exec_query_stats`, но 157-секундный запрос мог уже вымыться из кэша).*

### 4. Технологический журнал (ТЖ) 1С

ТЖ — это единственный способ связать SQL-запрос с бизнес-логикой 1С (какой именно документ проводится).

1. Настройте ТЖ на сервере 1С (или на клиенте, если тонкий/толстый клиент, но лучше на сервере, если это фоновые задания).
2. Включите события: `LOCK`, `EXCP`, `ADMIN`, `TDE` (если используется).
3. Для события `LOCK` обязательно укажите фильтр по времени (например, срабатывать только если ожидание > 3 секунд), иначе ТЖ захлебнется.
   ```xml
   <script><![CDATA[
   <!-- Настройка ТЖ -->
   </script>
   ```
   *Пример настройки в `cfg.xml` для отлова долгих блокировок:*
   ```xml
   <log location="C:\1CLogs" history="1">
       <event>
           <eq property="Name" value="LOCK"/>
           <ge property="Duration" value="3000"/> <!-- мс -->
       </event>
   </log>
   ```
4. В ТЖ вы увидите не просто `UPDATE _AccumRgT123`, а **Контекст** (Context). Там будет написано: `Проведение документа "Реализация товаров и услуг" / Обмен данными / ...`. Это сразу укажет на виновника.

### 5. Проблема с диском E:\ (БД "2026")

Задержка 51–193 мс на E:\ — это **катастрофа** для SQL Server. Даже если БД "2026" пока не используется активно, сам факт её наличия на таком медленном диске опасен:
*   Если SQL Server решит сделать `CHECKPOINT`, `AUTO_SHRINK`, или фоновое обновление статистики для БД "2026", это создаст очередь на уровне воркеров (workers) или пула потоков SQL Server.
*   Если в БД "2026" включены модели восстановления `FULL` и не делаются бэкапы логов, или если она участвует в каких-то фоновых задачах — это может косвенно влиять на `MS_ERP`.

**Рекомендация:** 
1. Выясните природу E:\ (через `diskpart` -> `list disk` -> `detail disk` или через утилиты Windows, либо посмотрев конфигурацию ВМ в Proxmox). Скорее всего, это Ceph pool `ceph-bulk` (HDD или медленные SATA SSD) или вообще локальный диск хоста.
2. **Временно отключите БД "2026"** (переведите в SINGLE_USER или сделайте DETACH), чтобы полностью исключить её влияние на `MS_ERP` во время тестов.
3. В идеале — перенести её на `D:\` или выделить ей отдельный пул с адекватной производительностью.

### ASSISTANT
Текущий подход со сбором данных через опрос DMV (`sys.dm_exec_requests` и т.д.) раз в N секунд имеет фундаментальную проблему: **это «фотографирование» состояния**. Если блокировка или дедлок возникли и разрешились между двумя опросами (например, за 3 секунды, а интервал 10 сек), вы их просто не увидите. 

Чтобы «усилить» мониторинг, нужно идти в двух направлениях: **архитектурном** (переход на события) и **аналитическом** (обогащение данных в текущем скрипте).

---

### Направление 1. Архитектурное: Переход на Extended Events (XEvents)
Это «золотой стандарт» для SQL Server. Вместо того чтобы спрашивать сервер «что у тебя болит?» каждые 10 секунд, мы настраиваем «видеорегистратор», который срабатывает *только* при возникновении проблемы. Это дает 100% покрытие без пропуска коротких блокировок и с минимальной нагрузкой на CPU.

**Что нужно настроить (один раз):**
1. **Перехват блокировок:** Событие `blocked_process_report`.
2. **Перехват дедлоков:** Событие `xml_deadlock_report`.

*Скрипт для создания сессии (пишет в файл на диске D:):*
```sql
-- 1. Включаем порог срабатывания для blocked_process_report (например, 5 секунд)
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'blocked process threshold', 5; RECONFIGURE;

-- 2. Создаем Extended Event сессию
CREATE EVENT SESSION [1C_Blocking_Deadlock] ON SERVER 
ADD EVENT sqlserver.blocked_process_report(
    ACTION(sqlserver.client_app_name, sqlserver.database_id, sqlserver.session_id, sqlserver.sql_text)
),
ADD EVENT sqlserver.xml_deadlock_report(
    ACTION(sqlserver.client_app_name, sqlserver.database_id, sqlserver.session_id, sqlserver.sql_text)
)
ADD TARGET package0.event_file(SET filename=N'D:\SQL\DATA\XEvents\1C_Blocking.xel', max_file_size=(50))
WITH (MAX_MEMORY=4096 KB, EVENT_RETENTION_MODE=ALLOW_SINGLE_EVENT_LOSS, MAX_DISPATCH_LATENCY=10 SECONDS);

-- 3. Запускаем
ALTER EVENT SESSION [1C_Blocking_Deadlock] ON SERVER STATE = START;
```
**Итог:** У вас на диске всегда будут лежать точные XML-файлы с «жертвами», «блокировщиками» и их SQL-запросами. Вам больше не нужно гадать, что происходило между опросами скрипта.

### Направление 2. Аналитическое: Усиление текущего SQL-скрипта
Если вы хотите оставить опрос DMV (например, для сбора общей статистики в `ActiveQueriesLog`), его нужно серьезно доработать. Текущий скрипт, скорее всего, просто выгружает плоский список сессий. 

Вот **5 критических улучшений**, которые нужно добавить в `SELECT` для вставки в `ActiveQueriesLog`:

#### 1. Построение «Дерева блокировок» (Поиск Head Blocker)
Вместо того чтобы видеть 50 сессий, которые ждут друг друга, нужно видеть **корень зла** (head blocker) — сессию, которая держит блокировку и является причиной всего остального.
*Добавляем рекурсивный CTE:*
```sql
WITH BlockingTree AS (
    -- Находим "корни" (те, кто блокирует других, но сами не заблокированы)
    SELECT r.session_id, r.blocking_session_id, 0 AS Level, r.session_id AS HeadBlockerID
    FROM sys.dm_exec_requests r
    WHERE r.blocking_session_id = 0 
      AND r.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id > 0)
    
    UNION ALL
    
    -- Рекурсивно спускаемся к жертвам
    SELECT r.session_id, r.blocking_session_id, bt.Level + 1, bt.HeadBlockerID
    FROM sys.dm_exec_requests r
    INNER JOIN BlockingTree bt ON r.blocking_session_id = bt.session_id
)
```

#### 2. Возраст транзакции и использование лога
Вы видели `COMMIT` на 157 секунд. Чтобы ловить такие аномалии, нужно знать, сколько времени живет транзакция и сколько места в логе она съела.
*Добавляем JOIN к `sys.dm_tran_session_transactions` и `sys.dm_tran_active_transactions`:*
```sql
SELECT 
    tat.transaction_begin_time,
    DATEDIFF(SECOND, tat.transaction_begin_time, GETDATE()) AS tran_age_sec,
    tat.database_transaction_log_bytes_reserved
FROM sys.dm_tran_active_transactions tat
JOIN sys.dm_tran_session_transactions tst ON tat.transaction_id = tst.transaction_id
```

#### 3. Детализация ресурсов ожидания
`wait_type = LCK_M_X` говорит, что сессия ждет эксклюзивную блокировку. Но **чего именно**? Таблицы? Страницы? Конкретной строки?
*Добавляем `sys.dm_os_waiting_tasks`:*
```sql
SELECT wt.resource_description 
FROM sys.dm_os_waiting_tasks wt 
WHERE wt.session_id = r.session_id
```
*(В `resource_description` для 1С часто лежат ID ключей или страниц, что очень помогает разработчикам).*

#### 4. Сбор планов запросов (Query Plans)
Для запросов вида `INSERT INTO #tt... WITH(TABLOCK)` наличие плана — это вопрос жизни и смерти. Без плана вы не поймете, почему 1С берет блокировку на всю таблицу вместо одной строки.
*Добавляем `sys.dm_exec_query_plan`:*
```sql
CROSS APPLY sys.dm_exec_query_plan(r.plan_handle) qp
```

#### 5. Парсинг контекста 1С из `program_name`
В SQL Server `program_name` для 1С выглядит как `Srvr="srv1c";Db="2026";App="1C:Enterprise 8.3";...`.
Чтобы в таблице мониторинга сразу было видно, из какой базы и какого приложения пришел запрос, добавьте парсинг:
```sql
-- Извлекаем имя базы
CASE 
    WHEN r.program_name LIKE '%Db=%' 
    THEN SUBSTRING(r.program_name, CHARINDEX('Db="', r.program_name) + 4, 
         CHARINDEX('"', r.program_name, CHARINDEX('Db="', r.program_name) + 4) - CHARINDEX('Db="', r.program_name) - 4)
    ELSE r.program_name 
END AS db_name_1c
```

### Готовый «Усиленный» запрос для ActiveQueriesLog
Объединяем всё в один мощный `INSERT ... SELECT`, который можно запускать по расписанию (например, раз в 5-10 секунд):

```sql
INSERT INTO test.dbo.ActiveQueriesLog (
    collection_time, session_id, blocking_session_id, head_blocker_id, wait_type, 
    wait_time_ms, resource_desc, status, command, db_name_1c, tran_age_sec, 
    log_bytes_reserved, sql_text, query_plan
)
SELECT 
    GETDATE(),
    r.session_id,
    r.blocking_session_id,
    bt.HeadBlockerID,
    r.wait_type,
    r.wait_time,
    wt.resource_description,
    r.status,
    r.command,
    -- Парсинг базы 1С
    CASE WHEN r.program_name LIKE '%Db="%' 
         THEN SUBSTRING(r.program_name, CHARINDEX('Db="', r.program_name) + 4, 
              CHARINDEX('"', r.program_name, CHARINDEX('Db="', r.program_name) + 4) - CHARINDEX('Db="', r.program_name) - 4)
         ELSE DB_NAME(r.database_id) END,
    DATEDIFF(SECOND, tat.transaction_begin_time, GETDATE()),
    tat.database_transaction_log_bytes_reserved,
    st.text,
    qp.query_plan
FROM sys.dm_exec_requests r
-- Дерево блокировок
LEFT JOIN (
    SELECT r2.session_id, r2.session_id AS HeadBlockerID
    FROM sys.dm_exec_requests r2
    WHERE r2.blocking_session_id = 0 AND r2.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id > 0)
    UNION ALL
    SELECT r3.session_id, bt.HeadBlockerID
    FROM sys.dm_exec_requests r3
    INNER JOIN (
        SELECT r2.session_id, r2.session_id AS HeadBlockerID
        FROM sys.dm_exec_requests r2
        WHERE r2.blocking_session_id = 0 AND r2.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id > 0)
    ) bt ON r3.blocking_session_id = bt.session_id
    -- Примечание: для полноценной рекурсии лучше использовать CTE, но для INSERT в таблицу можно использовать упрощенный вариант или функцию.
) bt ON r.session_id = bt.session_id
-- Ресурсы ожидания
LEFT JOIN sys.dm_os_waiting_tasks wt ON r.session_id = wt.session_id AND wt.waiting_task_address IS NOT NULL
-- Транзакции
LEFT JOIN sys.dm_tran_session_transactions tst ON r.session_id = tst.session_id
LEFT JOIN sys.dm_tran_active_transactions tat ON tst.transaction_id = tat.transaction_id
-- Тексты и планы
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
OUTER APPLY sys.dm_exec_query_plan(r.plan_handle) qp
WHERE r.session_id <> @@SPID 
  AND r.session_id > 50 -- Исключаем системные
  AND r.command NOT IN ('BRKR TASK', 'WAITFOR') -- Исключаем фоновый шум
  AND (r.wait_time > 100 OR r.blocking_session_id > 0 OR DATEDIFF(SECOND, tat.transaction_begin_time, GETDATE()) > 5); -- Фильтр шума: ждем >100мс ИЛИ блокируем ИЛИ транзакция висит >5сек
```

3. **Передайте разработчику 1С:**

- В базе `2026` зафиксированы массовые блокировки (`LCK_M_S`, `LCK_M_U`, `LCK_M_X`) до 18 секунд и **45 взаимных блокировок (deadlock)** за один день (02.10.2026), сгруппированных в два всплеска (11:11–11:24 и 15:15–15:16).
- Разовые ручные замеры через DMV (`sys.dm_exec_requests`, `sys.dm_os_wait_stats`) и Extended Events дали точечную картину, но нужен **постоянный мониторинг** для выявления паттернов и корреляции с действиями пользователей/фоновыми заданиями.

## Что нужно настроить (приоритеты)

### 1. Базовый мониторинг SQL Server (через плагин `mssql`)
Использовать встроенный плагин Zabbix Agent 2 `mssql` (не требует дополнительных скриптов, работает через TDS-протокол):
- **Performance counters:**
  - `SQLServer:Wait Statistics` — по типам `LCK_M_S`, `LCK_M_U`, `LCK_M_X`, `PAGEIOLATCH_*`, `WRITELOG`.
  - `SQLServer:Locks` — количество блокировок по базе, время ожидания.
  - `SQLServer:Transactions` — `Transactions/sec`, `Longest Transaction Running Time`.
  - `SQLServer:Databases` — `Log File(s) Size`, `Log File(s) Used Size`, `Data File(s) Size`.
  - `SQLServer:General Statistics` — `User Connections`, `Processes blocked`.
  - `SQLServer:Buffer Manager` — `Page life expectancy`, `Buffer cache hit ratio`.
- **Deadlocks:** счётчик `SQLServer:Locks(_Total)\Number of Deadlocks/sec` — ключевая метрика для нашей проблемы.

### 2. Мониторинг ОС Windows (стандартный плагин `system`)
- CPU: `% Processor Time`, `% Privileged Time`, `Processor Queue Length`.
- RAM: `Available MBytes`, `Pages/sec`, `Pool Nonpaged Bytes`.
- Disk: `Avg. Disk sec/Read`, `Avg. Disk sec/Write` по каждому диску (D:, E:).
- Network: `Bytes Total/sec`, `Current TCP Connections`.

### 3. Кастомные UserParameters (если плагин `mssql` не покрывает)
Для специфичных метрик 1С/SQL:
- Количество активных сессий по базам (`MS_ERP` vs `2026`).
- Возраст самой долгой транзакции (`DATEDIFF(SECOND, transaction_begin_time, GETDATE())`).
- Размер `tempdb` и количество файлов.
- Запросы с `TABLOCK` (по нашим наблюдениям — источник дедлоков).

### 4. Триггеры (примерный набор)
- `Number of Deadlocks/sec` растёт > 0 за 5 минут → **HIGH**.
- `Processes blocked` > 10 в течение 3 минут → **AVERAGE**.
- `Longest Transaction Running Time` > 60 сек → **WARNING**.
- `Page life expectancy` < 300 сек → **WARNING** (признак нехватки RAM под буферный кэш).
- `Avg. Disk sec/Write` на E: > 20 мс → **AVERAGE** (наша аномалия с диском 2026).
- `Available MBytes` < 10 GiB → **HIGH**.

## Технические ограничения и вопросы для обсуждения
1. **Учётная запись для подключения:** Zabbix Agent 2 должен подключаться к SQL Server. Нужен логин SQL с правами `VIEW SERVER STATE` + `VIEW DATABASE STATE`. Создавать отдельного пользователя `zabbix_monitor` или использовать Windows-аутентификацию?

4. **Интервалы опроса:** Для `Processes blocked` и `Deadlocks` — 10-30 сек, для `Buffer cache hit ratio` — 1 мин, для `Disk sec/Write` — 30 сек. Согласовать.
5. **Хранение данных:** Сколько дней хранить тренды? Для расследования инцидентов типа «дедлоки 02.10.2026» нужен минимум 30 дней.
6. **Нагрузка на SQL Server:** Плагин `mssql` выполняет DMV-запросы. Не добавит ли он сам «тормозов» в пиковые часы? Нужен ли режим «только при проблемах» или постоянный сбор?
