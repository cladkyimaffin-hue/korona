# sysagentd — демон на Go: как он на самом деле работает

Мини-версия предыдущего Python-агента, но одним бинарником (3 МБ, без зависимостей).
Собрано и проверено на Debian 13 / systemd 257 / Go 1.23.

## Ответ на вопрос «запустил — висит в памяти — начинаю работать»

Да, но с важным уточнением: **демон сам по себе не даёт вам никакого набора команд.**
Интерфейс вы проектируете сами. «Свой набор команд» появляется только потому, что
в том же бинарнике есть **клиентская часть**, которая разговаривает с демоном.
Тут их две в одном файле:

```
$ sysagentd daemon            # роль 1: слушает unix-сокет, висит в памяти
$ sysagentd logs --unit nginx # роль 2: клиент, отправляет запрос и печатает ответ
$ sysagentd logs --local      # роль 2б: тот же запрос без демона (для cron)
```

Важно: `sysagentd logs` — это **не** «команда внутри демона» и не отдельная
утилита. Это тот же бинарник, запущенный второй раз; он открывает unix-сокет
`/run/sysagentd.sock`, отправляет JSON, получает JSON, печатает, выходит.
Демон при этом продолжает висеть и помнит состояние (uptime, кэш, счётчики).

## Четыре способа «работать с демоном» — выберите один

| Способ | Как выглядит | Когда использовать |
|---|---|---|
| **Подкоманды + unix-сокет** (реализовано здесь) | `sysagentd logs --unit nginx` | локально на хосте, самый быстрый и безопасный: файл сокета `0660` — только свои |
| **HTTP/JSON API** (`127.0.0.1:8080`) | `curl localhost:8080/logs?unit=nginx` | нужен web-UI, другой язык, удалённый доступ через SSH-туннель |
| **MCP over stdio** | клиент запускает `sysagentd mcp` как дочерний процесс | хотите, чтобы Claude Desktop / IDE видел инструменты как свои tools |
| **systemd-таймер + CLI** | `sysagentd failed --local` в `.timer` | простая периодика без демона вообще: демон не нужен |

Разница между первым и вторым — принципиальная для безопасности: **unix-сокет
не открывает TCP-порт**, его нельзя достичь по сети. HTTP на `0.0.0.0` без
аутентификации — это удалённый root-доступ, которого вы не заметите.

## Что происходит при запуске

```
sysagentd daemon --mode readonly
```

1. `net.Listen("unix", "/run/sysagentd.sock")` — создаётся файл сокета.
2. `Accept()` в цикле; каждый запрос обслуживается в **горутине** (стоит ~2 КБ).
3. Простой демон **ничего не опрашивает** — он спит в `Accept()` и потребляет
   0% CPU. Работа появляется только когда пришёл запрос.
4. systemd держит его живым (`Restart=always`) и по желанию изолирует
   (см. `deploy/sysagentd.service`: `ProtectSystem=strict`, `CapabilityBoundingSet=`,
   `SystemCallFilter=@system-service`, `RestrictAddressFamilies=AF_UNIX`).

## Реальный расход памяти (замер, не обещание)

```
$ ps -o pid,rss,vsz,comm,etime -p $(pgrep sysagentd)
    PID   RSS    VSZ COMMAND   ELAPSED
   3206  4772 1671800 sysagentd   00:06
```

* **RSS 4.7 МБ** — это и есть память, которую демон реально занимает.
* **VSZ 1.6 ГБ** — виртуальное адресное пространство, которое Go *резервирует*
  заранее (арены для сборщика мусора). Оно не занято физически и не в swap;
  не пугайтесь этой цифры в `top` — смотрите на RSS.
* Под нагрузкой (много параллельных запросов) RSS растёт до десятков МБ и потом
  возвращается: GC отдаёт память ОС не сразу.

Если нужен ещё меньший footprint — `GOGC=50` в юните, либо отдельный бинарник для
лёгкого дежурного режима. Ниже ~4 МБ на Go-демон опуститься сложно, и это нормально.

## Проверка, которую можно повторить

```bash
export PATH=$PATH:/usr/local/go/bin
cd sysagent-go
go build -ldflags "-s -w" -o sysagentd .     # 3.0 МБ, статический

./sysagentd daemon --socket /tmp/sa.sock &    # или через systemd
export SYSAGENTD_SOCKET=/tmp/sa.sock
./sysagentd ping
./sysagentd failed
./sysagentd logs --since -24h
./sysagentd status --unit ssh.service
./sysagentd failed --local                    # без демона
go test ./...                                 # политика + склейка логов
cat /var/log/sysagentd/audit.jsonl | tail -3  # аудит каждого запроса
```

Отключить демон: `kill <pid>` (или `systemctl stop sysagentd`) — сокет удаляется
по сигналу SIGTERM.

## Где Go объективно лучше Python-версии

* один бинарник `scp`-ом на сервер, никаких venv и pip-зависимостей;
* ~5 МБ RSS против 40–70 МБ у Python-интерпретатора;
* нет GIL: 50 одновременных сборов журнала — не проблема;
* `systemd`-песочница работает лучше, потому что нет нужды в `/tmp`, pip, интерпретаторе;
* статическая типизация ловит половину ошибок на этапе сборки.

## Где Python удобнее

* LLM-часть (function calling, провайдеры) — зрелые SDK;
* быстрые эксперименты с разбором текста;
* если агент в основном «думает», а не «висит в фоне».

**Рабочая комбинация для вашего случая:** Go-демон как надёжный исполнитель
(журнал, службы, политика, unix-сокет) + Python/LLM-клиент, который к нему
подключается. Демон ничего не знает про модели — это его главное достоинство:
LLM можно менять, отключать или вообще не иметь.

## Дальше добавить (по приоритету)

1. `sysagentd mcp` — режим stdio, чтобы инструменты увидел любой MCP-клиент.
2. Список разрешённых команд в конфиге `/etc/sysagentd/policy.toml` вместо `map` в коде.
3. `sysagentd restart --unit X` за флагом `--mode=ask`: подтверждение в терминале клиента.
4. SQLite-история журнала (cgo-free: `modernc.org/sqlite`) — поиск «когда началось».
5. mTLS-транспорт вместо unix-сокета, если нужно управлять флотом с ноутбука.
