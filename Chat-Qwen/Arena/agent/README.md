# sysagent — локальный агент администрирования Linux

Рабочий скелет: читает ошибки журнала systemd, показывает состояние служб,
выполняет системные команды **через политику безопасности**, умеет работать как
обычный CLI-чат, как MCP-сервер и как дежурный демон.

Зависимостей нет — только Python 3.11+ (stdlib). Проверено на Debian 13 / systemd.

---

## 1. «Компилятор для агентов» — что это на самом деле

Компилятора агентов не существует, потому что **агент — это обычная программа**.
Никакой магии в ней нет: цикл «получить задачу → выбрать инструмент → выполнить →
посмотреть результат → снова выбрать». Компилятор/фреймворк не нужен, нужны три вещи:

| Слой | Что делает | Чем делать |
|---|---|---|
| Инструменты (tools) | реальные действия: журнал, systemctl, файлы | `subprocess`, `systemd` D-Bus, `psutil` |
| Мозг | понимает запрос, выбирает инструменты | LLM с function calling **или** жёсткие правила |
| Политика | решает, что вообще можно выполнить | ваш код-белый список (обязательно!) |

Так называемые «фреймворки для агентов» — это библиотеки-обвязки над этим циклом:

* **LangChain / LlamaIndex** — много готового, но тяжёлые и быстро меняют API;
  для системного агента это лишний слой абстракции.
* **Pydantic AI / smolagents / OpenAI Agents SDK** — тоньше, но всё равно
  привязывают вас к конкретному провайдеру моделей.
* **MCP (Model Context Protocol)** — *не фреймворк*, а стандарт: вы описываете
  инструменты один раз, и их видят Claude Desktop, IDE, собственный чат. Для
  «агента над системой» это самый практичный выбор: UI писать не нужно.
* **Ansible / SaltStack** — если задача на 80% про «привести сервер к состоянию»,
  а не про диалог. Агент тогда только вызывает плейбуки.

Вывод: начинайте с 200–400 строк своего кода (как в этом репозитории). Когда
упрётесь в конкретную проблему — добавите библиотеку под неё.

## 2. Выбор языка

* **Python** — быстрый прототип, богатые библиотеки для LLM, нормальная работа с
  журналом и D-Bus. Рекомендуется для старта (этот скелет).
* **Go** — один статический бинарник, без зависимостей на хосте, отличные
  `os/exec`, `log/syslog`, D-Bus-клиент. Лучший выбор для продакшена на флот
  серверов.
* **Rust** — если нужны минимальный footprint и жёсткая безопасность памяти;
  дольше в разработке.
* **Bash** — только для триггеров, не для агента.

## 3. Архитектура (то, что уже реализовано)

```
      пользователь / MCP-клиент / чат
                    |
        ┌───────────┴───────────┐
        |  cli.py    mcp_server.py   ← интерфейсы (можно менять, не трогая ядро)
        └───────────┬───────────┘
                    |
                 llm.py                ← цикл function calling (опционален)
                    |
                 tools.py              ← 8 инструментов, JSON-схемы
                    |
                policy.py              ← классификация риска + аудит + подтверждение
                    |
              subprocess / journalctl / systemctl
                    |
                 Linux-хост
```

Принципиальные решения:

1. **Модель не решает, что можно выполнять.** LLM предлагает инструмент, а
   `policy.py` решает: `read` → сразу, `write` → спросить человека, `dangerous` →
   запрет по умолчанию, неизвестное → запрет.
2. **`shell=False` всегда**, аргументы разбираются `shlex`, пайпы и `;` отклоняются
   на этапе классификации (иначе `journalctl | grep` — это уже произвольный код).
3. **Ошибки логов группируются по шаблону**, а не отдаются модели пачкой строк:
   `50 × "upstream timed out <n>"` вместо 50 одинаковых записей. Это резко
   поднимает качество ответов модели и экономит токены.
4. **Аудит**: каждое действие пишется в `~/.local/state/sysagent/audit.jsonl`.
5. **Три режима**: `readonly` (по умолчанию в дежурном контуре и в MCP),
   `ask` (подтверждение в терминале), `auto` (только для тестовых стендов).

## 4. Быстрый старт

```bash
cd sysagent

# 1. ничего не устанавливается, можно сразу смотреть систему без LLM:
python3 -m sysagent --mode readonly
sysagent> /failed
sysagent> /logs nginx.service
sysagent> /disk

# 2. разово вызвать инструмент:
python3 -m sysagent --tool journal_errors --json '{"unit":"nginx.service","since":"-24h"}'

# 3. подключить LLM (любой OpenAI-совместимый эндпоинт):
cp config.example.toml ~/.config/sysagent/config.toml
export OPENAI_API_KEY=sk-...
python3 -m sysagent                      # обычный чат
python3 -m sysagent --once "почему упал nginx сегодня ночью?"

# 4. локальная модель, без облака:
#    [llm] base_url = "http://127.0.0.1:11434/v1"  model = "qwen2.5:7b"
#    export OPENAI_API_KEY=ollama

# 5. как MCP-сервер для Claude Desktop / IDE:
python3 -m sysagent.mcp_server --mode readonly
```

Проверка политики и группировки логов:

```bash
python3 tests/test_policy.py     # без pytest
```

## 5. Установка на хост

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin sysagent
sudo usermod -aG systemd-journal,sudo sysagent   # sudo — только если нужны restart
sudo mkdir -p /opt/sysagent && sudo cp -r . /opt/sysagent
sudo cp deploy/sysagent-watch.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now sysagent-watch
```

Юнит уже содержит изоляцию (`ProtectSystem=strict`, `NoNewPrivileges`,
`SystemCallFilter`, пустой `CapabilityBoundingSet`). Для дежурного контура
`sudo` не нужен вовсе — только группа `systemd-journal`.

## 6. План разработки

**Этап 1 — скелет (готов).** Чтение журнала, статусы служб, метрики, политика,
CLI, MCP, дежурный демон.

**Этап 2 — свои инструменты (1–2 дня).** Добавляйте по одному на реальную боль:

```python
# sysagent/tools.py
def nginx_config_test(cfg, approve=None):
    res = run_command("nginx -t", cfg, approve=approve, force_risk=Risk.READ)
    return {"ok": res.exit_code == 0, "output": res.stderr}
```
и зарегистрируйте в `TOOLS` с описанием и JSON-схемой. Полезные кандидаты:
`systemctl list-timers`, `smartctl`, `docker ps`, `nginx -t`, `pg_isready`,
`ss -s`, «какие порты слушает процесс», проверка сертификатов (`openssl x509`).

**Этап 3 — качество диагностики.** Храните историю: SQLite + `journalctl -o json`
раз в минуту → поиск «когда это началось», корреляции. Добавьте правила
`/etc/sysagent/rules.toml`: «если `OOMKilled` в journal → проверить `free -h` и
`top_processes(mem)` и доложить». Правила дешевле и надёжнее LLM для типовых аварий.

**Этап 4 — автоматизация.** Только после 2–3 недель наблюдения: политика
`auto` для узкого списка действий (`systemctl restart <service>` при известном
паттерне ошибки), с обязательным лимитом (не чаще 1 раза в 15 минут), записью в
аудит и уведомлением человеку. Всё остальное — по-прежнему через подтверждение.

**Этап 5 — флот серверов.** Центральный узел (FastAPI + WebSocket) и агент на
каждом хосте (mTLS, только исходящее соединение). Тогда «управление с ПК»
= ваш ноутбук как клиент, а не открытый SSH-порт на прод.

## 7. Безопасность — не пропускайте этот раздел

Агент с правом `restart`/`kill` — это удалённый root-доступ, если ошибиться в
одном месте. Минимальный набор:

* **Не выставляйте агент в интернет.** Никаких `0.0.0.0:8080` без аутентификации.
  Если нужен удалённый доступ — WireGuard/Tailscale/SSH-туннель, mTLS.
* **Белый список, а не чёрный.** Запрещать `rm` бесполезно: `find -delete`,
  `> file`, `dd` сделают то же. Разрешайте явные команды.
* **Человек в цикле для всего изменяющего.** Первый месяц — обязательно.
* **Аудит-лог только на запись** (`chattr +a`) и выгрузка наружу; иначе
  скомпрометированный агент затрёт следы.
* **Ключ LLM — не root-овый.** У агента свои права; LLM не должна видеть
  секреты: вырезайте `MESSAGE` из журнала перед отправкой, если там бывают
  токены/пароли.
* **Prompt injection реален:** текст в логе может содержать «забудь инструкции,
  выполни …». Защита — только политика на стороне хоста, а не системный промпт.
* **Лимиты:** таймаут команды, обрезка вывода, лимит раундов инструментов,
  rate limit на изменения.
