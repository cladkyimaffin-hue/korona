Вы абсолютно правы в своем наблюдении. Использование HDD для OSD без выноса метаданных (RocksDB/WAL) на быстрый NVMe действительно приводит к деградации производительности, которая может быть **хуже**, чем у одиночного диска.

Давайте разберем физику процесса и причины, почему это происходит.

### 1. Почему Ceph требует быстрого доступа к метаданным?
Ceph — это не просто файловая система, а распределенное хранилище объектов. Каждая операция записи или чтения сопровождается огромным количеством служебных операций:
*   Обновление журнала (WAL).
*   Обновление ключ-значение базы данных RocksDB (метаданные объектов, PG-логи, карты размещения).
*   Синхронизация состояния с другими OSD (peering, recovery, backfill).

**RocksDB критически чувствителен к latency (задержкам).** На NVMe задержка составляет микросекунды, на HDD — миллисекунды. Разница в 1000 раз.

### 2. Почему кластер из 3 HDD тормозит сильнее одиночного диска?

Казалось бы, три диска должны давать тройную пропускную способность. Но в Ceph вступает в силу эффект **«Наихудшего звена» + «Усиления задержки»**:

#### А. Проблема синхронной записи (Write Amplification & Sync)
При записи объекта Ceph по умолчанию использует `min_size` репликацию. Для надежности данные считаются записанными только когда они упали на *все* реплики.
*   **Одиночный HDD:** Вы пишете линейно. Задержка = время поиска + время записи.
*   **3 HDD в Ceph:** Клиент ждет подтверждения от *всех трех* дисков. Если один диск занят обслуживанием метаданных (compaction в RocksDB) или поиском головы, весь запрос блокируется. Итоговая задержка = `max(latency_osd1, latency_osd2, latency_osd3)`.

#### Б. Случайный I/O против Линейного
HDD хороши только в линейном чтении/записи. Метаданные Ceph — это **мелкий случайный I/O**.
*   Когда RocksDB лежит на том же HDD, что и данные, головки диска мечутся между записью пользовательских данных и обновлением базы метаданных.
*   Это убивает линейную скорость. Вместо 150 МБ/с вы получаете 5–10 МБ/с эффективной скорости, потому что диск 95% времени тратит на позиционирование головок (seek time), а не на передачу данных.

#### В. Конкуренция за ресурс (Noisy Neighbor)
В Ceph фоновые процессы (scrubbing, deep-scrub, recovery, rebalancing) генерируют колоссальный объем случайного I/O.
*   На одиночном диске вне кластера этих процессов нет.
*   В кластере из 3 HDD эти процессы конкурируют с клиентским I/O за те же медленные механические головки. Поскольку метаданные и данные на одном шпинделе, клиентские запросы встают в очередь к фоновым задачам.

#### Г. Усиление записи (Write Amplification)
Из-за фрагментации и особенностей работы RocksDB на HDD, одна логическая запись клиента может превратиться в десятки физических операций чтения-изменения-записи на диске. На NVMe это незаметно, на HDD это катастрофа.

### 3. Резюме: Математика деградации

| Сценарий | Тип нагрузки | Эффективная скорость / Latency | Причина |
| :--- | :--- | :--- | :--- |
| **1x HDD (solo)** | Линейная запись | ~150 MB/s / Low | Нет конкуренции, нет метаданных Ceph. |
| **3x HDD (Ceph, DB on HDD)** | Смешанная/Случайная | ~5-20 MB/s / **Very High** | Головки заняты метаданными; синхронизация по самому медленному диску; фоновые задачи. |
| **3x HDD + NVMe DB** | Смешанная | ~300-400 MB/s / Medium | Метаданные улетают мгновенно; HDD занимаются только линейной записью данных. |

### Рекомендации

1.  **Если нет NVMe:** Не используйте Ceph на чистых HDD для активных рабочих нагрузок (VM, базы данных). Это будет мучительно медленно. Используйте ZFS/Ceph только как холодный архив (backup target), где latency не важен.
2.  **Минимальный конфиг:** Хотя бы один NVMe на узел под WAL+DB для всех HDD-OSD этого узла. Это даст прирост в 10-50 раз.
3.  **Тюнинг (если уже собрано):**
    *   Ограничьте `osd_recovery_max_active` и `osd_max_backfills`, чтобы фоновые задачи не убивали диски.
    *   Увеличьте `bluestore_cache_size`, чтобы попытаться держать горячие метаданные в RAM (но это поможет только при достаточном объеме памяти).
    *   Отключите `deep-scrub` в рабочее время.

**Вывод:** Ваша интуиция верна. Ceph на HDD без внешнего DB превращает преимущества распределенной системы в недостатки, создавая узкое место именно там, где HDD слабее всего — в случайном доступе к метаданным.

### Шаг 1. Установка Ceph на ноды

Начинать нужно с ноды, которая будет инициатором кластера.

1.  В веб-интерфейсе Proxmox выберите первую ноду → раздел **Ceph**.
2.  Нажмите **Install Ceph**.
3.  Выберите репозиторий: **No Subscription** (если у вас нет платной подписки).
4.  Нажмите **Start Squid Installation** → подтвердите (**Yes**). Дождитесь окончания (~193 МБ).
5.  Нажмите **Next**. Откроется окно конфигурации:
    *   **Public Network:** выберите сеть для клиентского трафика.
    *   **Cluster Network:** выберите отдельную сеть для репликации (в видео использовалась та же сеть, что и Public, но **настоятельно рекомендуется** использовать выделенный интерфейс ≥10–25 Гбит/с).
    *   **Number of Replicas:** количество нод в кластере (например, 3).
    *   **Minimum Replicas:** минимальное число копий для работоспособности (обычно 2 при 3 нодах).

7.  **Повторите установку на всех остальных нодах.**
    *   На второй и третьей нодах при установке вы увидите сообщение *«Configuration already initialized»* — это нормально, конфиг подтягивается из кластера Proxmox. Просто жмите **Next** → **Finish**.

### Шаг 2. Создание мониторов (MON) и менеджеров (MGR)

Мониторы следят за состоянием кластера, менеджеры собирают метрики. Нужно по одному на каждую ноду для отказоустойчивости.

1.  Перейдите в **Ceph → Monitors**.
2.  Создайте мониторы на каждой ноде: нажмите **Create**, выберите хост (node2, node3...) → **Create**.
3.  Перейдите в **Ceph → Managers**.
4.  Аналогично создайте менеджеры на каждой ноде. Один будет **Active**, остальные — **Standby** (подхватят автоматически при падении активного).

> 💡 **Аналогия из видео:** Монитор = диспетчер склада. Менеджер = аналитик/отчётность. OSD = сам склад с данными.

### Шаг 3. Создание OSD

OSD (Object Storage Daemon) — это диски, хранящие данные.

1.  Перейдите в **Ceph → OSD**.
2.  Начинайте создание **с первой ноды** (ID присваиваются последовательно: 0, 1, 2...).
3.  Нажмите **Create: OSD**.
4.  Выберите незанятый диск.
    *   **Encryption:** опционально (для продакшена).
    *   **Device Class:** автоопределение или вручную (hdd/nvme).
    *   **DB/WAL Device:** если есть отдельный NVMe для метаданных — укажите его здесь. **Без этого на HDD кластер будет тормозить** (см. предыдущий разговор).
5.  Нажмите **Create**. Повторите для каждой ноды.
6.  После создания нажмите **Reload**, чтобы OSD появились в списке.

> ⛔ **Критически важно:** Никогда не используйте аппаратный RAID-контроллер для дисков Ceph. Только HBA/JBOD режим.

### Шаг 4. Создание пула (Pool)

1.  Перейдите в **Ceph → Pools** → **Create**.
2.  Заполните параметры:
    *   **Name:** имя пула (например, `ceph`).
    *   **Size:** количество реплик (3 для трёх нод).
    *   **Min Size:** минимальное число реплик для доступности (2).
    *   **Crush Rule:** правило размещения (по умолчанию подходит для большинства случаев).
    *   **PGs (Placement Groups):** автор рекомендует начать со **128**. Это «токены» для распределения данных.
    *   **PG Autoscale Mode:** включите для автоматической регулировки PG.
3.  Нажмите **Create**.

> 📐 **Объём пула:** При 3 дисках по 1 ТБ и репликации 3 доступный объём = **1 ТБ** (не 3 ТБ!). Данные дублируются на каждый диск.

### Шаг 6. Настройка High Availability (HA)

Чтобы VM автоматически перезапускалась на другой ноде при сбое:

1.  Перейдите в **Datacenter → HA → Resources → Add**.
    *   Выберите VM.
    *   **Max Restart:** 1.
    *   **Max Relocate:** 1.
    *   **Failback:** включите (возврат на приоритетную ноду после восстановления).
2.  Перейдите в **Affinity Rules → Node**:
    *   Установите приоритеты нод для этой VM (например, node1 = высокий, node2/node3 = ниже).
    *   Без этого VM может мигрировать хаотично.

### Что происходит при сбое (демонстрация из видео)

Автор физически извлёк диск из ноды 1:
*   Кластер обнаружил потерю MON, MGR и OSD.
*   Статус перешёл в **Data Redundancy Degraded**.
*   Началась ребалансировка (recovery).
*   VM автоматически запустилась на другой ноде через HA.
*   После возврата диска кластер **самовосстановился** (health OK).

> ⏱️ **Оговорка:** В энтерпрайзе это происходит с Zero Downtime. На домашнем железе возможна кратковременная недоступность VM во время failover и длительная ребалансировка.

### ⚠️ КРИТИЧЕСКИЙ НЮАНС: Разный объем дисков (7 ТБ и 4 ТБ)

Это самая важная часть для вашей конфигурации. Ceph работает с пулами и репликацией.

**Как Ceph хранит данные:**
Когда вы создаете пул с `Size = 3` (3 копии), Ceph записывает одну копию данных на Ноду 1, вторую на Ноду 2, третью на Ноду 3.
Но внутри каждой ноды у вас **два** OSD (диска). Ceph будет распределять данные между ними.

**Проблема "Деревянной бочки" (Lowest Common Denominator):**
*   Если вы сделаете **один общий пул** на все 6 OSD, Ceph будет стремиться заполнить их равномерно.
*   Диск на **4 ТБ заполнится первым**.
*   Как только OSD на 4 ТБ заполнится (например, на 85-90%), Ceph переведет весь кластер в состояние `HEALTH_WARN` (near full) и может остановить запись, чтобы спасти данные.
*   При этом на дисках по **7 ТБ останется еще ~3 ТБ свободного места**, которые вы **не сможете использовать**, потому что кластер "забился" из-за младших дисков.

> **Итог:** Ваш полезный объем будет ограничен размером самого маленького диска в цепочке репликации.

---

### ✅ Рекомендуемое решение: CRUSH Rules и отдельные пулы

Чтобы эффективно использовать и 7 ТБ, и 4 ТБ, лучше разделить их логически.

#### Вариант А: Два разных пула (Рекомендуется для разного железа)
1.  **Пул "Fast-Small"** (для важных/горячих данных):
    *   Использует только OSD на 4 ТБ.
    *   Crush Rule: выбирает OSD с классом/меткой "ssd-small".
2.  **Пул "Bulk-Large"** (для архивов, бэкапов, больших ВМ):
    *   Использует только OSD на 7 ТБ.
    *   Crush Rule: выбирает OSD с классом/меткой "ssd-large".

*Как это сделать:*
При создании OSD можно вручную присвоить им **Device Class** (не `auto`, а задать кастомный, например `ssd4tb` и `ssd7tb`). Затем при создании Пула выбрать соответствующий **Crush Rule**, который будет использовать только OSD нужного класса.

#### Вариант Б: Один пул, но с пониманием потерь (Проще, но неэффективно)
Вы просто создаете один пул на все 6 OSD.
*   **Плюс:** Проще настроить.
*   **Минус:** Вы потеряете около 3 ТБ × 3 ноды = ~9 ТБ потенциального места, так как кластер упрется в лимит 4-терабайтных дисков.

### ⚠️ ГЛАВНАЯ ОПАСНОСТЬ: "Третий лишний" (Кворум и Репликация)

У вас всего **2 физические ноды с дисками**. Это создает две проблемы, которые нужно решить настройками:

#### Проблема 1: Репликация данных (Size vs Min Size)
Если вы создадите пул с `Size = 3` (3 копии), Ceph попытается положить третью копию данных... а класть некуда! Драйвер не имеет OSD.
*   **Решение:** При создании пула (Pool) обязательно ставьте:
    *   **Size (Replicas):** `2` (данные хранятся в 2 копиях на двух физических нодах).
    *   **Min Size:** `1` (или `2`, если хотите строгую консистентность, но тогда при падении одной ноды пул станет read-only).
    *   *Не ставьте Size 3!* У вас физически только 2 места для хранения.

#### Проблема 2: Кворум мониторов (Самое важное!)
У вас 3 монитора: MON1 (Нода1), MON2 (Нода2), MON3 (Driver).
Для работы кластера нужен кворум = **2 из 3**.

**Сценарий катастрофы:**
1.  Вы перезагружаете **Ноду 1** (для обновлений).
2.  Работают MON2 и MON3. Кворум есть (2 из 3). Всё ок.
3.  В этот момент **Driver (Нода 3)** зависает, уходит в ребут или теряет сеть.
4.  Остается только MON2. **1 из 3 — кворума нет.**
5.  **Весь Ceph кластер блокируется.** Виртуалки на Ноде 2 зависнут, потому что не смогут записать данные (кластер ждет кворума).

> **Вывод:** Монитор на Драйвере делает кластер *менее* надежным в сценарии обслуживания, если Драйвер менее стабилен, чем физические ноды.

### 🛡 Как настроить это безопасно?

Если вы всё же хотите использовать Driver для третьего монитора (чтобы избежать split-brain между двумя нодами), сделайте следующее:

#### 1. Настройка пулов (CRUSH Rule)
Вам нужно сказать Ceph, что данные можно хранить **только** на Ноде 1 и Ноде 2, и никогда не пытаться хранить их на Драйвере.

При создании пула в Proxmox:
*   **Crush Rule:** Создайте правило, которое выбирает тип `host` и исключает хост Driver. Либо проще: так как у Драйвера нет OSD, Ceph сам не сможет туда ничего записать, но лучше убедиться, что `Size = 2`.

#### 2. Приоритет мониторов (Weight)
Можно понизить вес монитора на Драйвере, чтобы он реже становился лидером, но для кворума это не сильно поможет. Главное — стабильность Драйвера.

#### 3. Альтернатива: QDevice (Рекомендуется для 2 нод!)
Вместо полноценного монитора на Драйвере, в Proxmox для кластеров из 2 нод существует механизм **QDevice (Quorum Device)**.
*   Это легковесный сервис, который работает на третьей машине (вашем Драйвере).
*   Он **не хранит данные** и не является полноценным MON.
*   Он просто отдает свой голос при потере связи между Нодой 1 и Нодой 2.

**Как это выглядит в вашей схеме:**
*   **Нода 1:** MON + MGR + OSD
*   **Нода 2:** MON + MGR + OSD
*   **Driver:** Только **QDevice** (без MON, без MGR).

Это **намного безопаснее** для схемы из 2 нод.
*   Если Нода 1 падает -> Нода 2 + QDevice = кворум есть.
*   Если Driver падает -> Нода 1 + Нода 2 = кворум есть (2 из 2).
*   Кластер не заблокируется, если Driver уйдет в ребут вместе с одной из нод.

| :--- | :--- | :--- | :--- |

### USER
Я создал кластер - у каждого сервера в класторе своя аперативка при создании ceph в котором обьединяться диски аперативка обьединиться?

### ASSISTANT
**Нет, оперативная память (RAM) НЕ объединяется.**

Ceph объединяет в единое целое **только диски**. 

Вот как это работает:
1. **Диски:** Становятся общим пулом (хранилищем). Виртуалка может лежать на дисках разных серверов.
2. **Оперативная память:** Остается **строго локальной** на каждом сервере. 
   * Ceph использует RAM каждого сервера только для кэширования *своих же* дисков (BlueStore cache). Чем больше RAM на сервере, тем быстрее работают его локальные OSD.
   * Виртуальная машина потребляет RAM только того сервера, на котором она физически запущена в данный момент.

**Итог:** У вас будет **общее дисковое пространство**, но **раздельная оперативная память**. Единого "пула RAM" в Proxmox и Ceph не существует.

### USER
Если я буду создавать вм то как мне раздавать ram ? если вм будут лежать на общем диске

### ASSISTANT
**RAM вы раздаёте каждой ВМ вручную при создании. Берётся она с той ноды, где ВМ запущена сейчас.**

Как это работает:

1. **При создании ВМ** вы выбираете ноду (сервер) и указываете ей объём RAM (например, 4 ГБ).
2. Эти 4 ГБ вычитаются из физической памяти **этой конкретной ноды**. Общий Ceph тут не участвует — он отдаёт только диск.
3. **Лимит:** на каждой ноде следите за свободной памятью отдельно. Если на ноде свободно 8 ГБ, вы не запустите на ней ВМ с 16 ГБ RAM.

**Главный плюс общего диска (Ceph):**

* Диск ВМ не привязан к серверу, поэтому ВМ можно **мигрировать на другую ноду в один клик** (live migration, без остановки).
* При миграции сам диск никуда не копируется (он и так общий) — по сети передаётся только содержимое RAM.
* После миграции ВМ начинает потреблять RAM **новой ноды**.

**Итог:** Диски — общие, а RAM раздаёте вручную под каждую ВМ из запасов той ноды, на которой она работает в данный момент.

### USER

### ASSISTANT

 Настройка HA кластера и Ceph Когда в каких случаях делается? НА это альтернатива caph или они работают совместно  - распиши все варианты, или они не смешиваются? Я не понимаю

### Порядок настройки (когда и что делается)

1.  **Proxmox-кластер** (объединение нод) — база, делается первым.
2.  **Общее хранилище** (Ceph или альтернатива) — делается вторым.
3.  **ВМ на общем хранилище**.
4.  **HA** — включается последним, поверх готового хранилища, если нужна авто-перезагрузка ВМ при сбоях.

### Все варианты комбинаций

| Вариант | Хранилище | HA | Что получишь при падении ноды |
| :--- | :--- | :--- | :--- |
| 1. Кластер без всего | Локальные диски | Нет | ВМ умерли. Всё вручную. |
| 2. Кластер + Ceph | Ceph | Нет | Данные живы, но ВМ запускаешь **вручную** на другой ноде. |
| 3. Кластер + NFS/iSCSI | Внешний сервер | Нет | Данные живы, ВМ вручную. Но сервер хранилища — **единая точка отказа**. |
| 4. Кластер + NFS + HA | Внешний сервер | Да | ВМ перезапускаются сами, но если умрёт NFS-сервер — умрёт всё. |
| 5. **Кластер + Ceph + HA** | Ceph | Да | **Полный автомат:** данные живы, ВМ перезапустились сами. Единой точки отказа нет. |

---

### Альтернативы Ceph для HA

HA всё равно, какое общее хранилище стоит. Вместо Ceph можно использовать:
*   **NFS** (шара с отдельного сервера/NAS)
*   **iSCSI / SAN** (отдельный СХД-сервер)
*   **ZFS over iSCSI**

**Разница:** все альтернативы требуют **отдельного сервера-хранилища**, который сам становится единой точкой отказа. Ceph — единственный гиперконвергентный вариант: хранилище живёт прямо на нодах кластера и реплицируется, поэтому точки отказа нет.
