# Ceph: метаданные, разные диски и связь с HA

## Почему Ceph на «голых» HDD может быть медленнее одного диска
Каждая операция Ceph сопровождается служебной записью в RocksDB (метаданные,
PG-логи) и WAL — они крайне чувствительны к задержке. На NVMe задержка —
микросекунды, на HDD — миллисекунды (разница на порядки). Если RocksDB/WAL
лежат на том же HDD, что и данные, головки диска мечутся между
пользовательской записью и обновлением метаданных — линейная скорость
диска (~150 МБ/с) может упасть до 5-20 МБ/с эффективных. Дополнительно
кластер синхронно ждёт **самый медленный** OSD из реплик (`max(latency
всех реплик)`), а фоновые процессы (scrub, recovery, rebalance) добавляют
случайный I/O, конкурирующий с клиентским.

**Правило:** на чистых HDD под активную нагрузку (ВМ, БД) выносить WAL/DB
на отдельный NVMe (даёт прирост в 10-50 раз) либо не использовать HDD для
Ceph под активные нагрузки вообще (годится только под холодный архив).
**Если сами диски — SSD, отдельный NVMe под WAL/DB не нужен** — RocksDB
на том же SSD работает достаточно быстро.

## Проблема «деревянной бочки» при разных объёмах дисков
Если в один пул объединить диски разного объёма (например, 7 ТБ и 4 ТБ на
одной ноде), Ceph стремится заполнять все OSD равномерно. Меньший диск
(4 ТБ) заполнится первым и при приближении к порогу (~85-90%) переведёт
**весь кластер** в `HEALTH_WARN`/остановку записи — даже если на
7-терабайтных дисках ещё остаётся свободное место. Полезный объём кластера
ограничивается самым маленьким диском в цепочке репликации.

**Решение при разных объёмах:** присвоить дискам разные **Device Class**
(например, `ssd-small`/`ssd-large`) и создать под каждый класс отдельный
пул со своим CRUSH-правилом — тогда крупные и мелкие диски не заполняются
«по меньшему».

## Итоговая схема для 2 узлов + QDevice (подтверждено и согласовано с `AI-environment_facts`)

| Компонент | Где размещать | Количество | Почему |
|---|---|---|---|
| MON | Только на pve01, pve02 | 2 | На QDevice — не MON, а именно QDevice-механизм |
| MGR | Только на pve01, pve02 | 2 | Один active, второй standby |
| OSD | Только на pve01, pve02 | по числу физических дисков данных | На QDevice физических дисков для Ceph нет |
| QDevice | Отдельный хост/VM вне кластера | 1 | Даёт третий голос кворума **Corosync**, не Ceph-MON — не хранит данные |
| Pool Size | — | **2** | Больше двух копий класть некуда — только 2 узла с OSD |
| Pool Min Size | — | **1** | Кластер продолжает писать даже при потере одного узла (при `Min Size=2` пул уйдёт в read-only при падении узла) |

**Почему не 3 полноценных монитора (включая QDevice-хост как MON):**
Ceph-кворум мониторов требует нечётного числа и большинства (`2 из 3`).
Если третий «монитор» посадить на менее стабильный QDevice-хост, а не на
физический узел с данными, риск одновременной потери MON-кворума
(например, при плановой перезагрузке одного из двух основных узлов,
совпавшей со сбоем QDevice-хоста) — выше, чем при правильном QDevice,
который специально спроектирован именно для случая «2 узла + голос
кворума» и не хранит данные.

## RAM в Ceph не объединяется
Ceph объединяет **только диски**. Оперативная память остаётся строго
локальной на каждом узле — используется лишь для кэша BlueStore *своих же*
OSD. Виртуальная машина потребляет RAM того узла, на котором физически
запущена в данный момент; при live-миграции по сети передаётся содержимое
RAM, а не диск (диск и так общий через Ceph). RAM для новой ВМ выделяется
вручную при создании, с учётом свободной памяти именно на целевом узле.

## Ceph и HA — разные задачи, работают вместе
- **Ceph** = отказоустойчивость **данных**: диски реплицируются, при
  падении узла/диска данные остаются доступны с других узлов.
- **HA** = отказоустойчивость **сервиса**: при падении узла ВМ
  автоматически перезапускается на другом узле.
- **HA работает только при общем хранилище** (Ceph, NFS, iSCSI) — если
  диск ВМ локальный, HA не сможет поднять её на другом узле (там нет
  диска).

**Порядок настройки:** Proxmox-кластер → общее хранилище (Ceph) → ВМ на
общем хранилище → HA (последним, поверх готового хранилища). Создавать ВМ
до готовности Ceph имеет смысл только при срочной необходимости — тогда
на `local-lvm`, с последующим переносом через `Move Storage`.

## Диски можно добавлять в любой момент
`Ceph → OSD → Create: OSD` на новом диске — в любое время, кластер сам
перебалансирует данные (нагрузка на сеть/диски, лучше делать в спокойное
время). При добавлении диска другого класса/объёма — снова помнить про
проблему «деревянной бочки».

## Уточнение по составу дисков (разрешено следующим документом этой же пачки)
В этом обсуждении реальный состав дисков не был точно подтверждён (звучал
как общий пример «7 ТБ + 4 ТБ», без вывода команд). Реальная конфигурация,
подтверждённая `lsblk` на обеих нодах в `PROXMOX-CEPH-OSD-DISK-PREP-2026-001`:
на каждой ноде — **`sdb` (7 ТБ, SSD) + `nvme0n1` (3.5 ТБ, NVMe)**, разные
по типу и объёму, но не «7+4». Это и есть основание для решения из этого
документа про разные device class и раздельные пулы — оно осталось верным,
просто с уточнёнными реальными цифрами. Сверка с `hardware-spec.md`
(ещё не мигрирован) по-прежнему актуальна для полей CPU/RAM, но по дискам
данных источником истины теперь считать `PROXMOX-CEPH-OSD-DISK-PREP-2026-001`.
