# Подготовка дисков и утверждённая архитектура OSD для Ceph

## Реальная дисковая конфигурация (подтверждено `lsblk` на обеих нодах)

| Устройство | Размер | Тип | Роль |
|---|---|---|---|
| `sda` | 446.1 ГБ | AVAGO | Системный диск Proxmox (зеркало) |
| `sdb` | 7 ТБ | AVAGO, **SSD** (не HDD) | Данные Ceph — «ёмкий» OSD |
| `nvme0n1` | 3.5 ТБ | Samsung MZQLW3T8HMLP (NVMe) | Данные Ceph — «быстрый» OSD |

Идентична на `pve01` и `pve02`.

## Проверка перед созданием OSD

**1. Синхронизация времени** (критична для Ceph — рассинхронизация ломает кворум):
```bash
chronyc tracking
```
Подтверждено на обеих нодах: Stratum 3, смещение < 1 мс — в норме.

**2. Состояние дисков:**
```bash
lsblk -d -o NAME,SIZE,MODEL,TYPE,MOUNTPOINT
lsblk -f /dev/sdb /dev/nvme0n1     # именно -f, чтобы увидеть FSTYPE/UUID
```
**Обнаружено:** `sdb`/`nvme0n1` на pve02 (и частично на pve01) содержали
**остаточные NTFS-разделы** с китайскими метками (`新加卷` — «новый том»)
— следы предыдущего использования дисков в Windows-системе, не относящиеся
к текущей задаче.

## Очистка дисков (обязательно перед созданием OSD)

⚠️ Безвозвратно удаляет все данные на указанных устройствах.
```bash
wipefs -a /dev/sdb
sgdisk --zap-all /dev/sdb
wipefs -a /dev/nvme0n1
sgdisk --zap-all /dev/nvme0n1
```
`wipefs -a` убирает сигнатуры файловых систем, `sgdisk --zap-all` —
таблицу разделов GPT (включая backup GPT в конце диска). При необходимости
`apt install gdisk` (для `sgdisk`). После — `partprobe`, если ядро не сразу
увидело изменения.

**Проверка результата:**
```bash
lsblk -f /dev/sdb /dev/nvme0n1
```
Ожидается: пусто (без FSTYPE/UUID/MOUNTPOINTS) — подтверждено на обеих нодах.

## Как принималась финальная архитектура OSD (ход рассуждения, коротко)

Рассматривались варианты выделения `nvme0n1` под DB/WAL для `sdb`:
- Весь `nvme0n1` (3.5 ТБ) под DB/WAL для `sdb` → большая часть NVMe простаивала бы (DB нужно ~280 ГБ = 4% от 7 ТБ).
- Раздел `nvme0n1` на 300 ГБ (DB/WAL) + ~3.2 ТБ (независимый OSD) → сложнее в настройке, но полное использование объёма.
- **Принято:** `nvme0n1` целиком — отдельный независимый OSD, `sdb` — отдельный OSD со своим DB/WAL на себе же (не критично, так как `sdb` тоже SSD, а не HDD).

Решающий фактор — характер нагрузки (Active Directory, база 1С, терминальный
сервер — все три чувствительны к задержкам, особенно 1С как OLTP) и сеть
Ceph, которая **была впоследствии повышена с 1 Гбит/с до 10 Гбит/с**
(та же пара `nic4`+`nic5` в `bond0`, режим оставлен `active-backup` — сочли
переход на LACP не нужным при текущей нагрузке). При 10G сеть перестаёт
быть основным узким местом, что сделало вынос части NVMe под отдельный
быстрый OSD осмысленным.

## Утверждённая архитектура (финал)

| Устройство | Роль | Пул | Для чего |
|---|---|---|---|
| `nvme0n1` (на каждой ноде) | Независимый быстрый OSD | `ceph-fast` | Active Directory, база 1С (OLTP), терминальный сервер — чувствительные к задержкам нагрузки |
| `sdb` (на каждой ноде) | Независимый ёмкий OSD | `ceph-bulk` | Бэкапы, менее критичные к задержкам ВМ |

Итого **4 OSD в кластере** (по 2 на узел), выделенный раздел под DB/WAL —
не создавался (упрощение, обосновано выше).

## ⛔ Don't repeat
- `lsblk` без `-f` не показывает файловую систему/UUID — можно принять «грязный» диск за чистый.
- Не создавать OSD, не очистив остаточные разделы (`wipefs -a` + `sgdisk --zap-all`).
- DB на Ceph BlueStore требует ~4% от объёма данных — не пытаться уложиться в 1 ГБ.
- При апгрейде сети — пересматривать ранее принятые архитектурные компромиссы, они могли основываться на устаревшем узком месте (в данном случае — сети 1G).

## Проверка результата
- [x] `chronyc tracking` — синхронизация в норме на обеих нодах.
- [x] `lsblk -f /dev/sdb /dev/nvme0n1` — оба диска чистые на обеих нодах.
- [ ] (следующий документ/шаг) — фактическое создание OSD и пулов через `Datacenter → Ceph → OSD/Pools`.
