# Архитектурные решения: дисковая и сетевая топология для Ceph-кластера

## Статус документа
Это запись **планового обсуждения** архитектуры (с внешним ассистентом,
до фактического внедрения), а не протокол выполненных команд. Фактически
выполненная установка OSD и пулов зафиксирована в отдельных документах
(«Создание Ceph №1», «Настройка Ceph Планирование Дисков OSD», «Установка
Ceph OSD на pve02 pve01» — ещё не мигрированы). Часть этого обсуждения
(схема на 3 узла, `Size=3/Min Size=2`) в итоге **не была реализована** —
подтверждённая реальная топология (`AI-environment_facts-korona-proxmox.md`)
это **2 узла (pve01, pve02) + внешний Corosync QDevice**, без третьего
полноценного узла с OSD. Ниже отмечено, какие решения относятся к
фактически принятой 2-узловой схеме, а какие — к обсуждавшейся, но не
реализованной 3-узловой.

## Решение 1: диски данных (7 ТБ) — отдельные OSD, не RAID/ZFS mirror

**Принято и актуально независимо от числа узлов.**

| Вариант | Итог | Вердикт |
|---|---|---|
| Каждый 7 ТБ диск — отдельный OSD | Полная сырая ёмкость участвует, Ceph сам реплицирует между узлами | ✅ Выбрано |
| RAID1/ZFS mirror из двух 7 ТБ + один OSD поверх | Теряется ~50% ёмкости, двойная репликация (RAID + Ceph) — лишняя нагрузка | ❌ Отклонено |

Причина: отказоустойчивость на уровне диска здесь избыточна — Ceph и так
хранит копии данных на **разных узлах**, локальное зеркалирование внутри
одного узла почти ничего не добавляет к надёжности, только съедает место.

Диски перед созданием OSD должны быть чистыми, без разделов:
```bash
lsblk    # диски данных должны быть без разделов (sdc, sdd и т.п.)
```
OSD создаются через `Datacenter → Ceph → OSD → Create: OSD`, каждый диск
по отдельности (не через `zpool`/`mdadm`).

## Решение 2: системный диск — зеркало 2×480 ГБ

Отдельно от дисков данных: ОС + `local-lvm` (только ISO/шаблоны/некритичные
тестовые ВМ) — на программном или аппаратном RAID1 из 480 ГБ дисков,
настраивается штатно на этапе установки Proxmox. **Все основные рабочие ВМ
— только на Ceph**, не на `local-lvm` (иначе теряется live-migration и HA
при падении узла).

## Решение 3: разделение сетей

**Принято.**

| Сеть | Что через неё ходит | Скорость |
|---|---|---|
| Внутренняя | Ceph Public + Ceph Cluster + Corosync (кластерный кворум) | 10G |
| Внешняя | Веб-интерфейс, SSH, трафик ВМ наружу | 1G |

Обоснование: Corosync критично чувствителен к задержкам и потерям пакетов
— выделенная быстрая сеть снижает риск ложных срабатываний кворума.
Проверить, какая сеть реально используется кластером:
```bash
cat /etc/pve/corosync.conf   # смотреть строку ring0_addr
```

## Решение 4: параметры пула Ceph — зависят от числа узлов

**Для фактически реализованной топологии (2 узла + QDevice) — актуально:**
```
Size: 2
Min Size: 1
```
QDevice не имеет OSD и не участвует в размещении данных Ceph (CRUSH-правило
исключает его) — он даёт кворум только уровню Corosync/Proxmox, не Ceph.

**Обсуждавшийся, но не реализованный вариант на 3 полноценных узла:**
```
Size: 3
Min Size: 2
```
Такая схема даёт больше устойчивости (переживает потерю любого одного из
трёх узлов без риска для записи), но требует третьего узла именно с OSD,
а не просто QDevice для кворума. Если инфраструктура когда-либо перейдёт
на 3 полноценных узла с данными — вернуться к этому варианту.

## Справочно: типовой порядок действий для этой топологии (обобщённая шпаргалка из обсуждения)
1. Установка Proxmox на все узлы (системное зеркало 480 ГБ).
2. Создание кластера Proxmox (`pvecm create`/`pvecm add`) — по **внутренней** 10G сети.
3. Установка пакетов Ceph на каждом узле (`Node → Ceph → Install Ceph`).
4. Инициализация Ceph с указанием Public/Cluster network = внутренняя 10G подсеть (`pveceph init --network <subnet>` или через GUI).
5. Создание Monitor + Manager на каждом узле с OSD.
6. Создание OSD — по одному на каждый диск данных.
7. Создание пула с параметрами по числу реальных узлов с данными (см. Решение 4).
8. Добавление RBD-хранилища в Proxmox (`Datacenter → Storage → Add → RBD`).
9. Создание ВМ с диском на этом хранилище.

Проверочные команды:
```bash
ceph -s              # HEALTH_OK
ceph osd tree         # все OSD up/in
ceph df               # использование места
pveceph status
```

## ⛔ Don't repeat
- Не зеркалировать диски данных перед созданием OSD.
- Не ставить Ceph Monitor на QDevice.
- Не путать параметры пула для 2-узловой (Size=2/MinSize=1) и 3-узловой (Size=3/MinSize=2) схем — использовать те, что соответствуют **реальному** числу узлов с OSD, а не общей рекомендации из статьи/видео.
