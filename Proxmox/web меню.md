**Шаг 1 — Подробная расшифровка меню «Datacenter» в Proxmox VE 8.2.2 (по вашему скриншоту)**

На скриншоте открыта правая панель — меню объекта **Datacenter** (обведено красной рамкой), ветка **Permissions** развёрнута. Разбираю каждый пункт сверху вниз.

---

### Основные пункты меню

**1. Search** — поиск по объектам датацентра: узлы, виртуальные машины (VM), контейнеры (CT), хранилища, пулы. Поиск идёт по имени и по ID (например, ввод «100» находит VM 100). Клик по результату сразу переносит к объекту в дереве слева.

**2. Summary** — сводка по датацентру: версия Proxmox VE (на скриншоте 8.2.2), состав и состояние узлов, общая статистика по объектам. Быстрый ответ на вопрос «что у меня вообще есть и в каком оно состоянии».

**3. Notes** — свободные текстовые заметки администратора по датацентру. Хранятся в конфигурации кластера и видны всем, кто имеет доступ к датацентру. Удобно фиксировать договорённости, особенности конфигурации, контакты.

**4. Cluster** — создание кластера Proxmox VE и управление им:
- создание нового кластера (объединение нескольких узлов в единое управление);
- генерация «Join Information» — данных для присоединения нового узла;
- просмотр состава кластера и состояния quorum.
Если кластер не создан — узел работает автономно (как ваш `pve` на скриншоте).

**5. Ceph** — встроенное управление гиперконвергентным хранилищем Ceph прямо из веб-интерфейса:
- статус кластера Ceph;
- установка Ceph-пакетов на узлы, если Ceph ещё не развёрнут;
- управление OSD, MON, MGR;
- создание пулов для дисков VM/CT;
- просмотр конфигурации и CRUSH-схемы.

**6. Options** — параметры датацентра (применяются ко всем узлам), например:
- раскладка клавиатуры для консолей (keyboard);
- язык интерфейса (language);
- лимиты пропускной способности (bwlimit) для backup / restore / migration / clone / move;
- настройки миграции по умолчанию (тип миграции, выделенная сеть);
- тип консоли по умолчанию (VNC/SPICE/xterm.js);
- стиль тегов, MAC-префикс, лимит параллельных операций (max_workers).

**7. Storage** — добавление и настройка хранилищ на уровне датацентра (доступны всем узлам). Поддерживаемые типы: Directory, NFS, CIFS, iSCSI, LVM, LVM-Thin, ZFS over iSCSI, Ceph RBD, CephFS, Proxmox Backup Server и др. Для каждого хранилища задаётся, какой контент на нём хранится: Disk Image, ISO Image, Container Template, VZDump Backup File. Здесь же хранилища включаются/отключаются и удаляются.

**8. Backup** — плановые резервные копии (vzdump) на уровне всего датацентра:
- создание заданий с выбором VM/CT (все или конкретные ID);
- целевое хранилище и режим: **snapshot** (без остановки), **suspend** (с паузой), **stop** (с остановкой);
- расписание (daily / weekly / monthly / произвольный calendar-формат);
- политики хранения (retention: keep-last, keep-daily, keep-weekly, keep-monthly);
- просмотр журналов и ручной запуск.

**9. Replication** — плановая репликация дисков VM на другой узел: создаёт и периодически обновляет копию дисков на целевом узле (работает для хранилищ, поддерживающих репликацию, прежде всего локального ZFS). Используется для отказоустойчивости и быстрой миграции после сбоя узла.

---

### Ветка Permissions (RBAC — управление доступом)

**10. Permissions** — механизм «роль + субъект + объект». Внутри развёрнуты подпункты:

- **Users** — учётные записи: создание/редактирование, пароли, включение/отключение, e-mail, срок действия, участие в группах. Пользователи существуют в realm'ах: `pve` (встроенный Proxmox VE), `pam` (системные Linux-пользователи), а также LDAP / Active Directory / OpenID Connect после настройки realm'а.
- **API Tokens** — токены для доступа к API от имени пользователя без пароля. У токена собственные права (можно отделить от прав пользователя) и срок действия. Основа для автоматизации (Terraform, ansible, скрипты бэкапов и т.п.).
- **Two Factor** — двухфакторная аутентификация: TOTP (приложения-аутентификаторы), WebAuthn (FIDO2/U2F-ключи), recovery-ключи. Здесь же задаётся обязательность 2FA на уровне датацентра/realm'а.
- **Groups** — группы пользователей. Права выдаются группе один раз, а не каждому пользователю отдельно (например, группа `admins`).
- **Pools** — пулы объектов (VM/CT/хранилища). Логическая группировка, чтобы выдать права сразу на набор объектов (например, «все VM отдела бухгалтерии»).
- **Roles** — роли, то есть наборы привилегий. Встроенные примеры: `Administrator` (полный доступ), `PVEAuditor` (только чтение), `PVEVMAdmin` (управление VM), `PVEVMUser` (пользователь VM: консоль и т.п.), `PVEDatastoreAdmin` / `PVEDatastoreUser` (бэкапы), `PVESysAdmin`, `PVEMappingAdmin`, `PVETemplateUser`, `NoAccess`. Можно создавать собственные роли.

**Шаг 2 — Разбор меню «HA» (Datacenter → HA): пункты Groups и Fencing, с примерами под вашу конфигурацию (2 ноды + qdevice)**

**Контекст.** HA-стек Proxmox VE (pve-ha-manager) следит за помеченными ресурсами (VM/CT) и при падении узла перезапускает их на другом узле. Работает только при наличии quorum в corosync-кластере — именно поэтому в схеме из двух нод необходим qdevice.

**Сам пункт «HA»** (клик по строке HA) открывает панель **Status**: список HA-ресурсов (vm:100, ct:101…), их состояние (started / stopped / disabled), узел, на котором ресурс работает, состояние HA-менеджеров (master/lrm) и quorum. Здесь ресурсы добавляют и меняют им состояние.

---

### 1. Groups

HA-группа — именованный набор узлов с **приоритетами** и флагом **restricted**. Определяет, где ресурсу предпочтительно/разрешено работать и куда он едет при failover.

Поля в GUI (кнопка Create): Group ID; Nodes (узлы + приоритет); Restricted (checkbox); Comment.

**CLI-пример под вашу схему** (ноды условно pve1, pve2):

```bash
ha-manager groupadd grp-main pve1,pve2 --priority 1,2 --restricted 0
```
- `--priority 1,2` — предпочтительный узел pve1, запасной pve2;
- `--restricted 0` — ресурс предпочитает группу, но не заперт в ней (в схеме из двух нод это фактически не играет роли).

**Пример с restricted=1:**
```bash
ha-manager groupadd grp-pve1-only pve1 --restricted 1
```
Ресурс с такой группой работает **только** на pve1; при смерти pve1 он не поднимется на pve2 (останется в ошибке). Применяется, когда VM привязана к локальным ресурсам узла.

**Привязка ресурса к группе:**
```bash
ha-manager add vm:100 --state started --group grp-main
```

⚠️ Важно для двух нод: failover реально произойдёт, только если диски VM доступны на второй ноде — **общее хранилище** (NFS/Ceph и т.п.) либо **репликация дисков**. На чисто локальных хранилищах HA не сможет поднять VM на другом узле.

---

### 2. Fencing

Панель механизма **fencing** — изоляции «умершего» узла, чтобы одна и та же VM не работала одновременно на двух узлах (защита от split-brain и двойного монтирования хранилища). В Proxmox VE fencing выполнен через **watchdog**: узел страхует сам себя — по команде HA-менеджера либо при истечении блокировки watchdog узел гарантированно уходит в перезагрузку.

Панель Fencing показывает по каждому узлу, настроен ли watchdog и активен ли он (устройство/модуль, например iTCO_wdt).

**Проверка на узле:**
```bash
wdctl
```
Пример вывода (аппаратный watchdog Intel):
```
Device:        /dev/watchdog
Identity:      iTCO_wdt [version 0]
Timeout:       10 seconds
```
Если watchdog не настроен — загружается модуль (например, `modprobe iTCO_wdt` + запись в `/etc/modules`; программный fallback — `softdog`, но для production рекомендуется аппаратный watchdog).

---

### Почему для «2 ноды + qdevice» критичны оба элемента

- **qdevice даёт quorum**: голоса 1 (pve1) + 1 (pve2) + 1 (qdevice) = 3, quorum ≥ 2. При потере одной ноды оставшаяся имеет 2 голоса → quorum сохранён → HA имеет право действовать. Без qdevice при двух нодах потеря узла = потеря quorum = HA парализован.
- **Fencing (watchdog) даёт безопасность**: оставшаяся нода уверена, что «пропавшая» нода не продолжает крутить VM, и только тогда запускает их у себя.

**Шаг 3 — Разбор меню «SDN» (Datacenter → SDN): Zones, VNets, Options, IPAM**

SDN (Software Defined Networking) в Proxmox VE — это слой абстракции над сетями: вы описываете «зоны» и «виртуальные сети» (vnet), а Proxmox сам создаёт нужные интерфейсы (bridge/VLAN/VXLAN/VRF) на узлах после применения конфигурации. Доступен начиная с Proxmox VE 7.0 (сначала как tech preview, в последующих версиях доведён до рабочего состояния). Конфигурация хранится в `/etc/pve/sdn/` (zones.cfg, vnets.cfg, ipam.cfg, controllers.cfg, dns.cfg).

---

### 1. Zones

**Зона** — изолированная сетевая область, к которой привязываются VNets. Типы зон (по документации Proxmox SDN):

| Тип зоны | Суть | Когда применять |
|---|---|---|
| `simple` | Обычный Linux-bridge на узле, без тегов | Локальные сети узла, простые мосты |
| `vlan` | VLAN-aware bridge; VNets получают VLAN-теги; L2 тянется между узлами, если физический свич транкует эти VLAN | Классическая VLAN-сегментация |
| `evpn` | VXLAN + EVPN (BGP control plane); L2 растягивается поверх fabric без multicast; требует controller и VRF на узлах | Растянутые L2-сегменты между узлами без VLAN на свиче |

(В старых версиях присутствовал также тип `vxlan` — сейчас считается устаревшим; если встретите в документации — это именно так.)

Ключевые параметры зоны: `bridge` (физический мост, напр. vmbr0), MTU; для evpn — VRF, VXLAN-порт и ссылка на controller.

**Пример (CLI) под вашу схему из двух нод — VLAN-зона:**
```bash
pvesdn create zone vlan vz-vlan --bridge vmbr0
```
Условие: vmbr0 должен быть vlan-aware, а порт свича — trunk с нужными VLAN.

### 2. VNets

**VNet** — виртуальный L2-сегмент внутри зоны. Именно к vnet (а не к bridge) подключается сетевая карта VM/CT: в конфиге VM будет `bridge=vnetXXX`.

Параметры vnet: `zone`, `tag` (VLAN ID для vlan-зон, VNI для evpn), `alias`, в текущих версиях — **subnets** (CIDR + gateway + диапазоны) для связки с IPAM/DHCP.

**Пример:**
```bash
pvesdn create vnet prod --zone vz-vlan --tag 10 --alias production
pvesdn apply   # обязательное применение конфигурации SDN
```
После `pvesdn apply` (или кнопки Apply в GUI) Proxmox создаст на узлах соответствующие интерфейсы. В мастере создания VM сетевой device указываете с bridge = `prod`.

### 3. IPAM

**IPAM** — управление IP-адресацией для vnet-подсетей. Поддерживаемые бэкенды (по документации):
- `pve` — встроенный IPAM, работает без внешней настройки; хранит выданные адреса в кластере;
- `phpIPAM` — внешняя система, подключение по URL + токен;
- `Netbox` — внешняя система, подключение по URL + токен.

Схема работы: на vnet заводите подсеть (например `192.168.10.0/24`, gateway `192.168.10.1`), и при подключении NIC к этому vnet адрес резервируется в IPAM и виден в карточке VM (может передаваться в cloud-init). Это убирает ручное ведение таблиц адресов.

### 4. Options

**Options** — глобальные параметры подсистемы SDN (включение/выключение SDN и служебные настройки применения конфигурации). Точный набор полей зависит от версии Proxmox VE — сверьтесь со своей вкладкой Options в GUI; я не буду додумывать конкретные поля, чтобы не дать неверную деталь.

---

**Примечания (с пометкой о неуверенности):**
- В ряде версий Proxmox VE в меню SDN присутствует также пункт **Controllers** (настройка EVPN/BGP-контроллеров для зон типа evpn). На вашем скриншоте его не видно — возможно, из-за кадрирования или особенности версии. Проверьте в своём интерфейсе.
- Для двух нод + qdevice типичный сценарий SDN — `vlan`-зона + VNets + встроенный IPAM. `evpn` имеет смысл, только если fabric поддерживает BGP и нужны растянутые L2 без VLAN на свиче — для двух нод это обычно избыточно.
