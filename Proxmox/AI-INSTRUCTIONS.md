# AI-INSTRUCTIONS.md

## Статус документа

Этот файл содержит обязательные инструкции для искусственного интеллекта,
работающего с репозиторием инфраструктурной документации.

Инструкции распространяются на:

- ответы по документации;
- диагностику Proxmox;
- работу с виртуальными машинами;
- работу с Ceph;
- работу с Windows Server;
- работу с шаблонами и клонами;
- работу с сетями;
- работу с резервными копиями;
- создание и изменение Markdown-файлов;
- обновление индексов;
- подготовку команд для администратора.

ИИ должен считать эти правила обязательными.

---

# 1. Приоритет правил

Использовать следующие уровни приоритета (сверху вниз — от высокого к низкому):

1. явно сформулированное требование пользователя;
2. текущая конфигурация и свежий вывод команд;
3. профильная документация конкретной системы или ВМ;
4. `Proxmox/INDEX.md`;
5. `AI-README.md`;
6. остальные документы репозитория;
7. официальная документация Proxmox, Microsoft, Ceph или другого поставщика;
8. общие знания ИИ.

Если пользователь просит действие, нарушающее безопасность production,
ИИ должен предупредить о риске и предложить безопасную процедуру.
Если пользователь требует выполнить опасную операцию без проверки, ИИ не
должен молча соглашаться.

---

# 2. Главная задача

Главная задача ИИ — дать точный, короткий, проверяемый и безопасный ответ.

ИИ не должен:

- демонстрировать знания без практической пользы;
- повторять весь репозиторий;
- предлагать несколько десятков вариантов без необходимости;
- скрывать неизвестные параметры;
- выдавать предположение за факт;
- запускать опасную процедуру без подтверждения;
- менять несвязанные документы;
- удалять исторические данные без запроса;
- придумывать IP, пароли, VM ID или номера разделов.

---

# 3. Режимы работы

Перед ответом определить режим задачи и пометить его явно в начале ответа.

## 3.1. Режим поиска ответа

Использовать, если пользователь спрашивает:

- где находится информация;
- как настроена ВМ;
- какой используется storage;
- какой размер диска;
- зависит ли клон от шаблона;
- какая команда уже применялась.

Порядок действий:

1. определить ключевые слова;
2. открыть `Proxmox/INDEX.md`;
3. выбрать профильный файл;
4. прочитать YAML-контекст;
5. проверить `Quick Answers`;
6. дать краткий ответ;
7. указать источник в репозитории и, по возможности, привязку к коммиту/файлу.

Пример вывода: одно-два предложения с ссылкой на файл и нужными параметрами.

## 3.2. Режим диагностики

Использовать, если пользователь сообщает об ошибке.

Порядок действий:

1. переформулировать проблему одним предложением;
2. определить систему и объект (кластер, узел, VM ID, storage);
3. указать наиболее вероятную причину;
4. отделить подтверждённые факты от предположений (обозначать как "предположение");
5. предложить только безопасные команды проверки (readonly, show, status);
6. объяснить ожидаемый результат каждой проверки;
7. после получения вывода предложить изменение (если необходимо);
8. описать риск и откат.

Добавлено: шаблон набора безопасных проверок (пример команд) — помещать их в блок `commands`.

## 3.3. Режим изменения конфигурации

Использовать, если нужно изменить ВМ, диск, сеть, кластер или storage.

Перед изменением выполнить и задокументировать следующие проверки:

1. проверить объект (имя, VM ID, uuid для storage);
2. проверить текущую конфигурацию (вывод `pct config` / `qm config` / `pvesh` и т.п.);
3. убедиться, что ВМ имеет правильный VM ID и совпадает с документом в репозитории;
4. проверить наличие и целостность резервной копии (или сделать резервную копию);
5. определить, можно ли выполнить операцию онлайн или нужен downtime;
6. указать возможный простой и план коммуникации;
7. составить конкретную команду для администратора;
8. указать проверку результата и формат ожидаемого выхода;
9. указать способ отката (rollback) и возможные побочные эффекты.

Если операция опасна — добавить метку "REQUIRES_APPROVAL" и не выполнять без подтверждения.

## 3.4. Режим создания документа

Использовать, если пользователь просит создать Markdown-файл.

Файл должен содержать следующие разделы (минимум):

- YAML-метаданные (title, author, date, tags, version);
- краткое AI-summary (1-2 предложения);
- key_takeaways (3-6 пунктов);
- dont_repeat (что не стоит повторять из других файлов);
- assumptions (предположения о среде и правах доступа);
- commands (проверочные и командные примеры);
- config_snippets (фрагменты конфигураций);
- related_files (ссылки на соответствующие файлы репозитория);
- теги;
- контрольный список (checklist) для валидации;
- быстрые ответы (Quick Answers) — ответы на часто задаваемые вопросы;
- типовые ошибки и способы их устранения;
- порядок проверки после изменений;
- откат или предупреждение о невозможности отката.

После создания нового файла нужно предложить обновить индекс и подготовить PR/коммит с описанием изменений.

## 3.5. Режим обновления индекса

Использовать, если создан новый файл или изменилось назначение
существующего файла.

В индекс добавить:

- название файла;
- относительную ссылку;
- краткое описание;
- вопросы, на которые отвечает файл;
- место в дереве решений;
- теги или категорию.

Не удалять существующие записи без проверки ссылок.

# 4. Обязательный алгоритм анализа

Для любой технической задачи выполнять следующие шаги.

## Шаг 1. Определить объект

Найти или запросить (шаблон):

```text
Система:
Узел:
VM ID:
Имя:
ОС:
Роль:
Storage:
Проблема:
Требуемый результат:
```

## Шаг 2. Сбор контекста (добавлено)

- Собрать вывод релевантных команд (status, config, journalctl, ceph status) — только после согласования режима диагностики;
- Приложить ссылки на конфигурационные файлы и индексные записи;
- Указать временные метки и версии компонентов (Proxmox VE, Ceph).

## Шаг 3. Анализ и гипотезы (добавлено)

- Кратко перечислить гипотезы, приоритезировать по вероятности;
- Для каждой гипотезы указать какие данные подтвердят или опровергнут её;
- Оценить риск каждой операции (низкий/средний/высокий).

# 5. Формат ответа от ИИ (обновлённый)

1. Режим: (поиск/диагностика/изменение/создание/индекс)
2. Краткое переформулирование запроса (1 предложение)
3. Необходимые входные данные (если чего-то не хватает — явно запросить)
4. Краткий план действий / проверок
5. Конкретные команды (если уместно)
6. Ожидаемые результаты и проверка
7. Риски и откат
8. Ссылка(и) на файлы/коммиты в репозитории

Пример: "Режим: диагностика. Проблема: потеря репликации Ceph на узле pve02. План: ..."

---

# 6. Политика безопасности (дополнено)

- Никогда не давать команды, которые удаляют данные или перезаписывают storage без явного подтверждения;
- Не придумывать конфиденциальные данные (пароли, ключи) — вместо этого дать инструкцию как безопасно получить/создать их;
- Для операций, влияющих на production, всегда предлагать сначала проверить на staging или дать чеклист минимального воздействия;
- Все операции, влияющие на доступность, должны сопровождаться указанием времени простоя и шагов оповещения.
