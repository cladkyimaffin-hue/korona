# AI-INSTRUCTIONS.md

## Статус документа

Этот файл содержит обязательные инструкции для искусственного интеллекта,
работающего с репозиторием инфраструктурной документации.

Инструкции распространяются на:

- ответы по документации;
- диагностику Proxmox;
- работу с виртуальными машинами;
- работу с Ceph;
- работу с Windows Server;
- работу с шаблонами и клонами;
- работу с сетями;
- работу с резервными копиями;
- создание и изменение Markdown-файлов;
- обновление индексов;
- подготовку команд для администратора.

ИИ должен считать эти правила обязательными.

# 1. Приоритет правил

Использовать следующие уровни приоритета при принятии решений (в порядке убывания важности):

1. явно сформулированное требование пользователя;
2. текущая конфигурация и свежий вывод команд;
3. профильная документация конкретной системы или ВМ;
4. `Proxmox/INDEX.md`;
5. `AI-README.md`;
6. остальные документы репозитория;
7. официальная документация Proxmox, Microsoft, Ceph или другого поставщика;
8. общие знания ИИ.

Если пользователь просит действие, нарушающее безопасность production, ИИ должен предупредить о риске и предложить безопасную процедуру. Если пользователь требует выполнить опасную операцию без проверки, ИИ не должен молча соглашаться — требовать явного подтверждения человека-оператора (см. секцию "Подтверждение опасных операций").

---

# 2. Главная задача

Главная задача ИИ — дать точный, короткий, проверяемый и безопасный ответ.

ИИ не должен:
- демонстрировать знания без практической пользы;
- повторять весь репозиторий;
- предлагать несколько десятков вариантов без необходимости;
- скрывать неизвестные параметры;
- выдавать предположение за факт;
- запускать опасную процедуру без подтверждения;
- менять несвязанные документы;
- удалять исторические данные без запроса;
- придумывать IP, пароли, VM ID или номера разделов.

Дополнение (важно):
- Никогда не вставлять реальные пароли, приватные SSH-ключи, секреты или чувствительные данные в ответы или рекомендации. Всегда предлагать placeholder (e.g., <REDACTED>) и направление, где безопасно хранить секрет (Vault, секретный менеджер).
- При необходимости работы с секретами — рекомендовать безопасный workflow (vault lookup, привязка роли, временный ключ).

# 3. Режимы работы

Перед ответом определить режим задачи. Если невозможно однозначно определить режим — спросить уточнение.

## 3.1. Режим поиска ответа

Использовать, если пользователь спрашивает:
- где находится информация;
- как настроена ВМ;
- какой используется storage;
- какой размер диска;
- зависит ли клон от шаблона;
- какая команда уже применялась.

Порядок:
1. определить ключевые слова;
2. открыть `Proxmox/INDEX.md`;
3. выбрать профильный файл;
4. прочитать YAML-контекст;
5. проверить `Quick Answers`;
6. дать краткий ответ;
7. указать источник в репозитории (файл + путь + строки).

Пример выхода: одно-два предложения + команда для проверки + ссылка на файл(ы).

## 3.2. Режим диагностики

Использовать, если пользователь сообщает об ошибке.

Порядок:
1. переформулировать проблему одним предложением;
2. определить систему и объект;
3. указать наиболее вероятную причину;
4. отделить подтверждённые факты от предположений;
5. предложить только безопасные команды проверки (см. "Примеры безопасных диагностических команд");
6. объяснить ожидаемый результат;
7. после получения вывода предложить изменение;
8. описать риск и откат.

Примеры безопасных команд (не выполнять без подтверждения оператора; приводятся как шаблон):
- pveversion --verbose
- qm status <VMID> || pct status <CTID>
- qm config <VMID>
- lsblk /dev/<device>
- pvesh get /nodes/<node>/storage/<storage>/status
Для каждой команды указывать ожидаемый формат вывода и что в нём искать.

## 3.3. Режим изменения конфигурации

Использовать, если нужно изменить ВМ, диск, сеть, кластер или storage.

Перед изменением:
1. проверить объект;
2. проверить текущую конфигурацию;
3. убедиться, что ВМ имеет правильный VM ID;
4. проверить резервную копию;
5. определить, можно ли выполнить операцию онлайн;
6. указать возможный простой;
7. указать команду;
8. указать проверку результата;
9. указать способ отката.

Обязательное требование: для любых операций, влекущих потерю данных или простой — требовать явного подтверждения оператора (см. шаблон подтверждения ниже). Для операций, которые можно выполнять только в maintenance window — указывать это.

## 3.4. Режим создания документа

Использовать, если пользователь просит создать Markdown-файл.

Файл должен содержать:
- YAML-метаданные;
- краткое AI-summary;
- key_takeaways;
- dont_repeat;
- assumptions;
- commands;
- config_snippets;
- related_files;
- теги;
- контрольный список;
- быстрые ответы;
- типовые ошибки;
- порядок проверки;
- откат или предупреждение о невозможности отката.

После создания нового файла нужно предложить обновить индекс.

Пример шаблона YAML-метаданных (обязателен при создании новых файлов):
---
title: "Короткое название"
description: "Краткое описание содержания файла"
author: "Имя ответственного"
date: "YYYY-MM-DD"
version: "1.0"
tags: [proxmox, vm, ceph]
related: ["Proxmox/INDEX.md"]
review_required: true
---

## 3.5. Режим обновления индекса

Использовать, если создан новый файл или изменилось назначение существующего файла.

В индекс добавить:
- название файла;
- относительную ссылку;
- краткое описание;
- вопросы, на которые отвечает файл;
- место в дереве решений;
- теги или категорию.

Не удалять существующие записи без проверки ссылок.

# 5. Подтверждение опасных операций (обязательное)

Любая команда, которая:
- удаляет VM/диск/хранилище,
- форматирует разделы,
- вносит изменения в Ceph/cluster config,
- выполняет restore в production,

должна сопровождаться:
1) одобрением ответственного оператора (живой человек) — прямое «yes»/«подтверждаю» в чате с указанием имени/роли и времени; и
2) кратким чек-листом перед выполнением (backup, maintenance window, impact, rollback plan).

Шаблон подтверждения (copy/paste):
- Описание операции:
- Ожидаемая продолжительность:
- Impact (кто пострадает):
- Backup: [есть|нет] — если есть, указать путь/ID:
- Rollback steps:
- Подтверждаю (Имя, роль, время): ___________________

ИИ должен вставить готовую команду только после получения подтверждения.

# 8. Шаблоны и примеры

Пример minimal-check перед изменением:
- Проверить конфигурацию: `qm config <VMID>`
- Проверить состояние node: `pvecm status` / `systemctl status pve-cluster`
- Снять snapshot/backup: `vzdump <VMID> --mode snapshot --storage <storage>`
- Проверка после: `qm status <VMID>`

Пример YAML-метаданных для нового документа (повторно, как шаблон):
