# Тормоза 1С (ВМ 2001 Srv1c): public_network и линк pve02 — ЧАСТИЧНО ПРОВЕРЕНО

## Краткий ответ

- Клиентский трафик Ceph от ВМ 2001 идёт через `public_network`. На обоих узлах он проходит через физический порт `nic2` (Lom3) на скорости 1 Гбит/с. **VERIFIED.**
- Показание 10000 Mb/s у `vmbr0` на pve01 — скорость виртуального моста, а не физического линка. **VERIFIED** (опровергнуто, см. ниже).
- Что именно вызывает тормоза 1С, не доказано. **UNKNOWN.** Узкий линк 1 Гбит/с — рабочая гипотеза. **INFERRED.**

## Симптом (со слов администратора)

- Тормоза 1С на ВМ 2001 (Srv1c).
- Диски Srv1c находятся на Ceph (пул `ceph-fast`, см. AI-environment facts).
- Со слов администратора, часть соединений с OSD на pve02 идёт через `192.168.202.179` по порту 1 Гбит/с.

## Проверено командами (VERIFIED, 2026-10-15)

- pve01: `vmbr0` — `192.168.202.121/22`. `nic2` входит в `vmbr0`. `ethtool nic2`: `1000Mb/s`, link detected.
- pve02: `vmbr0` — `192.168.202.179/22`. `nic2` входит в `vmbr0`. `ethtool nic2`: `1000Mb/s`, link detected.
- pve02: `nic0` — `10.10.11.2/24`, `10000Mb/s`, в `vmbr0` не входит.
- pve01: `nic0` — `10.10.11.1/24`, `10000Mb/s`, MTU 9000, в `vmbr0` не входит.
- pve01 и pve02: `nic1` и `nic3` без линка (Speed Unknown).
- pve01 и pve02: `nic4` и `nic5` без линка, `bond0` DOWN.
- pve01: интерфейсы ВМ 2001 (`tap2001i0` → `fwbr2001i0` → `fwpr2001p0`) подключены к `vmbr0`, поэтому трафик ВМ уходит через `nic2` (1 Гбит/с).
- pve01, `ss -tnp`: процессы `kvm` (PID 60904, 61183, 61372) имеют ESTAB-соединения с `192.168.202.179` на порты 6800, 6802, 6804, 6806 (OSD).
- pve01 и pve02, `ss -tnp`: процессы `ceph-osd` имеют ESTAB-соединения между `192.168.202.121` и `192.168.202.179`.
- `/etc/pve/qemu-server/2001.conf` содержит `name: Srv1c`. Расхождение с именем `win-1c-app-01` описано в `00_Meta/CONFLICTS.md`.

## Опровергнуто

- Гипотеза «pve01 работает на 10G на public_network» опровергнута. Значение 10000 Mb/s, которое показывал `ethtool vmbr0`, относилось к виртуальному интерфейсу моста. Физический `nic2` на pve01 работает на 1 Гбит/с.
- Схема администратора (2026-10-12) показывала `vmbr0` pve01 как 10 Гбит/с. Схема требует обновления в этой части (см. `CONFLICTS.md`, RESOLVED).

## Гипотезы (INFERRED)

- Линк 1 Гбит/с на `public_network` ограничивает пропускную способность клиентского трафика Ceph обоих узлов. Теоретический потолок — около 110–120 МБ/с на весь трафик узла. Не измерено.
- Тормоза 1С связаны с задержками клиентского трафика Ceph. Не подтверждено.

## Не известно (UNKNOWN)

- Какие OSD и на каком узле держат данные Srv1c. `ceph osd map` не выполнялся.
- Какой PID `kvm` соответствует ВМ 2001. Сейчас PID 60904, 61183, 61372 не сопоставлены с VMID.
- Фактическая задержка и пропускная способность Srv1c к OSD.
- Причина состояния `SYN-SENT` у `corosync-qdevice` на pve02 (соединение `192.168.202.179:54446` → `192.168.200.84:5403`).

## План проверки (только чтение)

1. Определить образ диска ВМ 2001 и его объекты:
```bash
   qm config 2001 | grep scsi0
   rbd ls -p ceph-fast
   rbd info ceph-fast/<имя_образа>
```
2. Найти OSD, на которых лежат объекты образа (из `block_name_prefix` в выводе `rbd info`):
```bash
   ceph osd map ceph-fast <имя_объекта>
```
   Повторить для нескольких объектов, чтобы оценить распределение по узлам.
3. Замерить задержку и пропускную способность по образу во время обычной работы 1С:
```bash
   rbd perf image iostat ceph-fast
```
4. Сопоставить PID `kvm` с VMID:
```bash
   ps -o pid,args -p 60904,61183,61372 | grep -o -- '-id [0-9]*'
```
5. Разобрать `SYN-SENT` у corosync-qdevice на pve02:
```bash
   corosync-qdevice-tool -s
   nc -vz 192.168.200.84 5403
   journalctl -u corosync-qdevice --since "-1 day"
```
6. Только после шагов 1–3: решить, нужен ли 10G для `public_network`. Если да, проверить свободный порт (`nic1` или `nic3`), тип разъёма и порт коммутатора. Любое изменение сети планировать с откатом (см. ограничения ниже).

## Критерии решения

- Если задержка записи и чтения по образу 2001 высокая, а OSD для данных находятся на pve02, гипотеза о линке 1 Гбит/с подтверждается. Далее рассматривать 10G для `public_network`.
- Если задержка низкая, линк не является причиной. Искать причину в настройках SQL, гостевой ОС, клиентской стороне или нагрузке CPU на pve01.

## Ограничения и риски

- Изменение `public_network` на рабочем кластере без плана отката и доступа через консоль или IPMI не выполнять. В кластере два монитора Ceph, при потере связи с `mon.pve02` кворум Ceph теряется, запись блокируется.
- Перенос ВМ: вопрос о миграции закрыт администратором 2026-10-15. Основание закрытия в документе не зафиксировано, решение уточнить. См. `PROXMOX-VM-MIGRATION-ISOLATION-2026-001`.

## Конфликты

- Скорость `vmbr0` на pve01: схема (10 Гбит/с) против команд (1 Гбит/с на `nic2`). Решено командами, см. `00_Meta/CONFLICTS.md`.
- Имя ВМ 2001: `Srv1c` против `win-1c-app-01`. Открыто, см. `00_Meta/CONFLICTS.md`.
