# ⚠️ Задержки записи Ceph через bond0 — расследование не завершено

**Статус: открыто, реальная диагностика ещё не начата.** Вся сессия ушла
на поиск IP управления коммутатора и закончилась без результата — ни
одной команды `ethtool -S` с реальным выводом в этой сессии нет.

## Симптом (со слов администратора)
- Отдельные операции записи Ceph ждут подтверждения от второго узла **165-204 мс**.
- На сети репликации (`10.10.10.0/24`, `bond0`, `pve01`↔`pve02`) наблюдаются повторные передачи TCP (retransmissions).
- Неисправность сети пока не доказана — требуется сравнение и проверка пути.

## ⚠️ Важно: диагностика в этой сессии шла по неверной посылке
Сторонний ИИ (не в этом чате — читал репозиторий через GitHub-ссылку на
`AI-INSTRUCTIONS.md`) сделал вывод, что сеть работает на **1 Гбит/с**, со
ссылкой на документ `NETWORK-BOND0-CEPH-ACTIVEBACKUP-2026-001` в
состоянии **до** исправления этой миграции 2026-09-22 (см. тот документ,
раздел «Апгрейд до 10G»). **Реально сеть уже на 10 Гбит/с** — модули
1000BASE-SX заменены на 10GBASE-SR.

Из-за этого вся первая часть сессии (рекомендация заменить модули на
10GBASE-SR, проверка типа кабеля OM3/OM4) — **неактуальна, уже сделано**.
Это не ошибка сессии как таковая — это прямое следствие того, что
исходный документ не был обновлён вовремя, что мы сознательно отложили
как компромисс раньше (см. переписку от 2026-09-14). **Стоимость этого
компромисса — конкретно эта потраченная впустую часть диагностики.**

## Что реально было сделано (read-only, безопасно)
1. Прочитаны `AI-INSTRUCTIONS.md` и связанные документы через GitHub — источник неверной посылки о скорости.
2. Подготовлен (но не выполнен администратором с реальным выводом) план: `ethtool nic4/nic5`, `ethtool -S nic4/nic5 | grep -iE 'error|drop|crc|miss|over|fifo'`.
3. Попытка найти IP управления коммутатора TP-Link TL-SX3008F — **не увенчалась успехом за всю сессию**:
   - `nmap`/ARP-сканирование нескольких подсетей — не нашло.
   - Пакетный sniffer на MikroTik (роутере) показал: TP-Link (`F4:1E:57:E9:46:AF`) шлёт только L2-трафик (LLDP, STP BPDU) — **не имеет назначенного IP**, поэтому не отвечает на ARP/ping/nmap.
   - Обнаружено устройство `192.168.202.202`, рассылающее Omada Discovery broadcast (порт UDP 29810) — вероятно, Omada Controller, через который TP-Link (поддерживает управление Omada) можно найти/принять — **не проверено до конца**, доступ к Omada Controller не подтверждён.
4. **Обнаружен факт, не задокументированный ранее**: между MikroTik-роутером (`CRS112-8P-4S`, судя по промпту консоли — не тот же CRS326, что документирован в `MikroTik/AI-environment_facts-korona-mikrotik.md`!) и TP-Link есть прямое соединение через порт `sfp9` в `bridge1`. **Требует сверки** — возможно, в инфраструктуре два разных MikroTik-устройства, а не одно. См. соответствующую пометку в `MikroTik/AI-environment_facts-korona-mikrotik.md`.

## Что нужно сделать (порядок важен — сначала то, что не требует доступа к коммутатору)

1. **Сначала, без коммутатора вообще:**
   ```bash
   # На pve01 и pve02
   ethtool nic4 | grep -E "Speed|Link detected"
   ethtool nic5 | grep -E "Speed|Link detected"
   ethtool -S nic4 | grep -iE 'error|drop|crc|miss|over|fifo'
   ethtool -S nic5 | grep -iE 'error|drop|crc|miss|over|fifo'
   ```
   Присылать реальный вывод, не пересказ — счётчики важны дословно.

2. **Проверить реальную сетевую задержку и TCP-ретрансмиты напрямую:**
   ```bash
   ping -c 100 -i 0.2 10.10.10.2   # с pve01
   # + tcpdump/ss для подтверждения ретрансмитов во время нагрузки Ceph
   ```

3. **Только если пп. 1-2 не объяснили причину — тогда доступ к коммутатору:**
   - Уточнить, есть ли доступ к Omada Controller (`192.168.202.202`) — логин/пароль.
   - Если нет — консольный кабель к TP-Link напрямую (быстрее, чем дальнейший сетевой поиск).
   - На коммутаторе смотреть счётчики порта (errors, drops, output queue) для портов, к которым подключены `nic4`/`nic5` обоих серверов — точный физический маппинг портов коммутатора **тоже не задокументирован**, установить его заодно.

## Открытые вопросы
- Физический маппинг: какие именно порты TP-Link соответствуют `nic4`/`nic5` на `pve01` и `pve02`?
- Есть ли доступ к Omada Controller (`192.168.202.202`)?
- Одно или два MikroTik-устройства в инфраструктуре (`CRS326-24G-2S+` из основного аудита vs `CRS112-8P-4S`, увиденный в этой сессии)?
- Собственно причина задержек 165-204 мс — гипотеза (переполнение буферов при 1G) была неверной с самого начала, новая гипотеза ещё не сформулирована.
