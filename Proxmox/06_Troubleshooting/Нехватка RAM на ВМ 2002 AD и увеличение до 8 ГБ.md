# Нехватка RAM на ВМ 2002 AD и увеличение до 8 ГБ

## Краткий ответ

- ВМ 2002 (`AD`, третий контроллер домена `krnn.ru`) работает на `pve01`. Ей было выделено `memory: 4096`, `balloon: 1024`. **VERIFIED** (`qm config 2002`, 2026-10-25).
- В конфигурации значения изменены на `memory: 8192`, `balloon: 8192`. **VERIFIED** (`qm config 2002`, 2026-10-25).
- Перезагрузка из Windows новую память не применила: `info balloon` показал `max_mem=4096`. **VERIFIED.** Для применения нужна полная остановка и запуск ВМ.
- Администратор выполнил остановку и сообщил: «настройки применены, вопрос закрыт». Вывода `info balloon` после запуска и данных из Windows в источнике нет, поэтому применение подтверждено **только словами администратора**.
- Почему память доходила до 90% и выше, не доказано. Версия «для этой ВМ 4 ГиБ мало» — **INFERRED**.

## 1. Симптомы

- Оповещение мониторинга: использование памяти ВМ 2002 выше 90% (в чате приведено ~91.95%, длительность 28m 31s). Текст оповещения целиком в источнике не сохранён; система мониторинга в чате не названа (**UNKNOWN**).
- В тексте оповещения ВМ значилась как `[pve01:AD (qemu2002)]` на хосте `pve02`. По `pvesh get /cluster/resources` ВМ находится на `pve01` (**VERIFIED**). Откуда взялась подпись `pve02`, не выяснено (**UNKNOWN**).
- `pvesh`, строка `qemu/2002`: `running`, узел `pve01`, uptime `1w 6d 14h`. В строке без заголовков столбцов есть значения `4.00 GiB` и `3.70 GiB`; по порядку столбцов это максимум и текущее использование памяти — 92.5% (**INFERRED**: заголовки в выводе не приведены).
- Для сравнения: в `PROXMOX-VM-MEMORY-BALLOON-2026-001` внутри Windows было занято 2.43 из 3.93 ГБ (61.84%). Что изменилось с тех пор, не установлено (**UNKNOWN**).

## 2. Проверено и отвергнуто

| Гипотеза | Статус | Комментарий |

| Включить `hotplug: memory`, чтобы добавить память без остановки | ❌ Не применялось | У ВМ `numa: 0`, параметр `hotplug` не задан. Для hotplug памяти нужен `numa: 1`. Администратор сообщил, что на другой, Linux-ВМ включил hotplug при `numa: 0`, и она не загрузилась (**VERIFIED** опытом администратора; VMID и вывод ошибки не приведены). Выбрана полная остановка и запуск |

| Нехватка выделенной RAM — причина алерта | ⚠️ Не доказана | Согласуется с наблюдениями (раздел 3), но замеров внутри Windows в источнике нет |

## 3. Диагностика

Все команды выполнялись на `pve01`, 2026-10-25.

```bash
# [R] Размещение и состояние ВМ
pvesh get /cluster/resources --type vm | grep 2002
# → qemu/2002, running, узел pve01, uptime 1w 6d 14h; 4.00 GiB и 3.70 GiB (трактовка столбцов — INFERRED)

# [R] Конфигурация до изменения
qm config 2002
# → memory: 4096, balloon: 1024, cores: 2, sockets: 1, numa: 0, machine: pc-q35-11.0+pve2,
#   bios: ovmf, agent: 1, onboot: 1, startup: order=1,up=120; параметра hotplug нет
```

Конфигурация после изменения (`qm config 2002`, команда `qm set` в чате приведена как предложенная, вывод её запуска не показан):

```text
memory: 8192
balloon: 8192
numa: 0
```

Параметра `hotplug` в выводе по-прежнему нет.

После перезагрузки из Windows, до остановки ВМ:

```bash
# [R] Реальные параметры процесса QEMU
qm monitor 2002
# qm> info balloon
# balloon: actual=1448 max_mem=4096 total_mem=4028 free_mem=385 mem_swapped_in=7351676928
#   mem_swapped_out=3319336960 major_page_faults=278129 minor_page_faults=5462014
# qm> quit
```

Разбор вывода:

- `max_mem=4096` — процесс QEMU работал со старым объёмом, несмотря на `memory: 8192` в конфигурации. **VERIFIED.**
- `actual=1448` при `max_mem=4096` — балун на момент замера ограничил гостя примерно 1.4 ГиБ (**INFERRED**: смысл поля `actual` взят из общего знания о `info balloon`, в документации репозитория не описан). Что вызвало уменьшение, не установлено (**UNKNOWN**); минимум задавал `balloon: 1024`.
- `free_mem=385` МиБ при `total_mem=4028` МиБ. **VERIFIED** (вывод команды).
- `mem_swapped_out=3319336960` байт (≈3.09 ГиБ) и `mem_swapped_in=7351676928` байт (≈6.85 ГиБ) — накопленные счётчики подкачки гостя. **VERIFIED** как значения вывода; вывод о влиянии на работу контроллера домена не делался.
- Время `last_update=1792956950` соответствует 2026-10-25 19:35:50 UTC.

Команда `qm status 2002 --verbose | grep -i memory` вернула только `pressurememoryfull: 0` и `pressurememorysome: 0` (показатели `pressure` памяти процесса ВМ на хосте нулевые). **VERIFIED** как значения вывода.

## 4. Корневая причина

**Не доказана.** Рабочая версия (**INFERRED**): гостю Windows Server 2025 с ролями AD DS и DNS было выделено 4 ГиБ, из которых балун мог отнять часть, а гость использовал подкачку. Замеров внутри Windows (диспетчер задач, `Get-CimInstance Win32_OperatingSystem`, процессы) в источнике нет, поэтому утверждение ассистента из чата «служба AD кэширует данные и занимает всю память» остаётся предположением.

## 5. Решение

Решение принято администратором в ходе диалога.

1. **Изменить конфигурацию** (идемпотентно, можно повторять):

   ```bash
   # [W]
   qm set 2002 -memory 8192 -balloon 8192
   ```

   `balloon` равен `memory`, то есть память ВМ балунингом не уменьшается (**INFERRED**: из описания минимума памяти в Proxmox, на ВМ 2002 после изменения не проверялось). Откат: `qm set 2002 -memory 4096 -balloon 1024`, затем снова полная остановка и запуск.
2. **Перезагрузка из Windows не помогла** (раздел 3).
3. **Hotplug памяти не включали:** `numa: 0`; при включении `hotplug: memory` без `numa: 1` Proxmox отказывается запускать ВМ (см. раздел 6).
4. **Полная остановка и запуск ВМ:**

   ```bash
   # [W] Остановка контроллера домена прерывает его службы на время простоя
   qm shutdown 2002
   qm status 2002
   # ожидается status: stopped; затем запуск ВМ
   ```

   В источнике команда запуска отдельно не показана; администратор сообщил: «команда выполнена, настройки применены — вопрос закрыт».

На время остановки аутентификацию могут обслуживать `DC.krnn.ru` и `ANDQ.krnn.ru` (адреса — в `AI-environment_facts-korona-proxmox.md`). Их доступность в окно остановки в источнике не проверялась (**INFERRED**).

Запас по памяти хоста: по `AI-environment_facts-korona-proxmox.md` на `pve01` занято около 200 из 250 GiB (со слов администратора). Выделение ВМ 2002 увеличилось на 4 GiB и стало фиксированным (`balloon` равен `memory`). Актуальный замер памяти `pve01` не проводился (**UNKNOWN**). Вопрос размещения ВМ — в `PROXMOX-VM-MIGRATION-ISOLATION-2026-001`.

## 6. ⛔ Don't repeat

- Перезагрузка из Windows не перезапускает процесс QEMU: новая `memory` не применяется. Сверять `max_mem` в `info balloon`.
- `qm config` показывает записанную конфигурацию, а не то, что получил запущенный процесс QEMU.
- Hotplug памяти требует NUMA: порядок — сначала `numa: 1`, затем `hotplug: memory`. Подтверждения: (1) опыт администратора, 2026-10-25: на Linux-ВМ включён hotplug при `numa: 0`, ВМ не загрузилась (**VERIFIED** его словами; VMID, версия PVE и текст ошибки не приведены); (2) страница `Hotplug (qemu disk,nic,cpu,memory)` на `pve.proxmox.com/wiki`: «You need to enable NUMA and hotplug to get it working: numa: 1 hotplug: memory,...»; (3) темы на `forum.proxmox.com` об ошибке `NUMA needs to be enabled for memory hotplug` (PVE 6.3 и 7.4) и об ошибке `memory size (8000) must be aligned to 512 for hotplugging` — при включённом hotplug объём памяти должен быть кратен 512 МиБ. Актуальное руководство администратора PVE 9.x не открывалось, соответствие версии 9.2.11 по документации не проверено (**INFERRED**, подтверждается опытом администратора). Для Linux-гостя по wiki нужны модули `acpiphp`, `pci_hotplug` и параметр ядра `memhp_default_state=online` либо правило udev. Проверено 2026-10-25.
- Перед включением hotplug на любой ВМ сначала проверить `qm config <VMID>`: при `numa: 0` hotplug памяти не включать, объём памяти должен быть кратен 512 МиБ.
- Не принимать итоговые фразы чата («алерт снят», «VM 2002 успешно работает с 8 ГБ RAM») за факт: вывода команд после запуска нет.
