# Диагностика: оптические SFP-модули 1000BASE-SX вместо ожидаемых SFP+ RJ45

## 1. Симптомы
При сетевом аудите двух узлов Proxmox (`pve01`, `pve02`) обнаружено:
- Активен только один интерфейс на узел (`nic2`, встроенный GE RJ45, 1 Гбит/с) — используется под management (`vmbr0`).
- Остальные 5 интерфейсов (`nic0`, `nic1`, `nic3`, `nic4`, `nic5`), физически соответствующие SFP+ портам двух карт Intel X710 (`i40e`), в состоянии `DOWN`.
- Пользователь ожидал, что в порты вставлены **медные SFP+ RJ45** модули на 10 Гбит/с.

## 2. Отвергнутые гипотезы
- **«Коммутатор не перепрошит порты под SFP+»** — отклонено после проверки: коммутатор TP-Link SX3008F универсальный, принимает и SFP, и SFP+ в любой порт; индикаторы горели оранжевым (= 1 Гбит/с у него же), что уже указывало не на прошивку, а на согласованную скорость модуля.
- **«Проблема в самих портах/картах»** — отклонено: `ethtool -m` показал корректно определяемые модули на `nic4`/`nic5`, просто не того типа, что ожидался.

## 3. Диагностика

Проверка состояния и скорости всех физических интерфейсов:
```bash
for iface in $(ls /sys/class/net/ | grep -v '^lo$'); do
    echo "=== Интерфейс: $iface ==="
    ip link show "$iface" | grep -oP 'state \K\w+'
    ethtool "$iface" 2>/dev/null | grep -E "Speed:|Link detected:"
done
```

Идентификация драйвера/карты:
```bash
ethtool -i nic4 2>/dev/null | grep -E 'driver:|bus-info:'
# driver: i40e — подтверждает карты Intel X710
```

**Ключевая команда — определение реального типа установленного модуля:**
```bash
for iface in nic0 nic1 nic3 nic4 nic5; do
    echo "=== $iface ==="
    ethtool -m $iface 2>/dev/null | head -20
done
```
Результат на `nic4`/`nic5`: `Transceiver type: Ethernet: 1000BASE-SX`, `Connector: 0x07 (LC)`, `Vendor PN: FTLX8571D3BCVIT1` (pve01) / `AFBR-709DMZ-IN2` (pve02) — это **оптические** модули на многомодовое волокно, 850 нм, а не медные RJ45.

Проверка истории линка:
```bash
dmesg | grep -iE 'nic4|nic5|i40e|link' | tail -30
```
Показала на `nic0`/`nic1`/`nic3`: `Module EEPROM memory read not supported. Please update the NVM image.` — устаревшая прошивка карты не может прочитать EEPROM этих модулей. На `nic4`/`nic5`: линк периодически поднимается и падает на `1000 Mbps Full Duplex`.

## 4. Корневая причина

Две отдельные причины, обе подтверждены:
1. **Несоответствие ожиданий физике**: в порты вставлены оптические SFP-модули 1000BASE-SX (LC, многомод), а не медные SFP+ RJ45. Максимум для этого типа модуля — 1 Гбит/с, что и есть максимум скорости независимо от порта или коммутатора.
2. **Устаревшая прошивка (NVM)** сетевой карты на портах `nic0`/`nic1`/`nic3` не позволяет прочитать EEPROM установленных туда модулей — отдельная, не связанная с (1) проблема.

## 5. Решение
Согласовано с администратором: не решать проблему типа модулей (замена на реальные 10G SFP+ RJ45/оптику под 10G) и прошивку NVM в моменте — принять текущее ограничение и использовать `nic4`+`nic5` на скорости 1 Гбит/с для сети Ceph (см. `NETWORK-BOND0-CEPH-ACTIVEBACKUP-2026-001`).

## 6. ⛔ Don't repeat
- Не принимать на веру заявленный пользователем тип трансивера — проверять `ethtool -m`.
- Не ожидать 10G от 1000BASE-SX модулей.
- Не диагностировать интерфейс только по `Link detected: no` без `dmesg` — возможна нестабильность, а не полный отказ.

## 7. Проверка результата
```bash
ethtool nic4 | grep -E "Speed|Link"
ethtool nic5 | grep -E "Speed|Link"
```
Ожидаемо: `Speed: 1000Mb/s`, `Link detected: yes` (при физически подключенном и рабочем оптическом патч-корде).

## 8. Наименование интерфейсов — расхождение со справочником портов
Этот документ и `HARDWARE-HUAWEI-2288H-PORTMAP-2026-001` (карта портов того же сервера)
используют разные системы имён: здесь — `nic0`...`nic5` (персистентные имена,
присвоенные udev на этом конкретном узле), там — `LOM1-4`/`SLOT3 Порт 1-2`
(имена по документации Huawei). Это не противоречие в фактах, а два разных
слоя именования одного и того же физического оборудования — при сопоставлении
портов между документами ориентироваться на PCI-адрес (`0000:19:00.x` /
`0000:b3:00.x`), а не на совпадение текстовых имён.
