# Клонирование шаблона в производственную ВМ (на примере 1С:ERP)

## Что настраивается и зачем
Разворачивание конкретной производственной роли (в этом случае — сервер
приложений 1С:ERP) из готового обобщённого шаблона Windows Server 2022
(`PROXMOX-WINSRV2022-TEMPLATE-2026-001`), с ресурсами, подобранными под
роль, а не под шаблон.

## Предварительные условия
- [ ] Шаблон выключен и обобщён (Sysprep/Generalize выполнен) — см. документ шаблона.
- [ ] Хранилище `ceph-fast` доступно на целевом узле.

## Шаги

**1. Проверить шаблон перед клонированием:**
```bash
qm status 2000
qm config 2000
```

**2. Полное клонирование (обязательно `--full`, не linked):**
```bash
qm clone 2000 2001 --name win-1c-app-01 --full --storage ceph-fast
```
`--storage` здесь — это флаг именно `qm clone` (валиден), явно указывает
целевое хранилище, чтобы исключить ошибку маршрутизации в кластере — не
путать с `qm resize`, где этого флага нет (см. ниже).

**3. Увеличить диск под роль (было 100 ГБ → нужно 1 ТБ):**
```bash
qm resize 2001 scsi0 +924G
```
⚠️ **Без `--storage`** — команда его не поддерживает:
```
qm resize 2001 scsi0 +924G --storage ceph-fast
# → Unknown option: storage
```
Диск уже находится на нужном хранилище (задано на шаге клонирования),
здесь достаточно указать доразмер.

**4. Выделить ресурсы под роль:**
```bash
qm set 2001 --memory 163840   # 160 ГиБ
qm set 2001 --cores 24         # 1 сокет × 24 ядра = 24 vCPU
```

**5. Проверить итоговую конфигурацию перед первым запуском:**
```bash
qm config 2001
```
Ожидаемые ключевые поля: `agent: 1`, `bios: ovmf`, `cores: 24`, `memory:
163840`, `machine: pc-q35-11.0+pve2`, `net0: virtio,bridge=vmbr0`,
`ostype: win11`, `scsi0: ceph-fast:vm-2001-disk-1,size=1T`.

**6. Запустить и отключить установочные ISO:**
```bash
qm start 2001
qm shutdown 2001              # при необходимости
qm set 2001 --delete ide0
qm set 2001 --delete ide2
```

## ⚠️ Известная проблема: расширение диска в Proxmox ≠ расширение раздела C: в Windows

После `qm resize` гипервизор видит диск на 1 ТБ, но **раздел `C:` внутри
Windows не расширяется автоматически**. Причина в структуре разделов,
унаследованной от шаблона:

| № | Тип | Размер |
|---|---|---|
| 1 | System | — |
| 2 | Reserved | 16 MiB |
| 3 | Basic, `C:` | ~99.3 ГиБ |
| **4** | **Recovery** | **~567 МиБ** |
| — | (нераспределённое пространство) | ~924 ГБ |

Recovery-раздел физически расположен **сразу после `C:`**, а свободное
место — **после Recovery**. Windows не может расширить `C:` через занятый
раздел — сначала нужно убрать то, что стоит между `C:` и свободным
пространством.

**Порядок действий внутри гостя (PowerShell, от администратора):**
```powershell
# Сначала посмотреть реальную структуру — НЕ полагаться на номера из этого документа
Get-Disk | Format-Table Number, FriendlyName, Size, PartitionStyle
Get-Partition | Format-Table DiskNumber, PartitionNumber, DriveLetter, Size, Type

# Удалить Recovery-раздел — ТОЛЬКО после того как убедились в его реальном номере
Remove-Partition -DiskNumber 0 -PartitionNumber 4 -Confirm:$false

# Расширить C: на всё освободившееся место
Resize-Partition -DriveLetter C -Size (Get-PartitionSupportedSize -DriveLetter C).SizeMax
```
⚠️ Номер раздела (`4` в этом случае) — не универсальная константа, это
конкретный результат конкретного шаблона. Каждый раз проверять заново
через `Get-Partition`, а не копировать номер из этого документа.

## ⛔ Don't repeat
См. `dont_repeat` во фронтматтере — включая реальную ошибку с `--storage`
в `qm resize`, из-за которой администратор прямо попросил быть внимательнее
(«а то угробим серваки»).

## Проверка результата
- [x] `qm config 2001` — full clone, не зависит от шаблона 2000.
- [x] Диск `scsi0` — 1 ТБ на уровне гипервизора.
- [x] Раздел `C:` внутри Windows расширен до полного размера диска (после удаления Recovery-раздела).
- [x] Ресурсы: **20 vCPU** (1 socket × 20 cores), 160 ГиБ RAM — уточнено 2026-09-17 реальным `qm config 2001`; изначально было выставлено 24 vCPU (см. шаги выше), позже кем-то изменено на 20 — сам факт изменения и его причина в архиве не задокументированы, зафиксировано только итоговое состояние.
- [x] Финальная проверка загрузки ОС и QEMU Guest Agent — подтверждена постфактум: ВМ эксплуатируется в production, `winsat`/AIDA64 тесты изнутри гостя выполнялись успешно (см. раздел «Оптимизация дисковой подсистемы» ниже).

## Оптимизация дисковой подсистемы (2026-09-17)

**Повод:** пользователь сообщил о медленном чтении диска — 300 МБ/с вместо ожидаемого ~1 ГБ/с для NVMe (`ceph-fast`).

**Диагностика показала: реальной проблемы с диском не было** — это важный урок сам по себе:
- `winsat disk -drive C` (блок 64 КБ, многопоточно) → **3333-3624 МБ/с** последовательное чтение, задержки <3 мс — диск уже работал на полной скорости.
- AIDA64 (тот же блок 64 КБ) → в **37 раз ниже** (~90 МБ/с) на тех же настройках.
- Причина расхождения: AIDA64 в этом тесте использовал queue depth = 1 (однопоточно, последовательные запросы без параллелизма), тогда как `winsat` — многопоточно, с реалистичной очередью запросов. Само по себе низкое число в AIDA64 не означает поломку — это особенность методики теста, не реальная деградация.

**Тем не менее применено улучшение** — добавлен `cache=writeback` для `scsi0`:
```bash
qm stop 2001
qm set 2001 --scsi0 ceph-fast:vm-2001-disk-1,cache=writeback,discard=on,iothread=1,size=1T,ssd=1
qm start 2001
```
⚠️ Параметр применяется **только при старте QEMU** — после `qm set` на уже
работающей ВМ требуется её перезагрузка (`qm stop`/`qm start`, не reset),
иначе конфиг в файле обновится, а реально работающий процесс останется на
старом `cache=none`. В этой сессии первая проверка после `qm set` без
перезагрузки ошибочно приняла новый конфиг за уже применённый — только
`journalctl`/фактический рестарт показал, что это не так.

**Результат (подтверждено `winsat` до/после):**

| Метрика | До cache=writeback | После | Изменение |
|---|---|---|---|
| Random 16.0 Read | 431.62 МБ/с | 689.29 МБ/с | +60% |
| Sequential 64.0 Write | 2007.47 МБ/с | 3081.33 МБ/с | +53% |
| Задержка 95% | 0.411 мс | 0.188 мс | -54% |
| Максимальная задержка | 2.439 мс | 0.719 мс | -70% |
| Sequential 64.0 Read | ~3510-3624 МБ/с | ~3510 МБ/с | без изменений (упирается в NVMe, не в кэш) |

**Компромисс, принятый осознанно:** `cache=writeback` означает запись
сначала в кэш QEMU на узле, асинхронный сброс на Ceph позже — при
аварийном отключении узла возможна потеря несброшенных данных. Для этой
production-ВМ 1С риск принят как допустимый, так как Ceph реплицирует
данные (Size=2) независимо от режима кэша QEMU.

### ⛔ Don't repeat (дополнение)
- Не считать однопоточный тест AIDA64 с queue depth=1 представительным для реальной производительности диска на Ceph/NVMe — сверять с многопоточным тестом (`winsat`, `fio` с несколькими jobs) перед тем как чинить несуществующую проблему.
- После `qm set --scsi0 ...cache=writeback` — обязательно перезапустить (`stop`/`start`) ВМ и проверить журналом/фактическим поведением, что новый режим кэша реально активен, а не только присутствует в конфиг-файле.
- Не переносить `cache=writeback` на другие ВМ автоматически «по аналогии» без отдельной оценки риска потери данных при отключении узла для каждой конкретной роли.

### Открытый вопрос
Пользователи сообщали (по состоянию на 2026-09-17) о возможных зависаниях
1С — отдельно от диска (сам диск оказался исправен). Гипотезы для
проверки при следующем обращении: антивирус/Defender сканирует файлы 1С
в реальном времени; схема электропитания Windows не «Высокая
производительность»; `numa: 0` в конфиге ВМ при 20 vCPU/160 GiB (возможно,
стоит `numa: 1`); сетевые задержки клиент↔сервер; блокировки/индексы на
уровне самой базы 1С. Ни одна гипотеза не проверялась в этой сессии.
