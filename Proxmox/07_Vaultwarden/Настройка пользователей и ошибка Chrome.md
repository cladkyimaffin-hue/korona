# ⚠️ Настройка пользователей Vaultwarden — не завершено

**Этот документ описывает незаконченную работу.** Ни один из двух
основных пунктов (настройки регистрации/приглашений, работа расширения
Bitwarden в Chrome) не имеет в исходной переписке финального
подтверждения. Перед использованием — проверить фактическое состояние
`Allow new signups`/`Allow invitations` в `/admin` и работоспособность
расширения в Chrome заново.

## Часть 1: расширение Bitwarden как клиент self-hosted сервера

Официальное браузерное расширение "Bitwarden — Password Manager" по
умолчанию подключается к облачному `bitwarden.com`. Для работы с
собственным Vaultwarden нужно вручную сменить сервер:
1. Настройки расширения → **Аккаунт** (или внизу экрана входа).
2. **Изменить сервер** / "Self-hosted environment".
3. URL: `https://192.168.200.230`.
4. Сохранить и войти под своими учётными данными.

## Часть 2: план настройки регистрации и приглашений — подготовлен, НЕ подтверждён

Контекст: ~10 человек, разные почтовые домены (не единый `@krnn.ru`).

**Подготовленные, но не подтверждённые как сохранённые настройки**
(`/admin → General settings`):
| Параметр | Значение |
|---|---|
| Allow new signups | `false` (выключено — блокирует свободную регистрацию) |
| Allow invitations | `true` (включено — только по приглашениям) |
| Require email verification on signup | `true` |
| Restrict registration to a single domain | **выключено** (домены разные) |

**Проверка после сохранения (не выполнена в этой сессии):** попытка
нажать «Создать аккаунт» на обычной странице входа (не `/admin`) должна
выдавать сообщение об отключённой регистрации.

## Часть 3: «Failed to fetch» в Chrome (в Яндекс.Браузере работало)

**Симптомы:** расширение Bitwarden в Chrome — ошибка `Failed to fetch`
при попытке входа; тот же сервер и та же учётка в Яндекс.Браузере
(Chromium-based) работали без проблем.

**Ход диагностики:**
1. Проверка настройки сервера в расширении — указан верно.
2. Проверка доступности сервера напрямую в Chrome — сертификат
   самоподписанный (`Caddy Local Authority`), принят вручную через
   `thisisunsafe`/«Перейти на сайт (небезопасно)» — расширению это не
   помогло, оно продолжало выдавать ошибку (расширения не наследуют
   ручное исключение сертификата, принятое во вкладке браузера).
3. Проверка SAN сертификата — IP `192.168.200.230` в SAN присутствует (сертификат в целом корректный).
4. Установлен экспортированный сертификат в «Доверенные корневые центры
   сертификации» на клиенте — **не помогло**.
5. Диагностика показала: на клиент был экспортирован **промежуточный**
   сертификат (`Caddy Local Authority - ECC Intermediate`, срок действия
   **12 часов**), а не корневой.

**Корневая причина:** для устойчивого доверия на клиентских машинах
нужно устанавливать именно **корневой** сертификат Caddy, а не
промежуточный — последний истекает за 12 часов и не даёт долговременного
доверия, к тому же в иерархии сертификатов Windows может быть выбран
неверный узел при экспорте вручную из браузера.

**Как получить и установить правильный (корневой) сертификат:**
```bash
# На сервере (CT 600) — вывести именно корневой сертификат
cat /var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt
```
Скопировать полный вывод (от `-----BEGIN CERTIFICATE-----` до `-----END
CERTIFICATE-----`) в файл `caddy-root-ca.crt` на клиенте, затем на
Windows: двойной клик → **Установить сертификат** → **Локальный
компьютер** → **Поместить все сертификаты в следующее хранилище** →
**Доверенные корневые центры сертификации** → Далее → Готово. Затем
**полностью** закрыть Chrome (проверить через Диспетчер задач отсутствие
`chrome.exe`) и открыть заново.

**Проверка срока действия сертификата на сервере (полезно при повторной диагностике):**
```bash
echo | openssl s_client -connect 192.168.200.230:443 2>/dev/null | openssl x509 -noout -dates
```
