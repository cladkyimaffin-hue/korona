# AI-ADD-DATA-INSTRUCTIONS.md

## Назначение

Этот файл определяет правила безопасного добавления новых данных в базу знаний **Korona**.

Цель — добавлять сведения так, чтобы после каждого изменения:

- содержание документа соответствовало его metadata;
- metadata соответствовали актуальной `SCHEMA.md`;
- теги соответствовали `TAGS.md`;
- `document_id` соответствовал `registry.csv`;
- внутренние ссылки были актуальными;
- индексы отражали текущую структуру;
- связанные документы были указаны корректно;
- новые факты не маскировали конфликты со старыми данными;
- история изменений была отражена в `CHANGELOG.md`;
- другой AI мог понять назначение документа, актуальность данных, источник фактов и связи между документами.

---

## 1. Главный принцип

**Никогда не добавляй новый документ вслепую.**

Перед изменением репозитория обязательно изучи:

1. `AI-INSTRUCTIONS.md`;
2. соответствующий `AI-README.md`;
3. соответствующий `00_Meta/SCHEMA.md`;
4. соответствующий `00_Meta/TAGS.md`;
5. соответствующий `00_Meta/registry.csv`;
6. соответствующий `INDEX.md`;
7. соответствующий `AI-environment_facts-*.md`;
8. `CONFLICTS.md`, если существует;
9. `CHANGELOG.md`;
10. минимум 2–3 существующих документа того же типа.

Если какой-либо из этих файлов отсутствует, устарел или противоречит другим файлам — не выдумывай недостающую информацию. Зафиксируй проблему или запроси уточнение.

---

## 2. Определи домен

Сначала определи, к какому домену относится новая информация.

Используй только существующую структуру репозитория. Например:

- `MikroTik`;
- `Proxmox`.

Если данные относятся к нескольким доменам:

- определи основной домен;
- укажи связанные домены;
- не создавай дубликаты одного и того же документа без необходимости.

Если домен невозможно определить однозначно — запроси уточнение.

---

## 3. Проверь существующие документы

Перед созданием нового файла обязательно выполни поиск по:

- теме;
- hostname;
- IP;
- имени VM/CT;
- имени устройства;
- MAC;
- VLAN;
- service name;
- `document_id`;
- ключевым словам;
- `related_files`.

**Не создавай второй документ, если подходящий документ уже существует.**

Если существующий документ подходит — обнови его.

Если информация относится к нескольким документам — определи authoritative source и используй ссылки из остальных документов.

---

## 4. Классифицируй данные

Определи тип входящей информации. Используй существующую терминологию проекта.

Возможные типы:

- configuration;
- inventory;
- network;
- infrastructure;
- service;
- security;
- monitoring;
- backup;
- troubleshooting;
- procedure;
- architecture;
- planning;
- incident;
- historical;
- reference.

Не создавай новый тип, если существующий уже подходит.

---

## 5. Разделяй факты и предположения

Каждое существенное утверждение классифицируй как:

### VERIFIED

Факт подтверждён предоставленными данными или authoritative-документом.

### INFERRED

Вывод логически следует из имеющихся данных, но напрямую не подтверждён.

### UNKNOWN

Достоверной информации нет.

### CONFLICT

Новая информация противоречит существующей.

Не превращай:

- предположение в факт;
- пример в реальную конфигурацию;
- старую информацию в текущую;
- комментарий в authoritative fact.

Если источник не указан, не выдумывай его.

---

## 6. Источник и дата

Для существенной технической информации по возможности указывай происхождение.

Если это предусмотрено текущей схемой, используй поля:

```yaml
source:
source_type:
verified_at:
```

Допустимые типы источников:

- `user_input`;
- `configuration_export`;
- `command_output`;
- `documentation`;
- `monitoring`;
- `inventory`;
- `historical_record`;
- `external_reference`.

Не выдумывай источник или дату.

---

## 7. Metadata

Каждый новый Markdown-документ обязан соответствовать текущей:

```text
00_Meta/SCHEMA.md
```

Не копируй metadata механически из другого документа.

Проверь все поля, предусмотренные схемой. В частности, если они разрешены текущей схемой:

```yaml
document_id:
title:
description:
category:
tags:
status:
priority:
ai_summary:
dont_repeat:
related_files:
```

Не добавляй произвольные поля, которых нет в актуальной схеме, без необходимости сначала изменить саму схему.

---

## 8. Title

Проверь цепочку:

```text
frontmatter.title
        ↓
H1 документа
        ↓
INDEX.md
        ↓
registry.csv
```

`title` должен точно описывать содержание документа.

Если проект требует совпадения `title` и H1 — они должны совпадать.

После переименования не оставляй старое название в registry или индексах.

---

## 9. Description

`description` должен отвечать:

> Что находится в документе и зачем AI нужно к нему обращаться?

Плохой пример:

```yaml
description: Proxmox
```

Хороший пример:

```yaml
description: Конфигурация и параметры Proxmox-кластера, включая сетевую архитектуру, storage, HA и связанные сервисы.
```

Не описывай сведения, которых нет в документе.

---

## 10. AI Summary

`ai_summary` должен позволять AI понять документ до полного чтения.

Укажи:

- назначение;
- основные сущности;
- важные зависимости;
- ключевые параметры;
- типы запросов, для которых документ релевантен.

Не копируй в `ai_summary` весь документ.

---

## 11. Dont Repeat

`dont_repeat` должен объяснять AI, какие сведения не следует дублировать в других документах.

Например:

```yaml
dont_repeat:
  - IP-адреса и параметры интерфейсов брать из network inventory
  - параметры VM брать из соответствующего VM inventory
  - исторические сведения не считать текущей конфигурацией
```

Используй поле для предотвращения расхождения данных.

---

## 12. Related Files

`related_files` должен содержать только реально существующие или создаваемые в рамках операции файлы.

Не оставляй ссылки на:

- старое имя файла;
- удалённый файл;
- несуществующий документ;
- неактуальный путь.

После переименования обнови все связанные ссылки.

---

## 13. Tags

Используй **только канонические теги из `TAGS.md`**.

Перед сохранением:

1. прочитай `TAGS.md`;
2. проверь каждый tag;
3. исправь регистр;
4. убери дубликаты;
5. убери неизвестные теги;
6. при необходимости предложи изменение `TAGS.md`.

Например, если каноническим является:

```text
Zabbix
```

не создавай самостоятельно:

```text
zabbix
```

если такой вариант не разрешён схемой тегов.

---

## 14. Document ID

**Не придумывай `document_id` для существующего документа.**

Сначала проверь:

```text
00_Meta/registry.csv
```

Для нового документа:

1. найди следующий допустимый ID по правилам проекта;
2. проверь отсутствие коллизии;
3. добавь запись в registry;
4. используй тот же ID во frontmatter.

После изменения должно выполняться:

```text
frontmatter.document_id == registry.document_id
```

---

## 15. Registry

После создания, удаления или переименования документа проверь `registry.csv`.

Для каждой записи должны совпадать:

- `document_id`;
- `title`;
- `path`;
- `category`;
- `status`;
- `tags`;
- остальные обязательные поля.

Особенно:

```text
registry.path == реальный путь файла
registry.title == frontmatter.title
```

---

## 16. INDEX.md

После добавления документа обнови соответствующий `INDEX.md`.

Проверь:

- название;
- ссылку;
- краткое назначение;
- релевантные вопросы/темы, если такой формат используется;
- теги, если они предусмотрены индексом.

Каждая ссылка должна вести на существующий файл.

---

## 17. AI-README

Обновляй соответствующий `AI-README.md`, если меняется:

- структура домена;
- способ поиска информации;
- назначение документов;
- authoritative source;
- правила навигации.

Не превращай AI-README в бессмысленный список всех файлов.

Он должен отвечать:

> Где искать какую информацию?

---

## 18. Environment Facts

Если новые сведения являются инфраструктурными фактами, проверь соответствующий:

```text
AI-environment_facts-*.md
```

Особенно проверяй:

- IP;
- VLAN;
- hostname;
- VM;
- CT;
- Proxmox node;
- storage;
- router;
- switch;
- firewall;
- monitoring;
- backup;
- DNS;
- DHCP;
- hardware.

Если новое значение противоречит старому:

**не исправляй старое значение молча.**

Определи, является ли оно:

- `CURRENT`;
- `HISTORICAL`;
- `CONFLICT`;
- `UNKNOWN`.

Если невозможно установить актуальное значение — зафиксируй конфликт.

---

## 19. CONFLICTS

Если новые данные противоречат существующим, создай или обнови `CONFLICTS.md`.

Используй понятную структуру:

```markdown
## Conflict: <topic>

### Existing information
<старое значение>

### New information
<новое значение>

### Source
<источник>

### Status
OPEN

### Required verification
<что необходимо проверить>
```

Не выбирай победившее значение без достаточного подтверждения.

После проверки:

```text
OPEN → RESOLVED
```

и укажи источник окончательного решения.

---

## 20. Исторические данные

Не удаляй старый факт только потому, что появилась новая конфигурация.

Если старое значение действительно было актуальным ранее, обозначь его как историческое в соответствии со схемой проекта.

Например:

```text
2025:
1 GbE

2026:
10 GbE
```

Историческое значение не должно выглядеть как текущая конфигурация.

---

## 21. Ссылки

После каждого изменения проверь:

- Markdown links;
- relative paths;
- `related_files`;
- registry paths;
- INDEX links;
- AI-README links;
- ссылки из environment facts;
- ссылки на переименованные документы.

Не должно оставаться ссылок на несуществующие файлы.

---

## 22. Не дублируй факты

Если IP, VLAN, hostname, VMID или другой факт уже хранится в authoritative-документе, предпочитай ссылку на источник вместо повторного копирования значения.

Особенно избегай неконтролируемого дублирования:

- IP;
- hostname;
- VLAN;
- VM ID;
- CT ID;
- hardware identifiers;
- storage identifiers;
- service endpoints.

Цель — минимизировать количество мест, которые нужно менять при изменении факта.

---

## 23. Имена файлов

Перед созданием имени проверь существующие соглашения.

Имя файла должно:

- отражать содержание;
- быть уникальным;
- соответствовать структуре домена;
- не конфликтовать с существующим;
- быть понятным другому AI.

При переименовании:

1. переименуй файл;
2. обнови `registry.csv`;
3. обнови `INDEX.md`;
4. обнови `related_files`;
5. обнови `AI-README.md`, если необходимо;
6. найди и исправь старые ссылки;
7. обнови `CHANGELOG.md`.

---

## 24. Не исправляй факты по предположению

Нельзя самостоятельно менять инфраструктурный факт только потому, что он кажется неправильным.

Особенно осторожно относись к:

- IP;
- сетям;
- firewall;
- маршрутам;
- VLAN;
- HA;
- storage;
- backup;
- security;
- hardware.

При сомнении:

```text
DO NOT GUESS.
```

Зафиксируй вопрос или конфликт.

---

## 25. Добавление нового документа

Используй следующий порядок:

```text
1. определить домен
2. изучить SCHEMA
3. изучить TAGS
4. изучить registry
5. найти похожие документы
6. проверить существование информации
7. определить authoritative source
8. определить category
9. определить tags
10. создать document_id
11. создать документ
12. заполнить frontmatter
13. написать содержание
14. добавить related_files
15. обновить registry
16. обновить INDEX
17. обновить AI-README при необходимости
18. проверить environment facts
19. проверить CONFLICTS
20. обновить CHANGELOG
21. выполнить финальную валидацию
```

---

## 26. Обновление существующего документа

Если документ уже существует:

**не создавай новый документ.**

Сравни старое содержание с новыми данными.

Затем:

- добавь только новую информацию;
- сохрани полезную историю;
- не дублируй существующие факты;
- обнови metadata;
- обнови registry;
- обнови индекс при необходимости;
- обнови CHANGELOG.

---

## 27. CHANGELOG

Каждая структурная операция должна быть отражена в `CHANGELOG.md`.

Укажи:

- дату;
- что изменено;
- какие документы затронуты;
- причину;
- источник, если известен.

Описание должно быть конкретным.

Хорошо:

```text
Added network inventory for MikroTik router.
Updated metadata and registry.
Added related links to firewall and VLAN documentation.
Source: user-provided configuration export.
```

---

## 28. Финальная проверка

Перед завершением выполни полный audit:

```text
[ ] YAML/frontmatter валиден
[ ] document_id уникален
[ ] document_id есть в registry
[ ] registry path существует
[ ] registry title совпадает с title
[ ] title совпадает с H1, если это предусмотрено правилами
[ ] category допустим
[ ] все tags существуют в TAGS.md
[ ] tags не дублируются
[ ] description соответствует документу
[ ] ai_summary соответствует документу
[ ] dont_repeat актуален
[ ] related_files существуют
[ ] INDEX содержит документ
[ ] ссылки INDEX рабочие
[ ] AI-README актуален
[ ] environment facts проверены
[ ] конфликты зафиксированы
[ ] CHANGELOG обновлён
[ ] старые ссылки отсутствуют
[ ] дубликаты документов отсутствуют
[ ] дублирование фактов минимизировано
```

---

## 29. Проверка качества содержания

Кроме metadata проверь документ на:

### Актуальность

Историческая информация не выдаётся за текущую.

### Полноту

Присутствуют необходимые параметры.

### Однозначность

Понятно, к какому объекту относится каждый факт.

### Трассируемость

Понятно происхождение важных фактов.

### Связность

Есть переходы к связанным сущностям.

### AI-readability

Другой AI сможет найти документ через:

- title;
- description;
- tags;
- registry;
- INDEX;
- related_files.

---

## 30. Не делай молчаливых изменений

Если изменение влияет на смысл существующей документации, сообщи:

```text
CHANGED:
<что изменено>

REASON:
<почему>

SOURCE:
<источник>

IMPACT:
<какие документы затронуты>
```

Если есть сомнение — не угадывай.

---

## 31. Приоритет источников

Используй следующий порядок для определения, где искать подтверждение:

```text
1. актуальный подтверждённый configuration/export
2. актуальный command output
3. подтверждённый inventory
4. официальная документация инфраструктуры
5. существующий authoritative document
6. историческая документация
7. пользовательское описание без подтверждения
8. предположение AI
```

Это порядок доверия к источнику, а не разрешение автоматически объявлять более высокий источник истинным при наличии конфликта.

**Предположение AI никогда не должно превращаться в VERIFIED FACT.**

---

## 32. Идентификация инфраструктурных объектов

Для объектов инфраструктуры по возможности используй несколько идентификаторов.

Например:

```text
Object:
Proxmox VM

Identity:
VMID: 2001
Hostname: example
IP: 192.168.x.x
Role: monitoring

Relations:
Node: pve01
Service: Zabbix
Network: VLAN xxx
```

Для MikroTik:

```text
Device:
Router

Identity:
Hostname:
Model:
Serial:
Management IP:

Relations:
WAN:
LAN:
VLAN:
Firewall:
Routing:
Monitoring:
```

Это логическая модель. Не добавляй новые поля во frontmatter, если их нет в актуальной `SCHEMA.md`.

---

## 33. Единый источник истины

Каждый важный факт должен иметь одно основное место хранения.

Например:

```text
IP address
    ↓
network inventory
    ↓
other documents reference it
```

а не:

```text
document A → IP
document B → IP
document C → IP
document D → IP
```

При изменении значения должно быть понятно, какой документ является источником истины.

## 35. Критерий завершения

Работа считается завершённой только если новая информация не просто записана в Markdown, а полностью интегрирована в систему знаний:

```text
NEW DATA
   ↓
DOCUMENT
   ↓
FRONTMATTER
   ↓
SCHEMA
   ↓
TAGS
   ↓
REGISTRY
   ↓
INDEX
   ↓
RELATED FILES
   ↓
ENVIRONMENT FACTS
   ↓
CONFLICTS
   ↓
CHANGELOG
   ↓
VALIDATION
```

Если какой-либо этап не может быть выполнен из-за отсутствия данных — явно укажи это в `NEEDS HUMAN VERIFICATION`.

---

## Главное правило

Твоя задача — не просто добавить текст.

Твоя задача:
