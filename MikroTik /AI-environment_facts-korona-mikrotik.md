# AI-environment_facts-korona-mikrotik.md

Подтверждённые факты об инфраструктуре MikroTik/RouterOS в составе
`korona`. Источник истины для сверки при обработке новых документов
(протокол конвейера, `../AI-INSTRUCTIONS.md`, раздел 8а, шаг 5).

## Устройство
- Модель: **CRS326-24G-2S+**, RouterOS **7.23.1** (stable), ARM 2×800MHz, 512 MiB RAM, 16 MiB NAND (свободно ~3 МБ — штатная особенность модели, не угроза).
- WAN физически: `sfp-sfpplus2`; логически: `pppoe-out1` (публичный IP `89.109.14.221/32`, dynamic; шлюз провайдера `79.126.0.1`).
- IPv6, UPnP, SNMP — отключены. Скрипты/планировщик — не используются.

## Сети (подтверждено, отменяет предыдущую предварительную запись)
- **`192.168.200.0/22`** (не `/24`, как предполагалось изначально) — основная LAN, интерфейс `bridge_localnet` (`192.168.200.1`).
- `192.168.1.0/24` — дополнительная LAN «Video», интерфейс `bridge_video` (`192.168.1.1`).
- Доверенный внешний IP источника VDI (после NAT провайдера): `91.217.9.238`.
- DHCP (`server1` на `bridge_localnet`, пул `pool-dhcp` 192.168.201.1–192.168.203.200, 276 активных аренд): выдаёт шлюз `192.168.200.1`, DNS `192.168.200.225` + `192.168.200.2`, домен `krnn.ru`.
  **Совпадает с доменом Proxmox**: `192.168.200.225` = ВМ `AD` (бывший `WIN-AD`, alias `2002`), `192.168.200.2` = `DC` — оба уже известны из `Proxmox/AI-environment_facts-korona-proxmox.md`. Один физический сегмент сети обслуживает оба домена документации.
- Bridge `bridge_localnet`: активные порты ether2–ether15; неактивные ether1, ether16–ether20; плюс `eoip-tunnel1` (disabled, не используется).
- Bridge `bridge_video`: активные ether22, ether24; неактивные ether21, ether23.
- Routing: только default (`0.0.0.0/0` via `pppoe-out1`) + connected-маршруты для обеих LAN. Policy routing отсутствует (mangle пуст).

## Проверенные ранее «известные аномалии» — итог
1. Legacy-правила NAT/Filter с `dst-address=192.168.199.1` — **подтверждено, реально существуют** (5 правил NAT, 1 правило Filter), мертвы (подсеть `192.168.199.0/24` нигде не маршрутизируется). Кандидаты на удаление — см. `NETWORK-MIKROTIK-FIREWALL-NAT-CLEANUP-2026-001`.
2. Дублирующее правило NAT `#21` (`src-address=172.19.1.30`) vs `#22` (`src-address=91.217.9.238`) — **не найдено при аудите**, в текущей конфигурации таких правил нет. Либо исходное предположение устарело, либо правила были удалены до этого аудита — причина не установлена, факт просто отмечается как не подтвердившийся.

## Управление устройством
- `ssh`, `www` (80), `winbox` (8291) — включены, **без ограничения `allowed-addresses`** (открыты для любого источника с LAN/VPN, WAN-доступ прикрыт firewall-правилами #11/#13).
- `mac-server`: `allowed-interface-list: all` — управление по MAC разрешено со всех интерфейсов.
- Локальные пользователи: только `admin` (группа `full`).
- Сертификаты: CA `sstp-korona-ca` + `cert-korona-sstp-server` (SAN: `hkb0akb33z4.sn.mynetname.net`, IP `89.109.14.221`) — оба валидны на момент аудита.

## VPN
- L2TP/IPsec и SSTP (порт 444) включены; PPTP отключён.
- 18 PPP-пользователей, профиль `vpn_profile` существует, но реально не используется — все на `profile=default`.
- Активные VPN-сессии есть (напр. `Gorelova`, `Brednev`), но получают адреса из нерабочего пула `pool-vpn` (`192.168.199.151-250`, подсеть `199.x` нигде не маршрутизируется).

## Статус аудита
Полный read-only аудит (интерфейсы, routing, firewall filter/mangle/raw/
address-list, NAT, VPN, DHCP/DNS/NTP, система, сертификаты, пользователи)
**завершён 2026-09-19**. Найденные проблемы задокументированы отдельно по
категориям, **ни одно исправление ещё не применено** — все рекомендации
из аудита остаются открытыми (см. `05_Troubleshooting/Критические
уязвимости — план устранения.md`).
