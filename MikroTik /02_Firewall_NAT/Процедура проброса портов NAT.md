# Процедура настройки проброса портов (NAT)

## Когда применять
Разовый запрос вида «нужен RDP/SSH/другой доступ к конкретному серверу
X снаружи» — точечный проброс одного порта на один сервер. **Не путать
со сценарием «новому человеку нужен полноценный доступ к сети» —
для этого см. VPN, отдельная процедура (не описана здесь, см. открытый
вопрос в конце документа).**

## Чек-лист (заполняет администратор перед запросом)
- [ ] Целевой сервер (имя/назначение): _________
- [ ] Внутренний IP сервера: _________
- [ ] Внутренний порт сервиса: _________ (3389 RDP / 22 SSH / другой)
- [ ] Желаемый внешний порт: _________ (или «предложи свободный»)
- [ ] Источник подключения: VDI (`91.217.9.238`) / конкретный IP / любой
- [ ] Паттерн `dst-address`: без (по умолчанию) / legacy `192.168.199.1` (см. предупреждение) / публичный `89.109.14.221`

## Три паттерна `dst-address`

| Паттерн | Когда использовать |
|---|---|
| **Без `dst-address`** | По умолчанию для новых правил — самый универсальный, пакет приходит на любой адрес роутера. |
| **`dst-address=192.168.199.1`** | ⚠️ Legacy. Один источник называет его «реально рабочим паттерном организации», другой (более поздний полный аудит) — мёртвым. Не использовать для новых правил без проверки на реальном устройстве. |
| **`dst-address=89.109.14.221`** | Когда нужно жёстко привязать правило к публичному IP (несколько внешних адресов на роутере). |

## Шаблон команды
```routeros
/ip firewall nat add chain=dstnat action=dst-nat protocol=tcp \
  in-interface=pppoe-out1 \
  src-address=<источник или пусто для любого> \
  dst-port=<внешний порт> \
  to-addresses=<внутренний IP сервера> to-ports=<внутренний порт> \
  comment="<Сервис>_<Сервер> from <Источник>"
```

**Перед выполнением — проверить, что внешний порт свободен:**
```routeros
/ip firewall nat print where dst-port=<порт>
```

## Подтверждённый реальный пример (2026-09-20)
Запрос: «SSH-доступ с рабочей машины `172.19.1.30` к серверу
`192.168.200.224`, порт 22» — типовая ошибка на старте: `172.19.1.30`
оказался **внутренним** IP машины на стороне VDI-провайдера, администратору
его назвали по ошибке. MikroTik видит только внешний адрес **после** NAT
провайдера — им оказался `91.217.9.238` (уже присутствовал в
`environment_facts` как доверенный IP VDI).

**Итоговое рабочее правило** (старое ошибочное правило с
`src-address=172.19.1.30` сознательно не удалялось — оставлено как
исторический артефакт, не как рекомендация):
```routeros
/ip firewall nat add chain=dstnat action=dst-nat protocol=tcp \
  in-interface=pppoe-out1 dst-address=89.109.14.221 dst-port=2222 \
  src-address=91.217.9.238 to-addresses=192.168.200.224 to-ports=22 \
  comment="Srv1c SSH from VDI egress"
```
Подтверждено: SSH-вход с VDI через порт 2222 проходит, сервер отвечает.
На сервере `192.168.200.224` дополнительно настроен Windows Firewall —
разрешение только для `91.217.9.238`, OpenSSH — вход по ключу.

**Урок:** когда пользователь называет «свой IP» для проброса — уточнять,
это адрес **до** или **после** NAT на его стороне. Внутренний адрес
источника (за чужим NAT) в правиле MikroTik никогда не сработает.

## Обязательный шаг после создания правила
Напомнить и/или настроить на целевом сервере (Windows):
```powershell
New-NetFirewallRule -DisplayName "<Сервис> from <Источник>" -Direction Inbound -LocalPort <внутренний_порт> -Protocol TCP -Action Allow -RemoteAddress <источник>
```

## Проверка результата
```routeros
/ip firewall nat print detail where comment="<comment>"
/ip firewall connection print where dst-port=<внешний порт>
```

## ⛔ Don't repeat
См. `dont_repeat` во фронтматтере.

## Открытый вопрос — сценарий «новому человеку нужен доступ из дома»
Точечный проброс порта (эта процедура) **не подходит** для случая, когда
человеку нужен полноценный доступ к внутренней сети из дома — для этого
в организации уже есть VPN (L2TP/IPsec, SSTP), но он в известном
нерабочем состоянии — см. `NETWORK-MIKROTIK-VPN-PROFILE-BROKEN-2026-001`.
Процедура онбординга нового VPN-пользователя не описана отдельным
документом — обсуждалось в чате, не зафиксировано письменно.
