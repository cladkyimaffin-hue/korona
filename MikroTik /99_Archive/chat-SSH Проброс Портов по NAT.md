## Шаг 1 — Сбор контекста (уточнение перед настройкой)

Смотрю на скриншот: у тебя MikroTik RouterOS, вкладка NAT, все существующие `dstnat`-правила используют:

### Предварительный шаблон правила (пока без подтверждения):

```routeros

  chain=dstnat \
  action=dst-nat \
  protocol=tcp \
  in-interface=pppoe-out \
  dst-address=192.168.199.1 \
  dst-port=22 \
  src-address=172.19.1.30 \
```

### Предварительный скрипт (будет уточнён после ответа про диск)

Скрипт сгенерирует команды REBUILD/REORGANIZE только для индексов, где это даст эффект:

```sql
-- Генерация команд обслуживания индексов для MS_ERP
-- Пороги: >30% фрагментации и page_count > 1000 → REBUILD ONLINE
--         5-30% фрагментации и page_count > 1000 → REORGANIZE
--         <5% или page_count < 1000 → пропуск

SET NOCOUNT ON;

SELECT 
    CASE 
        WHEN ips.avg_fragmentation_in_percent > 30 AND ips.page_count > 1000 
            THEN 'ALTER INDEX [' + i.name + '] ON [' + s.name + '].[' + t.name + '] REBUILD WITH (ONLINE = ON, SORT_IN_TEMPDB = ON);'
        WHEN ips.avg_fragmentation_in_percent BETWEEN 5 AND 30 AND ips.page_count > 1000 
            THEN 'ALTER INDEX [' + i.name + '] ON [' + s.name + '].[' + t.name + '] REORGANIZE;'
        ELSE NULL
    END AS command,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    s.name AS schema_name,
    t.name AS table_name,
    i.name AS index_name
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
INNER JOIN sys.tables t ON ips.object_id = t.object_id
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 5
  AND ips.page_count > 1000
  AND i.name IS NOT NULL
ORDER BY ips.page_count DESC;

-- Отдельно для HEAP BinaryData
SELECT 'ALTER TABLE [dbo].[BinaryData] REBUILD WITH (ONLINE = ON);' AS command,
       'HEAP rebuild' AS note;
```

1. Запустить скрипт — он выведет список команд
2. Скопировать команды в новое окно SSMS
3. Выполнить ночью в окне обслуживания

**Откат:** не требуется. REBUILD/REORGANIZE не удаляют данные.

### Скрипт

Запустить в SSMS в контексте базы **MS_ERP**:

```sql
USE [MS_ERP];
GO
SET NOCOUNT ON;

-- 1. Проверка свободного места в tempdb (нужно для ONLINE REBUILD)
SELECT 
    name AS file_name,
    size_mb = size / 128.0,
    free_mb = (size - FILEPROPERTY(name, 'SpaceUsed')) / 128.0
FROM tempdb.sys.database_files;
GO

-- 2. Генерация команд обслуживания индексов
-- Пороги: >30% + page_count>1000 → REBUILD ONLINE
--         5-30% + page_count>1000 → REORGANIZE
--         <5% или page_count<1000 → пропуск (шум)

SELECT 
    CASE 
        WHEN ips.avg_fragmentation_in_percent > 30 AND ips.page_count > 1000 
            THEN N'ALTER INDEX [' + i.name + N'] ON [' + s.name + N'].[' + t.name + N'] REBUILD WITH (ONLINE = ON);'
        WHEN ips.avg_fragmentation_in_percent BETWEEN 5 AND 30 AND ips.page_count > 1000 
            THEN N'ALTER INDEX [' + i.name + N'] ON [' + s.name + N'].[' + t.name + N'] REORGANIZE;'
        ELSE NULL
    END AS command,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    s.name AS schema_name,
    t.name AS table_name,
    i.name AS index_name,
    i.type_desc AS index_type
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
INNER JOIN sys.tables t ON ips.object_id = t.object_id
INNER JOIN sys.schemas s ON t.schema_id = s.schema_id
INNER JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.avg_fragmentation_in_percent > 5
  AND ips.page_count > 1000
  AND i.name IS NOT NULL
ORDER BY ips.page_count DESC;
GO

-- 3. Отдельно: HEAP BinaryData (ALTER INDEX не работает для HEAP)
SELECT 
    N'ALTER TABLE [dbo].[BinaryData] REBUILD WITH (ONLINE = ON);' AS command,
    N'HEAP rebuild' AS note;
GO
```

2. **Затем** выполни блоки №2 и №3 — они выведут список команд.

## Просмотр NAT-правил в консоли MikroTik

**Краткий режим** — показываю команды для проверки созданного правила.

### 1. Показать все NAT-правила (базовый список)
```bash
/ip firewall nat print
```

### 2. Показать правила с деталями (полная информация)
```bash
/ip firewall nat print detail
```
Покажет все поля: `chain`, `action`, `src-address`, `dst-address`, `protocol`, `in-interface`, `to-addresses`, `to-ports`, `comment`.

### 3. Показать правило по номеру (если знаешь ID)
```bash
/ip firewall nat print detail where .id=*16
```
(замени `*16` на номер твоего правила, например `*22` как на скриншоте)

### 4. Найти правило по комментарию
```bash
/ip firewall nat print detail where comment="Srv1c SSH from VDI egress"
```

### 5. Показать статистику (счётчики пакетов)
```bash
/ip firewall nat print stats
```
Покажет `bytes` и `packets` — сколько трафика прошло через каждое правило.

### 6. Проверить активные SSH-подключения
```bash
/ip firewall connection print where dst-port=22
```
Покажет текущие подключения: `src-address` (кто подключился), `dst-address` (куда), `bytes` (трафик).

### 7. Экспорт правил (для сохранения/копирования)
```bash
/ip firewall nat export
```
Покажет правила в формате команд — удобно для бэкапа или переноса на другой роутер.

## Разбор NAT-правила MikroTik

Это одно правило `dst-nat` (Destination NAT, оно же «проброс порта»). Разберу по полям и по потоку пакета.

### Поля правила

| Поле | Значение | Что означает |
|---|---|---|
| `chain=dstnat` | `dstnat` | Цепочка обработки. Срабатывает, когда пакет **пришёл на сам роутер** (а не транзитом через него). Именно сюда попадают запросы на внешний IP роутера. |
| `action=dst-nat` | `dst-nat` | Действие: **изменить адрес назначения** в пакете и перенаправить его на другой хост внутри сети. |
| `in-interface=pppoe-out1` | `pppoe-out1` | Фильтр: правило применяется только к пакетам, пришедшим через интерфейс PPPoE (внешний канал в интернет). |
| `protocol=tcp` | `tcp` | Только TCP-трафик (SSH работает по TCP). |
| `src-address=91.217.9.238` | `91.217.9.238` | Фильтр по источнику: правило сработает **только** если пакет пришёл с этого IP. Это внешний адрес VDI-KB после NAT оператора. Ограничение безопасности — никто другой не сможет подключиться. |
| `dst-address=89.109.14.221` | `89.109.14.221` | Фильтр по адресу назначения: пакет должен быть адресован этому внешнему IP (это «белый» адрес, который «висит» на интерфейсе `pppoe-out1` роутера). |
| `dst-port=2222` | `2222` | Фильтр по порту назначения: пользователь стучится на порт **2222** внешнего IP роутера. |
| `to-addresses=192.168.200.224` | `192.168.200.224` | **Куда** перенаправить: внутренний IP сервера Srv1c. |
| `to-ports=22` | `22` | **На какой порт** внутри: стандартный SSH-порт на Srv1c. |

### Поток пакета (пошагово)

```
[VDI-KB 172.19.1.30]
        │
        │  (оператор делает SNAT)
        ▼
[Интернет]  src=91.217.9.238, dst=89.109.14.221:2222
        │
        ▼
[MikroTik pppoe-out1]
        │  Правило dstnat:
        │  - dst-address=89.109.14.221 ✓
        │  - dst-port=2222 ✓
        │  - src-address=91.217.9.238 ✓
        │  - in-interface=pppoe-out1 ✓
        │  → меняем dst на 192.168.200.224:22
        ▼
[Srv1c 192.168.200.224:22]  ← OpenSSH отвечает
```

### Почему именно так (ключевые моменты)

1. **Почему `src-address=91.217.9.238`, а не `172.19.1.30`?**
   VDI-KB находится за NAT оператора (или за другим роутером). Когда пакет доходит до твоего MikroTik, его исходный адрес уже заменён на внешний `91.217.9.238`. MikroTik никогда не видит `172.19.1.30` — это и была причина, почему старое правило не работало.

2. **Почему `dst-address=89.109.14.221`, а не внутренний IP?**
   Пользователь подключается к **внешнему** адресу роутера (`89.109.14.221:2222`). MikroTik видит пакет, адресованный этому IP, и только потом меняет его на внутренний `192.168.200.224`. Если бы в правиле стоял внутренний адрес — правило бы никогда не сработало, потому что пакет из интернета на внутренний адрес не придёт.

3. **Почему порт 2222 → 22?**
   Порт 2222 — «внешний» порт на роутере (чтобы не светить стандартный SSH наружу и не конфликтовать с SSH самого MikroTik, если он есть). Внутри сети Srv1c слушает стандартный 22-й порт.

4. **Почему `chain=dstnat`, а не `srcnat`?**
   `dstnat` — меняет **адрес назначения** (проброс внутрь). `srcnat` (маскарад) — меняет **адрес источника** (чтобы внутренние хосты могли выходить в интернет). Для проброса SSH нужен именно `dstnat`.

### Обратный поток (ответ от Srv1c)

MikroTik автоматически помнит соответствие в таблице conntrack. Когда Srv1c отвечает, роутер сам меняет `src=192.168.200.224:22` обратно на `src=89.109.14.221:2222` — это происходит прозрачно, отдельное правило не нужно.

### Ключевые моменты

1. **Двойной NAT**: VDI-KB → NAT оператора → MikroTik → Srv1c. MikroTik видит только адрес после первого NAT (`91.217.9.238`), а не оригинальный `172.19.1.30`.

3. **Conntrack**: Обратная трансляция происходит автоматически — отдельное правило для return-трафика не нужно.

4. **Фильтр по src-address**: Только `91.217.9.238` может подключиться — это ограничение безопасности на уровне NAT.

## Откуда взялся 91.217.9.238

Это **внешний (публичный) IP-адрес VDI-KB после NAT оператора связи**.

### Как это работает

```
─────────────────────────────────────────────────────────────────┐
│  VDI-KB (внутри сети оператора)                                  │
│  Внутренний IP: 172.19.1.30  ← частный диапазон 172.16.0.0/12   │
─────────────────────────────────────────────────────────────────┘
         │
         │  Запрос в интернет (SSH на 89.109.14.221:2222)
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  NAT оператора связи (прозрачно для тебя)                        │
│  SNAT: 172.19.1.30 → 91.217.9.238                                │
│  (оператор заменяет внутренний IP на свой публичный)             │
─────────────────────────────────────────────────────────────────┘
         │
         │  Пакет идёт через интернет
         ▼
┌─────────────────────────────────────────────────────────────────┐
│  MikroTik видит пакет:                                           │
│  src: 91.217.9.238  ← именно этот адрес, а не 172.19.1.30        │
│  dst: 89.109.14.221:2222                                         │
─────────────────────────────────────────────────────────────────┘
```

### Почему так

1. **VDI-KB находится за NAT оператора** — у него нет своего публичного IP, только внутренний `172.19.1.30`
2. **Оператор делает SNAT** (Source Network Address Translation) — заменяет внутренний адрес на свой публичный `91.217.9.238`, чтобы пакет мог дойти до интернета
3. **MikroTik никогда не видит `172.19.1.30`** — до него доходит только адрес после NAT оператора
