# 📐 SCHEMA.md — канонический формат метаданных документа (общее ядро)

Этот файл — единственный источник правды о том, какие поля фронтматтера
обязательны, а какие опциональны, для **всех доменов** репозитория
(`Proxmox/`, `MikroTik/` и любых добавленных позже). До 2026-10-20 существовали
две копии — в `Proxmox/00_Meta/` и в `MikroTik/00_Meta/`; они почти не
отличались и могли разойтись, поэтому общее ядро вынесено в корень.

Доменные файлы `<домен>/00_Meta/SCHEMA.md` остаются и содержат только то,
что зависит от домена (список категорий, доменные значения опциональных
полей). Если доменный файл противоречит этому файлу — приоритет у этого файла,
а расхождение записывается в `<домен>/00_Meta/CONFLICTS.md`.

Конвейер (ИИ или скрипт), обрабатывающий любой документ, обязан сверяться
с этим файлом, а не с тем, что видит в соседних файлах — соседние файлы могут
быть написаны по старой версии схемы, и это нормально (см. раздел «Принцип
эволюции» ниже).

## 1. Обязательное ядро (15 полей)

Присутствует в **каждом** документе без исключений. Проверка выполняется по
этому файлу. Скрипт `validate.py`, упомянутый в версии 1.0, в репозитории не
найден (проверено 2026-10-20 в корне и в `Proxmox/00_Meta/`); до его появления
проверка ручная.

```yaml
document_id: ""        # уникален в пределах registry.csv своего домена, формат см. ниже
title: ""               # человекочитаемое название, совпадает с H1 в теле файла
document_type: ""       # runbook | troubleshooting | reference | setup | meta
status: ""               # draft | in_progress | completed | archived
priority: ""             # critical | high | medium | low | info
date_created: 2026-01-01
date_modified: 2026-01-01
next_review: 2026-01-01
author: ""
category: ""              # имя целевой папки домена; точный список — в AI-README.md и в <домен>/00_Meta/SCHEMA.md
tags: []                  # значения только из <домен>/00_Meta/TAGS.md, без исключений
ai_summary: ""            # 1-2 предложения, по которым ИИ находит документ без чтения всего тела
dont_repeat: []            # запреты/грабли из этого документа, если применимо; иначе []
related_files: []          # ссылки на другие document_id, с которыми документ логически связан
schema_version: "1.0"      # версия ЭТОЙ схемы, под которую написан документ — см. раздел 3
```

### Формат `document_id`

`<ОБЛАСТЬ>-<ТЕМА>-<ГГГГ>-<NNN>`, например `CEPH-OSD-PLANNING-2026-001`,
`PROXMOX-VM-CLONE-2001-2026-001`. Уникальность проверяется по `registry.csv`
перед присвоением — не изобретается на глаз.

## 2. Опциональный расширенный блок

Добавляется **только если документ реально об этом** — не по умолчанию,
не «на будущее про запас». Если в документе фигурирует конкретная ВМ, узел
или окружение — используйте нужные поля из списка, остальные не пишите вообще
(лучше отсутствие поля, чем поле со значением `""`).

```yaml
environment: ""       # production | staging | test
target_system: ""
hostname: ""
node: ""               # имя узла или устройства; допустимые значения — в <домен>/00_Meta/SCHEMA.md
cluster: ""             # имя кластера, если применимо
vm_id: ""
keywords: []             # альтернативные формулировки для полнотекстового поиска
aliases: []               # другие названия того же инцидента/документа
confidentiality: ""       # public | internal (по умолчанию internal, если не указано)
superseded_by: ""         # document_id документа, который заменил этот; указывается вместе со status: archived
last_verified: 2026-01-01 # дата последней сверки фактов документа с живой системой; не равна date_modified
```

**Почему не 266 полей, как в самом подробном текущем документе**: при проверке
образца (`Зависание ssh...md`) 64 из 266 полей были пустыми — заполнение под
будущее использование, которое так и не случилось. Прагматика: поле существует
в схеме только если хотя бы один реальный документ в архиве его заполнил
осмысленным значением.

## 3. Принцип эволюции схемы (важно)

Схема будет меняться со временем — это нормально и предусмотрено, а не
исключение. Правило: **аддитивно и по ситуации, без ретроактивного переписывания
того, что не затронуто**.

1. **Если ничего не случилось** — документ, написанный под `schema_version: "1.0"`,
   остаётся под `"1.0"` сколько угодно. Проверка идёт по версии схемы, под
   которой подписан документ, а не по последней версии `SCHEMA.md`.
   Массовая миграция старых документов на новую версию схемы **не выполняется
   автоматически**.
2. **Если что-то случилось и это затронуло документ** (нашли противоречие,
   документ редактируется по факту реального изменения инфраструктуры,
   или новое поле обязательно именно для его типа) — тогда при следующем
   редактировании именно этого документа он поднимается до текущей версии
   схемы, и только он.
3. Каждое изменение самой схемы фиксируется здесь, в разделе «История версий»
   ниже, с датой и причиной — не молча.
4. Breaking change (переименование поля, смена формата) допускается только
   с записью в `<домен>/00_Meta/CONFLICTS.md` — так как он может сделать старые
   документы формально невалидными, и это требует вашего подтверждения,
   а не тихого решения ИИ. Добавление опциональных полей breaking change
   не является.
